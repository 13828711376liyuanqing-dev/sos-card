# OTA 合并后失败：定位与修复方案

SAM | 2026-11-06 +08:00 | 状态：待实施方案。依据最新日志、合并前备份、源码和一次针对性主机复现；未证明此次实板走了哪条拒绝分支。按方案设计技能整理，不修改固件。

## 1. 结论与证据边界

本轮 1.5.12/b16 → 1.5.13/b17 在GR传输完成后、安装前失败。GR OTA目录既有源码与合并前备份一致；新GR业务代码未运行。CAT1接收端已合入业务模块，因此合并仍可能通过链路、时序、活动状态触发原有缺陷，尚未确定具体模块。

已复现的因果链：ACTIVATE到达时safe(true)=false → activation_read_check返回false → 普通短租约路径 → install_check_ready=false → activation_validation_failed → CAT1 on_gr调用transport_fault(reason,true) → spend试装票 → RECOVERY_HOLD。主机stable=false时验证调用0次、安装准备0次、提交0次；stable=true对照执行验证并GRANT。证据在 logs/ota_merge_analysis_20261106/result.log。

CAT1 fresh_safety()使用同owner且小于3秒的GR安全响应；这只能证明刚才安全，不能保证ACTIVATE到达时仍安全。GR要求按键采样100ms内、电池3000ms内、运动1500ms内，且稳定60秒。采样或活动变化均可使两个时刻的结果不同。不能据此断定是运动，亦不能放宽采样时限来修复。

## 3. 第一阶段：保存当前失败证据，关闭归因问题

不重启、不清任务、不擦B槽。优先复用已有原始owner/Boot/RAM转储；截图中的null不是完整探针报告。

下一次经授权的设备只读诊断，先确认GR正常运行及CAT1真实启动；不使用会自动reset/power key的预检脚本。取得：

- 安装首次错误16word、quiet阶段/trace/拒绝记录、门控与采样年龄。历史没有记录则明确标注，当前门控不能充当失败时门控。
- A区与B区真实签名镜像范围的内容，独立核对摘要、尾部、目标版本和本地冻结包。不能从CAT1 G进度推断B区全量一致。

3. 首次错误为0且能确认预验证未进入：优先处理已复现的调度路径；历史阶段证据缺失时，需要新诊断版捕获，不能凭0单独定案。

## 4. 第二阶段：最小修复设计

### GR：请求识别、安全等待、签名失败分别处理

目标文件：Src/user/ota/yp001_ota.c，必要时yp001_ota_port.c。

- ACTIVATE预验证路径的识别只依据合法JSON、匹配owner/epoch/job/hash/target/version及允许阶段，不把safe(true)作为“是否为此请求”的条件。完整字段和重复键校验继续保留。
- 合法GR激活请求进入已有只读分步验证路径。安全条件不满足时等待，不落入没有校验收据的普通激活分支。前台持续服务，不持有写Flash租约。
- 校验执行、等安全窗、短租约握手分别计时。沿用已有120秒验证上限但不把整个安全等待误算成签名校验超时；本轮一次安全等待上限120秒，超出返回明确暂态原因并保留PREPARED，不无限保电等待。下一次在同任务安全条件恢复后有限重试。
- 真正A/B认证失败、owner变更或校验收据失效继续拒绝，不能拿等待规则绕过验证。提交前仍重查签名收据、owner/Boot/B区关联及实际安全条件。
- 记录一次性诊断：请求进入时的门控掩码/采样年龄，是否进入校验、具体stage、是否获得/失去收据。状态变化时输出，避免10秒重复刷屏。
- 本次不实施“OTA期间忽略运动/按键”等独立需求；不改充电参数、电源策略、Flash布局、签名或用户数据。

### CAT1：只对明确暂态、未提交的拒绝保留任务

目标文件：Air780EGH/ota_manager.lua，必要时ota_runtime.lua。

- 对明确安全等待原因先QUERY核对同一owner/epoch/hash，只有GR仍PREPARED才回到等待条件。保留候选、进度及试装资格，不通过transport_fault(...,true)把临时条件变化永久变成SPENT。
- 自动重试最多3次，间隔至少30秒，条件恢复且有新鲜GR安全回执才发；计数持久化，不因重推或重启清零。达到上限保留任务并报告等待/人工处理，不持续发令。
- INSTALL_PENDING、Boot已有安装意图、回包丢失或状态不明进入现有恢复核对；不得以PREPARED规则重复授予安装。
- activation_validation_failed保持不可盲重试，直到GR通过明确新分类或现场证据证明是暂态；不得把所有DENY统一转重试。新增原因仅为内部UART诊断，平台JSON字段保持原协议。

## 5. 针对性验证与交付

先把现有主机复现固定为回归，再覆盖：ACTIVATE到达时不稳定/采样过期/链路变化；条件恢复后执行真实校验路径；真实签名失败不被重试；收据失效、租约超时、owner更换、ACK丢失及重启后不重复安装。CAT1验证暂态不SPENT、同任务有限退避、跨重启计数保留和INSTALL_PENDING隔离。沿用已有成功证据，不重复无关基础测试。

主机模型只证明分支和时序处理，不证明硬件SHA/RSA或实板升级。随后按用户工作流：核对产物/过期编译单元与配置，用户在同一Keil主工程F7增量编译，保留Objects/.d，不Rebuild。Boot逻辑不变则复用既有Boot并核对配套指纹。重新冻结新包、MD5及接收端。

重要交付限制：修复写在新的GR候选里不会修复仍在执行的旧b16安装器。必须先根据当前owner/Boot证据确定维护路径，再由用户授权并手动完成所需GR有线维护；不得在未知安装事务下直接覆盖、复位或擦B。若旧GR无需维护即可安全完成当前事务，应先完成核对再安排下一轮修复验证。

实板只跑针对性一轮：预先计划一次安装前临时活动/链路扰动 → 明确等待而非终止 → 条件恢复 → GR确认 → CAT1升级确认 → 实际版本与otaResultMsg。真实SOS/通话仍优先，不能为了证明OTA完成而屏蔽。核对两端用户参数、居民信息及待报记录保留。若出现真镜像校验错误立即转对应分支，不叠加修补。

通过标准：同任务候选不被无故重下/清除，暂态不误报签名失败或永久SPENT；真坏包仍被阻止；完整双端串行完成，owner COMPLETE/success、Boot CONFIRMED、两端实际版本匹配且平台取得结果。
