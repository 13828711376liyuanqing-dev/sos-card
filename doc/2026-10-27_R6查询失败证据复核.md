- 固定字段标准紧凑 JSON 的主机参考长度 231 字节，远低于长度门；设备实际编码结果未知，不能完全排除编码失败。
- UART 故障锁存只阻止 OTA 控制文本，普通状态回复可通过；因此普通状态回复正常不排除锁存，但本次未保存实时锁存值。

## 新证据：后台查询与故障锁存链

- 部署版 `ota_runtime.lua` 的 `tick()` 在 GR `RECOVERY_HOLD` 期间仍调用 `manager:reconcile()`，任务存在时发送只读 QUERY。`ota_uart_window.lua` 控制查询未获匹配回应超过 2 秒可设置 `UART_REPLY_TIMEOUT` 锁存。
- 同时部署版 `ota_manager.lua` 的 `transport_fault(reason,hold)` 对既有 trial=SPENT 的单参数通知提前返回，保留旧原因。因此一个新 UART 故障可能被实时锁存在 UART 层，FOTA_STATUS 仍展示历史 `UART_QUIET_DENIED`。这一点是源码路径结论。
- `tools/ota/test_r6_hold_query_fault_chain.py` 使用交付版 CAT Lua 模块，主机上模拟后台 QUERY 发出、GR 不回复和 2 秒流逝，真实 UART 窗口发生超时锁存，管理器继续保留旧原因；随后 selector 5 返回 `INSTALL_RECOVERY_QUERY_FAILED` 并消耗票据。测试通过；GR 不回复是测试注入，不是本次现场已经证实的事实。
- Luatools 既有日志中，20:46 以后记录 257 次 QUERY，最后一次发出日志为 **20:50:49.267**；之后到 21:16 接续失败没有再记录 QUERY，但其他 UART 业务输出及 MQTT 状态仍连续记录。最后 QUERY 的模块运行计时 272.420 秒，21:16:21.360 失败时计时 1804.591 秒；与墙钟间隔约 1532.093 秒接近，支持同一次 CAT1 启动，不能单独证明具体锁存。

## 事务顺序分析

- 固件源码及之前的 GR 只读回读证据表明 `QUERY` 通过只读分支返回状态；项目 host 测试覆盖了它不写任务和不发静默租约。现行做法却先持久 ARMED，再发送 QUERY，因此即使只是只读查询排队失败也会消费此次安装机会。这个事务顺序与 GR 是否最终允许安装是两个独立问题。
- 可考虑先完成一次精确身份的只读查询，再在发送 ACTIVATE 前持久化单次使用状态，避免只读查询自身失败就消费安装票；但不能因此提前发送 ACTIVATE、抹去 SPENT 历史、自动创建新机会或放宽 GR 的提交/镜像验证。
- 当前 GR QUERY 回复没有为 QUERY 回显随机 challenge，现有匹配依赖 job/hash/target/epoch 和等待窗口。单凭这些字段不能证明响应不是同一任务的延迟旧帧；新顺序必须专门设计并测试新鲜性和排队时序，是否需要 GR 配套更改尚未决定。
- journal 写入的 Lua 路径无显式 `sys.wait()`；候选哈希有显式 `sys.wait(1)`。人为在 `disk.write` 内重入能复现检查后故障，但底包实际文件 API 是否让出 Lua 执行权没有文档或现场证据，不能把这个模拟当成本次确定根因。

## 后续应完成的工作

### 本轮新增：可复现的准入缺口

已定位部署源码中的一个确定性缺陷：selector 5 在持久化安装恢复机会前检查任务身份、历史、签名、完整候选和业务空闲，但没有检查 `_G.ota_uart_faulted()`。`uart_app.lua` 在 `window:blocked()` 时会拒绝 `OTA_CTL` 文本；因此如果故障锁存已存在，该路径仍可能先持久化 ARMED，随后 QUERY 入队失败并将本次票据置为 SPENT。

`tools/ota/test_r6_blocked_uart_admission.py` 在内存测试端口中显式模拟“UART 已锁存、QUERY 发送返回 false”，复现 `INSTALL_RECOVERY_QUERY_FAILED` 且安装票据由未创建变成 SPENT。测试通过意味着缺口被成功复现，不代表设备本次确实处于锁存，也不代表软件已修复。测试使用发送替身；部署版真实发送层的锁存拒绝由源码静态证据支持，尚需组合验证。

已进一步完成组合复现：`tools/ota/test_r6_real_uart_gate.py` 使用 Lua 5.3、实际交付集合的 `ota_manager.lua`、`ota_runtime.lua`、`ota_platform.lua` 和 `uart_app.lua`。在主机 UART 替身上注入一次部分写入，真实 UART 窗口进入故障锁存；后续真实平台发送路径返回失败，真实管理器将新票据置 SPENT 并返回与实板相同的 `INSTALL_RECOVERY_QUERY_FAILED`。命令退出码 0，复现通过；注入的部分写入只是实验造锁存的方法，不能反推实板发生过部分写入，也不能证明实板实际处于锁存。

随后对交付源码分别模拟四种条件：UART 窗口锁存、DFU 标志占用、64 条发送队列满、QUERY JSON 编码返回无效结果。四种条件均复现 `INSTALL_RECOVERY_QUERY_FAILED` 和安装票据 SPENT。测试中的业务空闲和文件校验是受控替身；对 DFU/队列条件是否可与实板当时的业务空闲同时成立未作实板证明。这个结果进一步说明仅凭当前错误码和线上的查询缺失无法区分四种原因，不能把某项写成实板确因。

这与本次实板的失败表象吻合，但现场锁存值缺失；因此只能将其列为**确定存在、必须修复的准入缺陷及本次候选原因**，不能写成实板首错已确因。安全修复需在消费前检查实际 UART/DFU/队列准入，并处理检查后状态变化的竞态；不能清除故障锁存、绕过 GR 授权或自动续发。查询失败的其他分支仍需记录和覆盖。

在不复用已消费机会的前提下，先审查能否通过既有合法接口获取当前锁存；若不能，明确记录本次即时值已不可得。然后设计最小可审查的发送拒绝来源与故障首错记录，覆盖 JSON、函数、DFU、窗口及队列路径，并用真实平台/串口适配器联合测试。只读诊断不能清锁存或自动重试，也不能将重启后的值误作本次证据。新恢复机会须在具备新的确定性依据及单独授权后才可执行。

已针对“预检时发送器已知不可用仍消费票据”完成主源码离线补丁及真实模块测试；另有人为重入测试发现检查后新故障仍可消耗票据，实际设备是否发生尚未证明。原生 USB 预览仅余 18 字节，未交付或烧录。详细范围及未闭合条件见 [R6查询准入缺陷离线修复](2026-10-27_R6查询准入缺陷离线修复.md)。
