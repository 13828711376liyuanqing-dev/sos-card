# 方案二：字形生成器（文字输入 + 描点生成）评估与实现方案

SAM | 2026-11-02 | 读者：项目负责人、GR/CAT1/后台开发、测试 | 配套：`2026-11-02_方案一_姓名字形平台推送整体落地方案.md`

## 0. 它是干什么的

给"姓名字形推送"链路提供**字形数据的来源和测试夹具**：

1. **文字输入**：输入"张秀华"，自动按指定字体、字号把每个字渲染成点阵。
2. **描点生成**：在 16×16 / 32×32 的格子里用鼠标逐点画（或在文字生成的结果上改点），用于生僻字、字体里没有的字、或修正渲染瑕疵。
3. **输出多种格式**：给平台的 `residentNameMsg` JSON、给 GR 做串口注入测试的 `BUS_EVT=` 行、给人看的预览图、给 C 代码的数组。
4. **自检**：和本工程现有字体（`font_cn_16/32`）里已有的字逐字节对比，证明生成格式正确。

它同时有两个身份：**平台后台的字形服务的原型**（同一份核心代码可以直接做成后台脚本/服务），和**测试人员的桌面工具**。

## 1. 可行性结论

**可行，难度低到中等；建议用 Python（Pillow + tkinter）一个文件起步。** 依据（本次已实测）：

| 项 | 实测结果 |
|---|---|
| 本机环境 | Python 3.12、Pillow 12.3 可用；`C:\Windows\Fonts\simhei.ttf` 存在；Node 可用（需要时可用 `lv_font_conv`）；`tkinter` 一键工具已在用 |
| 现有字体的存储格式 | `lv_customer_font_simhei_32.c`：SimHei、`--bpp 1 --no-compress`，`line_height=33, base_line=5`；"张"（U+5F20）字形 `box_w=29, box_h=29, ofs_x=2, ofs_y=-4, adv_w=512`，位图 116 字节 = **每行 4 字节（按字节补齐）× 29 行** |
| 用 Pillow 渲染"张" 32px | 阈值 128 二值化后包围盒 28×28，形状与本工程字形一致，**但框比字库的 29×29 小一圈** —— 说明字库是用 FreeType 渲染并带 1px 边距，Pillow 需要校准偏移才能做到逐位相同 |
| 本地字体覆盖 | 32px 字体共 185 个字符（含 ASCII），姓名里的常用姓/名用字大部分已有；"张""秀"（5F20/79C0）在内 |

> 实测还发现一个**纠正点**：字形位图是"每行按字节对齐"，不是连续位流。第一次我按连续位流读，结果是斜纹乱码；按行对齐才对。生成器和 GR 动态字体都必须按这个格式。

**风险（诚实）**：Pillow 渲染和 `lv_font_conv`（FreeType）在抗锯齿阈值、包围盒上有细小差异，所以"和现有字库逐字节一致"可能做不到 100%，只能做到"形状一致、差异在 1 px 内"。对**显示效果**这通常够用，但验收口径要提前定（见 §5）。想做到完全相同，改用 `lv_font_conv`（Node）或 `freetype-py` 做渲染后端。

## 2. 功能设计

### 2.1 文字输入模式

输入：姓名字符串（也可只输入若干生僻字）、字体文件（默认 `simhei.ttf`，可选其他 TTF/OTF）、字号（16/32，可多选）、二值化阈值（默认 128，滑块可调）、是否加粗/微调边距。

处理（每个字、每个字号）：
1. 用 Pillow 渲染灰度字形（按字号像素）。
2. 阈值二值化 → 求包围盒 → 裁成 `W×H`。
3. 按**基线**算 `ofs_x / ofs_y / adv_w`：以字库的 `line_height/base_line`（32px：33/5；16px 需读 `lv_customer_font_simhei_16.c`）为基准；`ofs_x` = 左边距，`ofs_y` = 字形底边到基线的距离（可为负，见"张" `-4`），`adv_w = 字号 × 16`（32px → 512）。**偏移量用"校准"解决**：自动选一个本地已有的字（如"张"）渲染，对比其字库值，算出整体偏移修正并保存，后续所有字套用同一修正。
4. 按"每行按字节补齐、高位在前"打包成字节串，算 CRC16。
5. 在界面里以 1:1 和放大 8 倍的两种方式预览，并**用同一份字形模拟电子纸显示**（200×200 黑白）。

### 2.2 描点模式

- 格子编辑器（16×16 / 32×32，也可选 40×40 以后扩展）：鼠标左键画黑点、右键擦除、按住拖动连续画；撤销/重做；清空；水平/垂直平移一格；反色。
- **从文字模式带入**：点"转到描点"，把当前渲染结果放进编辑器修改（例如修复某个细笔画断开）。
- 手工设置 `U`（码点）、`ofs_x/ofs_y/adv_w`（默认取文字模式的值，或"居中"一键计算）。
- 保存/载入：单个字形保存为 `.glyph.json`（含点阵位图的 0/1 矩阵，易读易改），也可从 PNG（黑白）导入。

### 2.3 输出

| 输出 | 内容 | 谁用 |
|---|---|---|
| `residentNameMsg.json` | 与方案一 §3.1 完全一致的 JSON（含 Name、Seq、Glyphs[]、CRC） | 平台/后台、MQTT 发布测试 |
| `bus_evt.txt` | `BUS_EVT={"op":"name_begin"…}` 一系列行（名称、各字形、`name_end`），每行 < 400 字节 | GR 串口注入（T3）、CAT1 测试 |
| `preview.png` | 每字每字号的放大预览 + 200×200 模拟屏 | 评审/人工检查 |
| `glyphs.c`（可选） | 与 `lv_font_fmt_txt_glyph_dsc_t` 对齐的数组，便于做本地 Flash 补字（以后若要做持久化） | GR 开发 |
| `report.md` | 本次生成的字、字号、与本地字库对比的差异、CRC | 测试留痕 |

### 2.4 自检（T0）

- "与本地字库对比"：对输入里**本地字体已有**的字，自动取出该字在 `lv_customer_font_simhei_16/32.c` 中的 `box_w/box_h/ofs_x/ofs_y/adv_w/bitmap`，与生成结果逐项对比，输出"完全一致 / 差 n 个像素 / 尺寸不同"。
- "查缺字"：对输入的每个字，标注**本地字体有/没有**（解析字体文件里的 `cmap`），一眼看出哪些字必须靠推送。
- 载入 GR 动态字体后的**回读校验**：把生成的数据再按 GR 的读取方式（行对齐、MSB 优先）解码成点阵，和原图比较，确认没有位序错误。

### 2.5 可选：直接发送

- "发到 GR"：通过 COM 口把 `bus_evt.txt` 逐行发出，等待回显 `name_ack`。依赖 GR 的测试 CLI 命令（`busline`）或 UART4 注入方式，见方案一 §6 的 T3。
- "发到平台测试主题"：用 MQTT 向设备下行主题发布 `residentNameMsg`（只在你提供主题、账号和确认之后才做，不会默认联网）。

## 4. 实现方案

- **语言/依赖**：Python 3.12，`Pillow`、`tkinter`（标准库）、可选 `pyserial`、`paho-mqtt`；不引入大依赖，和 `tools/` 下其他工具风格一致。
- **位置**：`D:\CODEX\sos-card\tools\glyph_maker\`，文件：
  - `glyphlib.py`：核心（渲染、二值化、基线计算、打包/解包、CRC16、字库解析、JSON/串口行生成）— **同一份代码可复用给平台后台**。
  - `glyph_maker.py`：界面。
  - `glyph_maker.bat`：双击启动，与 `ota_oneclick`、`tree_sync` 一致，中文菜单/颜色输出（命令行版：`python glyph_maker.py --name 张秀华 --sizes 16,32 --out <目录>`）。
  - `test_glyphlib.py`：核心的单元测试。
  - `使用说明.md`。
- **工作量估计**：核心 + 命令行 0.5~1 天；界面和描点编辑 1 天；自检和对比 0.5 天；联调和说明 0.5 天。共约 2~3 天（估计值，未排期）。
- **不做**：不改固件/CAT1 源码；不联网（除非你要求）；不碰 Git/SVN；不覆盖已有文件，所有输出写到新目录。

## 5. 验收标准（建议）

1. 对本地字体已有的 20 个常用字，生成结果与字库对比：**尺寸和偏移完全一致，像素差 ≤ 阈值（建议先定 ≤ 2% 像素）**；不达标则换 `lv_font_conv`/`freetype-py` 渲染后端。
2. "张秀华"三字在 16px 和 32px 下预览清晰、笔画不断。
3. 一个本地没有的字（如"珺"）能出字形，并能在**模拟屏**和**GR 实屏**（T3）显示正确。
4. 输出的 JSON 通过方案一 §4.1 的 CAT1 校验规则（长度、CRC、范围）；输出的 `BUS_EVT` 行每行 < 400 字节、JSON 平铺、无重复键。
5. 描点模式能完整画出一个生僻字并导出，格式与文字模式输出无区别。
6. 核心库有单元测试：打包/解包互逆、CRC、字节对齐、边界尺寸（W=1、W=32、H=33）。

## 6. 风险与待确认

| 项 | 说明 |
|---|---|
| 与现字库 1:1 | 见 §1 风险；先做校准和逐字节对比，决定是否换渲染后端 |
| 字体授权 | SimHei 用于生成并分发字形的授权需确认；可换客户认可的字体，生成器支持任意 TTF |
| 本地字体解析 | 需要解析 `lv_customer_font_simhei_16/32.c`（正则可行，本次已验证可取"张"）；16px 的 `line_height/base_line` 还没读取，实现时补 |
| 位序/对齐 | 已确认行对齐 + MSB 优先（以 32px "张"为证）；16px 同样要核对 |
| GR 侧接收 | 生成器只是数据来源；GR 动态字体和 `BUS_EVT` 解析是方案一的工作，生成器无法替代它们的验证 |
| 注入通道 | 调试串口 COM26 现在不能直接喂 `BUS_EVT`，需要加测试 CLI 命令或接 UART4（方案一 T3） |
| 未做 | 本方案没有写任何工具代码；上面 §1 的实测只是在 Python 里读了现有字库并用 Pillow 渲染"张" |

## 7. 建议下一步

1. 确认生成器放在 `tools\glyph_maker\`，先做 `glyphlib.py` + 命令行，并完成 T0 自检（对比现有字库）。
2. T0 通过后做界面（文字 + 描点），再加 `BUS_EVT`/JSON 输出。
3. 同时安排方案一的 GR 最小原型（动态字体 + 一条测试 CLI），做 T3 实屏验证。

> 先做 1 的好处：它最快暴露"字形格式/偏移是否与屏上字体一致"这个最大的不确定项，决定后续渲染后端选型。
