# OTA 新旧后台对比：Range 分段下载带来了什么

SAM | 2026-11-03 | 读者：项目负责人、后台同事 | 依据：2026-11-03 整机 OTA 1.5.8 → 1.5.9 实板记录（`doc/2026-11-03_整机OTA_1.5.8到1.5.9_新后台实板记录.md`）、2026-10-24 旧后台实测（`doc/2026-10-24_客户后台新地址下载与Range不兼容定位.md`）

## 一、结论

后台这次的变化，实测是**支持了 HTTP Range 分段下载**（加上强 ETag、固定长度）。

| 方面 | 有没有改善 |
|---|---|
| 断线续传 | **有**：从已下的位置接着取，不用从头再下 |
| 防止中途换包 | **有**：每次请求都校验 ETag |
| 流量 | **有**：少约四分之一 |
| CAT1 内存 | **有**：不用再缓存 zip 元数据 |
| CAT1 文件区空间 | **没有**：GR 组件仍要整份暂存。这次空间够，是精简字库让 GR 小了 55 KB |
| 下载时间 | **略慢**：分段请求次数多 |
| 下一步"边下边转" | **最大的价值**：消除了它原来最大的缺点（断线只能从头重读） |

## 二、新旧后台实测对比

| 项 | 旧后台（tkaiot 平台存储接口） | 新后台（nginx 1.22.1） |
|---|---|---|
| 请求 `Range: bytes=64-127` | 仍返回 200，内容是**文件开头**，不是请求的那一段 | 返回 **206**，`Content-Range` 精确，内容逐字节一致 |
| 传输方式 | `Transfer-Encoding: chunked` | `Content-Length`（固定长度） |
| ETag | **没有** | 强 ETag，两次请求一致 |
| 跳转 | 无 | 无 |
| 空闲断开 | 实测限速 7 分钟不断 | `Keep-Alive: timeout=4`（空闲 4 秒断） |
| 设备走的下载路径 | 兜底的**顺序读**（`ota_seq_zip.lua`） | 原本设计的 **Range 路径**（`ota_bundle.lua` + `ota_http_range.lua`） |
| 电脑上用设备 Lua 代码校验 | `check_sequential_tcp.py` 通过 | `check_range_tcp.py`（新）通过：`transport_mode=HTTP_RANGE`，整包 MD5、签名、两个组件摘要都对，`restart_from_zero=false` |

## 三、两种下载方式怎么工作

### 旧后台：顺序读（兜底方式）

| 步骤 | 做法 |
|---|---|
| 第 1 次 GET | 从头读完整个 zip，算 MD5、验签名；固件内容读完就丢，只在内存里留最多 35 KB 元数据 |
| 第 2 次 GET | 再从头读，丢掉前面的部分，读到 GR 组件时存进 CAT1 文件区 |
| 第 3 次 GET | 再从头读，读到 CAT1 组件时存进文件区 |
| 断线 | 只能重新 GET、**从头读** |

### 新后台：Range 读（设计的正式方式）

| 步骤 | 做法 |
|---|---|
| 整包校验 | 按段读完整个 zip 算 MD5、验签名 |
| GR 组件 | 只按位置取 GR 组件那一段，存进 CAT1 文件区，并定期记下进度 |
| CAT1 组件 | 只取 CAT1 组件那一段 |
| 断线 / CAT1 重启 | 按记下的进度，用 Range **接着取**；带 ETag 校验，确保还是同一个文件 |

## 四、逐项分析

### 1. 断线续传（改善）

- **旧**：GR 组件 37 万多字节，下到一半断线，就要从 zip 开头重新读起。越靠后断，浪费越多。
- **新**：从断点接着取。CAT1 在下载过程中重启、4G 掉线，已下的部分不用重下。
- 对现场意义大：信号差的地方，旧方式可能一直下不完。

### 2. 防止中途换包（改善）

- **旧**：没有 ETag，只能靠最后的整包 MD5 和组件摘要兜底。中途后台文件被换掉，要下完才发现。
- **新**：每次分段请求都核对 ETag，文件一变马上就能发现，不会把两个版本的数据拼在一起。

### 3. 流量（改善约 25%）

| 方式 | 一轮读多少（按这次 575746 字节的包估算） |
|---|---|
| 旧：3 次 GET | 整包约 576 KB + 读到 GR 结尾约 390 KB + 读到 CAT1 结尾约 576 KB ≈ **1.5 MB** |
| 新：整包校验 + 两个组件 | 实测 1176751 字节 ≈ **1.18 MB** |

加上断线时旧方式还要从头重读，实际差距会更大。

### 4. CAT1 内存（改善）

顺序读要在内存里缓存最多 35 KB 的 zip 元数据。Range 模式按位置直接读，不需要这份缓存（实测 `metadata_bytes` 为空）。

### 5. CAT1 文件区空间（没有改善）

- 两种方式都要把 GR 组件**整份存进 CAT1 文件区**，再经串口转给 GR，要求一样：镜像 + 16384。
- 这次能升级，是因为**精简字库**：GR 签名镜像从 429288 降到 372968，要求从 445672 降到 389352。可用 425984，余 36.6 KB。

### 6. 下载时间（略慢）

| 轮次 | GR 镜像 | GR 段用时 | 下载方式 |
|---|---|---|---|
| 11-02（旧后台） | 约 424 KB | 约 10 分钟 | 顺序读 |
| 11-03（新后台） | 372968 B | 约 13 分钟 | Range |

- 原因：Range 模式每段取 4 KB，每段都单独发一次请求；电脑上校验时，一轮就有约 90 个请求。新后台空闲 4 秒就断开连接，几乎每段都要重新建连接。
- 可以优化：把每段加大到 16 KB 左右，请求次数会少到四分之一。这段代码在 OTA 受保护文件里，要单独评估、实板验证。

## 五、对下一步"边下边转"的意义（最大的价值）

原来的评估（`doc/2026-11-03_OTA空间_分片直传与分文件两方案评估.md`）里，"边下边转"最大的缺点是：

> 旧后台不支持 Range，断线后要重新 GET、从头读、丢掉 GR 已收部分，多费流量；越靠后断线越费。

新后台支持 Range 以后：

| 项 | 旧后台下的边下边转 | 新后台下的边下边转 |
|---|---|---|
| 断线 | 从头重读，跳过已收部分 | 按 GR 已确认的位置**精确续传** |
| 流量 | 断一次多读一遍 | 只重取当前这一段 |
| 文件一致性 | 只靠最后的组件摘要 | 每段都有 ETag 校验 |
| 方案评价 | 可行，但信号差时不稳 | **稳定可行** |

做完"边下边转"以后：

| 项 | 现在 | 边下边转之后 |
|---|---|---|
| GR 阶段 CAT1 文件区需要 | 约 389 KB（随 GR 变大） | 约 20 KB（固定） |
| GR 能不能继续变大 | 只剩约 36 KB 余量 | 只受 GR 自己的槽位限制（441464） |

## 六、建议

1. **继续用新后台**（或者让平台存储也支持 Range、ETag、`Content-Length`），旧接口只作兜底。设备代码两种都支持，不用改。
2. **"边下边转"单独立项**，按 Range 方案做（原方案 A）。现在余量约 36 KB，不急，可以做好完整的实板验证再上。
3. **评估加大每段的大小**（4 KB → 16 KB），缩短 OTA 时间。要改 OTA 受保护文件，和第 2 条一起做。
4. **问后台**：新地址是长期的正式地址，还是测试地址？是否所有升级包都会走这个服务？`Keep-Alive` 4 秒能否调长（减少重新建连接）？

## 七、依据和边界

- 新后台的特性是电脑上实测（curl）加上用设备同一套 Lua 代码对真实服务器的校验结果；4G 下的实际表现来自这次实板 OTA。
- 旧后台的流量是按读取方式估算的；新后台的流量是电脑校验工具的实测值，设备上实际流量没有单独统计。
- "每段加大到 16 KB 能缩短时间"是推断，没有实测。
