# R6三项逐查结果与ADC关中断修复

SAM | 2026-10-26 +08:00 | 按用户批准的三条线持续排查。复用原R6现场；本轮无烧录、无新票据、无OTA执行。源码修复不等于实板验收。

## 一、结果先说清

本轮找到了此前遗漏的、具体到HAL/ROM地址的接收阻塞路径：**电池ADC使用16kHz时钟，每次同步转换开始时，HAL在PRIMASK关中断期间调用ROM回调，回调等待ADC FIFO至少2个条目；这相当于4次转换，正常空FIFO等待约3.75ms，超过460800串口128B FIFO从空到满约2.78ms的时间。**

这是一条确定违反UART接收时间预算、足以造成同类FIFO溢出的软件路径，已经完成源码修正。它不是由“某函数看起来很慢”推测出来的：本轮核对了部署AXF、实板ADC参数、实板ROM回调指针及其代码、官方ADC转换时序。

**不能越过的证据边界**：原R6首错没有保存造成延迟的执行历史，因此不能独立证明这条ADC路径是该次故障的唯一触发者；新固件实际关中断时长、ADC读数质量及持续UART接收尚未实板验收。本轮不会把静态推导写成“整机OTA已修好”。

另两项已查实并修复：

1. 恢复hello没有前置换行，被GR的失链隔离态整条丢弃；原波形对应消息顺序已用实际C解析器回放复现。
2. 外层quiet安全门拒绝绕过内层拒绝快照；已增加独立RAM首拒记录，保存同一次判定的条件，不再拿全零的内层快照解释外层失败。

## 二、第一项：GR接收阻塞路径

### 2.1 输入与现场身份

- 实际部署AXF：`firmware_releases/gr_uart_recovery_20261025/baseline/Objects/YP001_GR5526.axf`。
- SHA256：`706dd6d41721ce36311c27381f5f26c6b1e11e84ad72483e84c75267a6babd32`，与R6冻结记录一致。
- 本轮串口只读返回：GR产品版本1.0.2、build3、USB bench=1；未发电源切换/PWRKEY/OTA命令。
- 原首错及恢复记录80B仍逐字一致，未被新实验覆盖。
- ADC参数实读：`s_adc=0x2000BBEC`，init偏移0x20，clock偏移0x34，值1；SDK定义1对应16kHz。
- `0x2000037C`实读回调指针为`0x00011A89`，即Thumb入口`0x00011A88`。

### 2.2 实际调用链

```text
battery_observation_poll（约每秒一次，独立于屏幕刷新）
  -> yp001_battery_read
     -> app_adc_init / hal_adc_init_ext（初始化后关闭转换时钟）
     -> app_adc_conversion_sync(raw,36,...)
        -> hal_adc_poll_for_conversion
           -> 先清空ADC FIFO
           -> hal_adc_try_set_clock(ADC_CLK_16K)
              -> PRIMASK=1
              -> 写时钟请求
              -> 调用实板ROM回调0x00011A89
                 -> 轮询FIFO条目数，直到至少2个条目
              -> 恢复PRIMASK
           -> 获取采样数据
```

可复核地址：

| 地址 | 实际代码作用 |
|---|---|
| 0x0023D44E～0x0023D458 | 清空ADC FIFO |
| 0x0023D460 | 调用hal_adc_try_set_clock |
| 0x0023D6C6 | 设置PRIMASK，屏蔽可屏蔽中断 |
| 0x0023D6E0 | BLX调用0x2000037C所指回调 |
| 0x00011B04～0x00011B0E | 读取FIFO条目数，与2比较；不足时继续等待 |
| 0x00011AFE | 等待循环调用delay_us(1) |
| 0x0023D700 | 回调返回后才恢复PRIMASK |

此前只看应用层的短临界区，遗漏了HAL内部调用的ROM等待；这也是首错记录只能看到FIFO溢出、无法从应用代码直接判断是谁阻塞的原因之一。

### 2.3 官方时序与预算

本轮实际读取[官方SADC章节](https://docs.goodix.com/zh/online/detail/datasheet_bl_b/V1.3/be347744eac54db59b259201c6a7d632)，原文明确：

> It takes 2 clocks for the SADC to sample and hold data, and then 13 clocks to convert ... totaling 15 clocks to generate one code.

同章说明一个32位FIFO条目保存2个样本。因此：

| 项目 | 数值 | 性质 |
|---|---:|---|
| 等待2个ADC条目 | 4个转换结果 | ROM条件+官方FIFO格式 |
| 16kHz下正常空FIFO转换部分 | 4×15÷16000≈3750µs | 时序推导，不是实测WCET |
| UART半满后剩余64B | 64×10÷460800≈1388.89µs | 硬件接收预算 |
| UART从空到满128B | 128×10÷460800≈2777.78µs | 硬件接收预算 |
| 1MHz下相同转换部分 | 4×15÷1000000≈60µs | 修复后的时序推导 |

等待值还受转换相位、启动开销及异常路径影响。上述计算用于证明旧设计超预算和新配置的正常转换余量，不能替代实际最坏时延测量。

这也解释了为什么前面若干块正常、某一块突然丢失：周期ADC操作与11.7ms左右的540B串口帧可能重叠；没有硬件流控，软件ring再大也接不住CPU长时间无法服务时的硬件FIFO溢出。

### 2.4 已实施的单点修正

`ble_app_uart_c/Src/user/yp001_battery.c`：ADC时钟由16kHz改为官方支持的1MHz，选择快速档中最低频率。保留：

- R42/R13分压及GPIO开关、50ms建立时间；
- 36个原始样本、丢弃前4个、32点标定换算及去极值平均；
- eFuse标定、原始值上下轨和电压范围检查；
- 电量规则、70%阈值和既定USB测试策略。

没有修改SDK私有ROM回调、UART优先级、UART波特率或Flash布局。

官方同时指出采样电容2pF。以本板100k/100k分压的50k等效阻抗估算，采样RC约0.1µs；1MHz下2个采样时钟约2µs，即约20RC，理想建立误差低于13位分辨率。原外部滤波电容和50ms建立时间仍保留。这支持选择1MHz，但输入噪声、实际ADC读数和平均时间缩短的影响仍需实板对照，不宣称已测通过。

### 2.5 已排除与仍不能排除

- 同次运行实读CPLL复位计数为0、无效IRQ计数1；结合实际分支计数写入位置，可以排除该次运行已执行CPLL复位分支这一解释。
- ADC FIFO读卡死计数0；不能由此排除正常但过长的ADC切钟等待。
- APP_LOG_LOCK阈值65本身不屏蔽优先级63的UART4，继续保留此前正确结论。
- 未证明每一个同级ISR、SDK内部Flash/时钟异常分支都满足UART最坏时延；不以本次修复宣布整个系统已无其他问题。

## 三、第二项：外层拒绝与恢复hello丢失

### 3.1 原波形中的恢复序列

原始D0数据在109.133639s发出恢复hello，前面紧邻的是上一DATA的二进制结尾，没有CRLF边界。随后依次为alarm_state、network=mqtt、call=idle、time、signal。109.397123s才重发offset1536的数据。

GR发生RX loss时，`yp001_ota_mux_lost()`将解析器置mode3。mode3丢弃到第一个换行；因此第一条hello整条丢弃，而后续状态行可继续解析。只有合法hello会设置`transport_ready=true`，单独收到network=mqtt不能恢复它。

本轮使用原波形消息顺序、实际`yp001_ota_wire.c`和`yp001_business.c`回放，设备身份已替换为测试值：

```text
DEPLOYED_CAPTURE hello=0 transport=0 mqtt=1 call_idle=1 peer_stable=0
BOUNDARY_CONTROL hello=1 transport=1 mqtt=1 call_idle=1 peer_stable=1
```

这是确定的软件恢复缺陷，能解释为何恢复消息已在线路上出现却仍被peer门拒绝。回放以实际失链路径已进入隔离态为前提；由于原外层快照缺失，不能把它冒充token9当时所有安全门值的实读，也不能排除同一时刻还有其他拒绝项。

### 3.2 已实施修正

`Air780EGH/business_runtime.lua`：仅hello在同一个发送队列成员中增加前置CRLF。边界与hello一起保留/重发，不分成两个可能被队列压力拆开的消息；普通业务事件格式不变。

实际CAT UART writer联测确认：新增边界不越过已授予的Flash静默窗，释放后才发送。没有直接解除GR隔离、没有允许损坏二进制中的文本执行。

### 3.3 外层首拒记录

`yp001_ota.c`及`yp001_ota_port.h`新增独立40B RAM记录`yp001_ota_quiet_denial`：

- token、kind、owner epoch/phase；
- unknown/alarm/call/activity/peer拒绝位图；
- 同一次读取的门状态、电量和观察时间；
- 首条内容保留，后续只累计次数；sequence最后发布。

外层通过与否使用同一份门快照；没有“先判定，再重读另一次状态”冒充现场。无Flash写入、无清任务、无新增票据接口。原116B内层快照保持不变。

`safe(false)`依旧不检查提交阶段的电池/充电门；提交阶段检查保持原规则。测试覆盖外层拒绝不进入RX/Flash、首次peer拒绝不被后续报警覆盖，以及传输阶段不意外增加提交条件。

## 四、第三项：Flash与DATA时序

本轮按原始字节时间戳逐段统计，不再仅凭DWT的stage2判断。

| 项目 | 原波形结果 |
|---|---|
| token8 quiet ACK发送完成 | 106.645187s |
| token8 RELEASE开始 | 106.783880s |
| ACK结束到RELEASE开始之间CAT字节数 | 0 |
| token8 RELEASE发送完成 | 106.784833s |
| 第四块DATA开始 | 107.077789s |
| RELEASE完成到第四块开始 | 约292.96ms |

因此可排除“这一个受测token8静默窗内CAT继续发送第四块”的解释。它不能排除所有SDK内部未受测Flash动作。

另一个必须纠正的名称：`g_ota_window_trace`计量的是整个事务处理，不是纯Flash耗时。接收端先累计4KB才写B槽；前三个512B DATA只在RAM累计。token8的138ms不能直接当作138ms的B槽写Flash。该路径还会刷新安全观测，包括ADC采样。

“错误回调看到stage2”本身仍不能证明错误产生时刻；本轮结论依靠完整线上静默区间，而非重复使用这个不足的排除依据。
