## 结论与证据边界

现场由 GR 下载/安装推进到 Boot TRIAL，但 CAT1 保持 RECOVERY_HOLD / ACTIVATION_RECHECK_FAILED / SPENT，尚无双端成功证据。用户另提供重启后 onlineMsg Version=1.5.29 的截图；该字段不能单独替代 GR、CAT1 分别读版本与 Boot CONFIRMED。

分析输入为 D:/123/YP01，日志为 D:/123/logs2/ota_monitor_20261110_193756_981_e18ccc。提供源码不等于已证明设备实际运行的 LuaDB 与源码逐字节一致。

## 已定位的代码缺陷

1. Air780EGH/uart_app.lua 的 uart_recv_cb 经 receive_text、dispatch_frame，在 UART 接收回调中直接调用 OTA_GR handler。
2. ota_runtime.lua 的 handler 同步调用 on_gr_line，再调用 manager:on_gr。
3. ota_manager.lua 收到 WAIT_ACTIVATE 下的 GRANT / INSTALL_PENDING，依次执行 safe、validate、verify_candidate；任何一项失败统一记录 ACTIVATION_RECHECK_FAILED，并将 RUNNING 票据消耗为 SPENT。
4. ota_runtime.lua 的 verify_candidate 调用 downloader:verify；ota_candidates.lua:112 的 verify_file 每读取 4096 字节执行 sys.wait(1)（第120行）。UART 回调不是 sys.taskInit 任务，此等待不能在该上下文中执行。
5. ota_download.lua 使用 pcall 包装文件校验，异常变成校验失败；上层再折叠为 ACTIVATION_RECHECK_FAILED，现场没有保留原始异常。

使用提供副本的真实 ota_candidates 模块、模拟文件/哈希接口，在 Lua 5.4 主线程以 coroutine.yield 模拟 sys.wait，实际返回：false, attempt to yield from outside a coroutine。此项证明代码上下文缺陷；不是实际 LuatOS 错误日志，不足以排除现场更早的 safe/validate 失败。

## 为什么 GR 版本会变、CAT1 却停止

GR 的 yp001_ota_port_install_commit 成功后已经激活 Boot，并安排至少250ms后的复位；随后才向 CAT1 发送 GRANT。CAT1 在收到 GRANT 后的本地复核失败，并不能撤销 GR 已提交的 Boot 安装。因此 GR 进入新版本 TRIAL 与 CAT1 暂停可以同时发生。

19:45:13 的 boot_commit_failed 是更早的提交失败。CAT1 manager 对 INSTALL_PENDING / boot_commit_failed 有一次受控重发 ACTIVATE 路径，后续 Boot TRIAL 支持安装后来实际推进。首次提交失败具体 stage 1–7 未记录到这批日志；g_ota_install_first_error 仅在 RAM 保存，重启后不能据当前值还原首错。不能将其直接归因于供电、运动或 Flash 损坏。

HEALTH_IDENTITY 另有误导路径：runtime 在 GR 任务的相关阶段也调用仅接受 CAT1 目标的 health checker，返回该错误。它不能单独证明现场 job/hash/epoch 不匹配，更不能代替 ACTIVATION_RECHECK_FAILED 的首错。

## 建议修复范围与待验

- UART 回调只接收/排队；可等待的校验放到单一串行 OTA 任务，保留任务身份、阶段、租约时效及重复应答门禁，不能简单删除校验或并行起多个任务。
- 复核失败保留 safe/validate/verify_candidate 的准确失败项和异常，不只打印总错误。
- CAT1 专用健康检查仅在 CAT1 阶段调用；GR 健康结果仍由 GR 的 Boot/运行身份/120秒观察给出。
- 首次 Boot 提交失败需补充可观测诊断，未有证据前不改安全门。
- OTA与字库影响：涉及 UART 回调、调度和文件校验；后续修改必须验证两端串行 OTA、重复/过期应答、字库双向并发让出与恢复、用户数据保持。当前仅分析和离线缺陷复现，均未实板验收。

现有 SPENT 事务不得通过清 B、复活票据或重复推送恢复；修复代码与恢复现场是两项独立工作，须绑定实际接收端/包及当前 Boot/owner 状态。
