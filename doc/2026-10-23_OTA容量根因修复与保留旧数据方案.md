# OTA 容量根因修复与保留旧数据方案

SAM | 2026-10-23 +08:00

## 本轮解决的问题

此前只逐项接收帧、精简帮助文字，没有先核对最终应用的容量组成，导致每加一点代码就越界。此次从真实链接 Map 找到容量根因：LVGL 配置启用了产品未使用的控件，主题中的类引用把日历、图表、键盘、色轮、菜单等实现保留在固件中。

只修改主/交付 `Src/external/lvgl_8.3.1/lv_conf.h` 的 29 个未使用控件开关；保留所有控件源文件。实际产品只创建基础对象、标签、图片、二维码；保留二维码所需 CANVAS、IMG、LABEL，以及现有主题、布局引擎、字体、页面和图片。GUI Guider 的键盘辅助引用已经位于 LV_USE_KEYBOARD 条件编译内，产品未创建键盘。

没有改 SDK、引脚、编译优化、链接脚本、下载配置、签名长度、用户数据区或版本号。

| 实际指标 | 修改前 | 修改后 |
|---|---:|---:|
| 应用 HEX 地址跨度 | 478560 | 408864 |
| 加 904 字节签名 | 479464 | 409768 |
| 原定 479232 字节槽余量 | 超出 232 | 剩余 69464 |
| 应用减少 | — | **69696 字节** |

主、交付两份 Keil 6 均 0 错误、0 警告，ReleaseCli 对两份新 HEX 的容量检查均通过。没有签发或上传新的 OTA 包。

## 界面没有靠删除功能缩小

- 38 个 GUI 页面、字体、资源及业务绑定文件的 SHA256 全部保持不变。
- 使用实际 LVGL 和实际产品页面运行原 `tools/test_guider_ui.py`；六页、240 次切换、无堆泄漏、刷新失败重试通过。
- 用保存的修改前 lv_conf.h 单独编译另一套主机测试，比较两套渲染结果：**六张 PBM 图逐字节完全相同**。
- 保留二维码数据变化检查、报警/来电优先页及原有页面测试。
- 以上是主机渲染证据，尚不是新配置在实物墨水屏上的验收。本轮未烧写。

## 旧 B 数据不必靠擦除来解决

现有旧候选 B 从 0x00277000 开始，该区域有未确认内容。用户没有最早 HEX，不能继续等待追溯成功，也不能将未知内容认定为废代码后擦除。

应用缩小后，新增一个**尚未部署的替代候选布局**：

| 区域 | 起点 | 结束（不含） | 说明 |
|---|---|---|---|
| SCA | 0x00200000 | 0x00202000 | 保持原地址 |
| A | 0x00202000 | 0x0026E000 | 442368 字节；执行入口不变 |
| 原内容保留区 | 0x0026E000 | 0x00280000 | 73728 字节，OTA 不可写；包含原未知 B 内容 |
| B | 0x00280000 | 0x002EC000 | 442368 字节 |
| Boot | 0x002EC000 | 0x002F6000 | 40960 字节，原候选地址不变 |
| scratch/journal/coordinator | 0x002F6000 | 0x002FB000 | 原候选地址不变 |
| 未分配 | 0x002FB000 | 0x002FE000 | 保留 |
| NVDS | 0x002FE000 | 0x00300000 | 原地址及 8192 字节不变 |

文件：`tools/ota/boot/layout_preserve_gap_candidate.json`。`approved=false`；不是已部署布局，不替换原候选，也没有修改现有签名合同或打包器常量。

新的 A/B 均能容纳当前 408864 字节应用和 904 字节签名，剩余 **32600 字节**。这为剩余接收/校验/安装接入提供容量，但最终完整镜像仍必须再次测量，不能先宣称全部代码必定容纳。

对已有 1 MiB 双读一致备份进行逐字节检查：候选 B、Boot、scratch/journal/coordinator 区均全 FF；原内容保留区有 67266 个非 FF 字节，全部保留。备份 SHA256：`883d8fcd7c1817f581e8a9ae9e5b2c27479b353cc2b779de7d55853b83b0cbf4`。

**这是历史备份证据。部署前必须重读实机，不能把历史空白直接当成当前擦写授权。** 旧大应用不能被当作新小槽的回退基线：布局检查已增加专门拒绝测试。需要先构建、验证紧凑版可信基线，再部署对应 Boot；不能直接把已经生成的旧签名包搬到新布局。

## 接下来完成真正升级所需的工作

1. 统一采用的布局到 Boot、应用接收器、签名头和离线打包器，并核对可写范围始终排除保留区和 NVDS。
2. 接收计数回调替换为受授权的镜像接收：会话/序号、ACK、受限 B 写入、持久偏移、完整签名与型号/版本校验。现阶段接收计数不代表传输完成。
3. 接通 Boot 真实入口、安全提交与试运行/回退；核对首次基线部署及 SCA 处理，不覆盖用户信息。
4. 接通 CAT1 默认生产运行实例与自身升级确认；两端仍严格串行。
5. 冻结同一批基线与 1.5.0 目标固件，完成容量/签名/配置保持检查后，再提供唯一上传 ZIP 和明确下载步骤。

本轮没有声称完整 OTA 成功，也没有让用户再次烧只有诊断功能的镜像。需要部署时，应提供同一批可核对的 Boot、应用、CAT1 和备份恢复说明，避免继续反复烧同版中间产物。
