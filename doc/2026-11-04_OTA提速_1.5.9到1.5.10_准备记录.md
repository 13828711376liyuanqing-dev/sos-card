## 一、结论

1. **昨晚的包不能直接用在这块板上**：包是 1.5.8 → 1.5.9，板子已经是 1.5.9，发令会被拒（REFUSED）。按你的选择，这轮做 **1.5.9 → 1.5.10 / build 14** 新包，旧包作废。

## 二、改了什么（只改下载节奏）

| # | 改法 | 文件 | 说明 |
|---|---|---|---|
| A | 每段 4 KB → **16 KB**（组件下载 + 整包 MD5 预检） | `ota_runtime.lua`、`ota_bundle.lua`、`ota_device_options.lua` | 请求次数降到 1/4 |
| B | **一次 tick 连续下多段**，3 秒预算 | `ota_runtime.lua` | 每段之后都检查业务是否空闲，忙就立刻停（报警、通话照样优先）；时钟读不到就退回每 tick 一段 |
| C | 下载进度 **每 16 KB 存一次**（原来每 4 KB） | 随 A 生效 | 方案里写的是 32 KB，但管理器有"两次进度最多相差 16 KB"的安全检查（主机测试专门测这条），不放宽；Flash 写入已减到 1/4 |
| 信标 | 每 10 秒的 `[OTA] B …` 末尾加 `P <进度>` | `update.lua`、`ota_runtime.lua` | `V已校验/总`（整包 MD5）、`D已下/总`（组件下载）、`G已发/总`（串口转 GR）。这样能分清下载和串口转发各占多少时间 |

- **提速参数只在设备配置里打开**（`ota_device_options.lua`：`chunk_size=16384, scan_bytes=16384, burst_ms=3000`）。不传这组参数时，代码行为和 1.5.9 逐字节相同，所以原有的主机测试照原样有效。
- **一行没改的**：整包 MD5、签名、组件 SHA256、GR 验签、Boot 试运行与回滚、健康检查、双方确认、断点续传规则（`ota_manager.lua`、`ota_download.lua` 未改）。
- 流式（顺序读）后台同样受益：B 让同一条流连续读，不再"读一段停一秒"。
- 版本：CAT1 `main.lua`、GR `yp001_fw_version.h` 改为 1.5.10 / 14。GR 代码没有其它改动。
- 改前备份：`D:\CODEX\_archive\before_ota_speedup_20261104_0957\`（CAT1 全部 .lua）。

## 四、后台地址检查改进

新工具 `tools/ota/check_url.py`，一条命令做完昨天手工分几步做的事：

```
python tools/ota/check_url.py logs/<轮>/url.txt --package <上传的zip>
```

下载核对 MD5（和 URL 里的 `md5=` 以及本地包），探测 Range / ETag / 传输方式 / 跳转 / 空闲断开，**自动判断是 Range 后台还是流式后台**，再选对应的设备 Lua 校验（`check_range_tcp.py` 或 `check_sequential_tcp.py`）。报告写进 `report.json`，`PASSED=true` 才往下走。已在昨天的地址上试跑通过（识别为 HTTP_RANGE，设备校验全部通过，16 秒）。

你说新后台是流式下载：拿到地址后工具会自动走顺序读校验。设备侧顺序读在 10-24 起就有主机测试，但**流式后台 + 新节奏还没在实板上跑过**，这轮是第一次。

## 五点八、11:49 实板发令失败与修复（12:01 重新打包，90a8cb20 作废）

**经过**：预检通过（IDLE、OUTBOX=0、used=25、可用 421888）。11:49 发令，`LOG_CLEARED 1763`，`WAIT_GR` → GR 授权（owner gen 103 `DOWNLOADING GR5526`）→ 整包 MD5 预检通过 → 11:50:57 第一段组件下载 `PAUSED SPENT write_readback_failed`，试运行票作废。GR 没收到任何数据，板子仍是 1.5.9，没有任何安装动作。

**原因（我的错）**：设备配置把组件下载每段设成 16 KB，但真实的候选文件接口 `ota_candidates.lua` 单次读写上限是 4096 B，16 KB 一写就被拒，报成写后读回失败（非网络类错误 → 直接作废票）。主机测试用的是夹具文件接口，没覆盖真实接口。

**修复**：

| 改动 | 文件 |
|---|---|
| 单次读写上限 `io_limit=16384`，底层文件系统仍按实板验证过的 4 KB 一块分次读写 | `ota_candidates.lua` |
| 下载段大小永远不超过文件接口的上限（`io_limit`，没有就用它自己的 `chunk_size`） | `ota_runtime.lua` |
| 信标 `G` 进度只在 GR 真正开始收数据后显示（之前一开始就显示 `G0`） | `ota_runtime.lua` |
| 台架命令 `cat_at OTA_GR_CANCEL_EMPTY`：CAT1 为 IDLE 时问 GR 当前任务；若 GR 报 `GR5526 DOWNLOADING`，原样回传其身份发 `CANCEL_EMPTY`。是否为空由 GR 自己核实（0 进度、B 槽全 FF、无 Boot 动作），否则拒绝 | `update.lua` |
| 接收端带一次性清理块（`--clean-ota-log`，标记 `yp001_clean_11041201`）：首次开机清 CAT1 OTA 记录和候选文件 | 一键工具 |

为什么要取消：GR 对"另一个任务"的新请求，在还挂着 `DOWNLOADING` 旧任务时回 `busy`。新包 MD5 变了，任务号也变，不先结束旧的空任务就发不了令。

**测试**：新增"真实候选文件接口 + 16 KB 下载"测试（只替换底层文件系统；在改前的接口上确实失败），"超过上限被截断"测试，取消命令 4 项；`test_candidate_files` 的旧上限断言改为 16385，并加 16 KB 真实文件写入读回；回归与之前一致；真实后台 `check_url.py` 通过。

**新包**：`firmware_releases/ota_1.5.9_to_1.5.10_20261104_1201/`，577348 B，**MD5 `4ac9ea42978a0189591f2f24549016de`**；LuaDB 496238/524288（余 28050）。
