## 根因与修复

旧GUI只有“CAT1厂商FOTA文件”入口，却没有从Lua工程生成FOTA的步骤；文件选择未过滤，打包核心仅按BIN/SOTA/PKG后缀放行，3字节普通BIN也能进入归档。新增回归用例实际复现旧行为失败。

第一次运行这个故意失败的用例时，CoreTests.exe没有顶层异常捕获，出现用户截图中的0xe0434352应用错误。已停止该测试进程并加入捕获，后续失败以`FAIL`和退出码1报告，不弹Windows未处理异常框；正式GUI启动自检也增加15秒超时。

## 原生格式依据和实际命令

依据本机已安装Luatools的`lua_script.CheckScript`及`soc.SocCombine.ec7xx_fota`实际脚本分支，并以独立的Luatools生成LuaDB缓存做只读格式对照。没有执行提取的Python代码，没有使用旧cat_1项目。

当前SOC为7z容器，info.json指定LuaDB、Lua5.3/64位、512KiB脚本区、脚本地址0x56E000、magic eac37218、块0x40000。mem_map.txt提供FOTA/备份/用户FS分区。本地证据位于`logs/cat1_fota_pack_20261022`；原生生成日志保留在各work目录。

实际使用Luatools自带`soc_tools.exe`，不是把USB缓存改后缀，也不是手造“原生”安装包。FotaToolkit用于底包差分，不是本次同底包脚本更新所需路径。

```text
luac_64bit.exe -s -o outN.luac srcN.lua
soc_tools.exe zip_file eac37218 56E000 script.bin script_fota.bin 40000 1
soc_tools.exe make_ota_file eac37218 0 0 0 0 0 script_fota.bin dummy.bin output.sota
```

其中script.bin由本轮当前源码编译的LuaDB构成，dummy.bin为空。所有厂商命令仅在新建工作目录运行，使用短相对文件名；长绝对路径曾导致厂商工具返回打开文件失败，已绕开。读取厂商目录，不写入D:\Installers、不调用下载/串口命令。

工具对关键厂商EXE与缺失依赖的外部来源核对SHA256。当前依赖库来自Luatools资源v2026.10.13.20；源码目录同名依赖优先。未捆绑厂商程序，因此其他人仍需准备对应Luatools目录，路径由界面选择。

## 版本与后台对接

整机`1.0---1.3`仍表示源→目标，CAT1实际版本单独记录。工具不会把整体标签当作组件已升级，不会自动改VERSION。当前生成的是001.000.000基线，不是N→N+1验收包。

新schema=3归档内容：bundle.json、GR5526/payload.bin、CAT1/payload.sota、CAT1/build.json。后台需升级字段/路径处理，拆分后按既定GR与CAT1串行流程下发。旧schema2路径不能直接沿用。CAT1固件的整包解析、正式验签/提交适配未因本轮主机工具修复自动完成。

原生包结构、对应SOC分区配置、解压读回已验证；当前运行设备的底包匹配仍未知，`cat_native_fota_partition_verified=false`保留，新增`cat_package_partition_profile_verified=true`用于区分。签名仍未验证、整机归档仍`device_installable=false`，禁止把CRC/MD5视为可信发布签名。
