# 方案一：居民姓名字形由平台推送（平台 → CAT1 → 串口 → GR → 电子纸）整体落地方案

SAM | 2026-11-02 | 读者：项目负责人、GR/CAT1/后台开发、测试 | 依据：`YP001_姓名生僻字动态字库方案可行性评估_20261019.md`（下称"评估"）+ 本次对工程代码的核对

## 0. 需求与已定边界

- 终端给"张秀华"使用，后台就把"张秀华"三个字的字形推送过来；**GR 里先不保存**这些字形（不写 Flash/NVDS，只放 RAM）。
- 路径固定：**平台 → CAT1（4G/MQTT）→ UART → GR5526 → LVGL → DEPG0150 电子纸**。
- 姓名文字本身 GR 已有保存机制（`resident_persist`，NVDS），本方案不改；只补"显示用的字形"。
- 本文是方案，**没有改任何固件/CAT1/后台代码，也没有板上验证**。

## 1. 对现有工程的核对结论（实际读过代码）

| 项 | 事实 | 对方案的影响 |
|---|---|---|
| 姓名来源 | 现在只有 `yp001_business.c:362` 里**写死的测试姓名**"张秀芳"（测试宏内），`yp_business_set_resident()` 有接口但**没有平台下发入口** | 平台→GR 的整条链路是**新做**的，不是修补 |
| 字体 | `font_cn_16/24/28/32/40`，SimHei，`--bpp 1 --no-compress`，**只导出约 185 个字**（0x20–0x7F + 固定的一批汉字），`line_height=33, base_line=5`（32px） | 偏僻字一定显示不出；字形格式是**无压缩 1bpp**，动态字形能与它完全同格式 |
| 缺字保护 | `epaper_ui.c:38 safe_text()`：整串只要有一个字缺，就整串显示 `"--"` | 动态字形接入前，姓名里有任何一个生僻字就是 `--`；这个策略要改（见 §5） |
| 姓名显示 | 主页姓名用 `font_cn_32`（`epaper_ui.c:359`），小字体页用 `font_cn_16`（:400）；房号 `font_cn_28`；园区 `font_cn_16` | **每个字至少需要 32px 和 16px 两套字形**（见 §3.2） |
| CAT1↔GR 业务通道 | 文本行协议：CAT1→GR `BUS_EVT={json}\r\n`，GR→CAT1 `BUS_CMD={json}\r\n`；GR 侧 `yp_business_handle_line()` 解析：**单行 < 512 字节、JSON 深度 ≤2、重复键拒绝、拒绝非法后不改状态** | 字形直接复用这个通道和它的安全规则，不另开串口协议 |
| CAT1 端接收 | `mqtts_receiver.lua` 里 `MsgType=="paraSetMsg"` 等已有分发；注意其中 `url` 等字段目前**大多被注释掉**，说明下发配置的存储路径还没做 | 新增 `MsgType` 即可，沿用同一个 MQTT 下行主题 |
| GR 内存 | 有 PSRAM（`yp001_psram_mem.h`），但**其中一块固定区域是 OTA 暂存**，内容易失 | 字形缓存用**普通 RAM（几 KB）**，不要占 PSRAM OTA 区 |
| CAT1 文件系统 | 空间很紧（见 OTA 空间文档），可用 430080，需 ≥ 440552 | **CAT1 不得保存字形**（仅做透传），否则会加剧 OTA 空间问题 |
| 产品文档 | F-021 居民信息显示，`paraSetMsg`；评估中 C-06 标"字段未定义" | 下面的报文是**草案**，必须先和客户/平台确认再冻结 |

## 2. 总体架构

```
平台后台                    CAT1 (Air780EGH)                          GR5526
┌──────────┐  MQTT下行   ┌─────────────────────┐ UART4 行协议  ┌──────────────────────┐
│姓名+字形 │───────────▶│ mqtts_receiver 校验  │──BUS_EVT────▶│ yp_business_handle_line│
│(含16/32px)│            │ 分包、限速、转发      │              │ 校验→RAM暂存→整批提交  │
│          │◀───────────│ 回执给平台           │◀──BUS_CMD────│ 应答 ack / need       │
└──────────┘  MQTT上行   └─────────────────────┘              └──────────┬───────────┘
                                                                        ▼
                                                    LVGL 动态字体适配层（RAM 缓存）
                                                    本地 font_cn_32 / 动态字形 → 电子纸
```

设计原则：
1. **后台出字形，设备不造字**（设备没有字体库和矢量渲染）。
2. **CAT1 只透传、不存**；**GR 只放 RAM、不写 Flash**。
3. **整批原子提交**：三个字没收齐、校验没过，就保持显示旧的有效姓名，不显示半截。
4. 重启后字形丢失 → **由 GR 向 CAT1 发"缺字请求"，CAT1 转平台重拉**（见 §4.4），不靠本地持久化。

## 3. 后台推送方案（平台怎样推）

### 3.1 一条 MQTT 下行报文（草案，需客户确认后冻结）

沿用现有下行主题（与 `paraSetMsg` 同一主题），新增 `MsgType`：

```json
{
  "MsgType": "residentNameMsg",
  "Seq": 1730500000,
  "Name": "张秀华",
  "Room": "1#1-102",
  "Campus": "泰康之家·燕园",
  "FontId": "simhei",
  "FontVer": 1,
  "Glyphs": [
    {"U": "5F20", "S": 32, "W": 28, "H": 29, "X": 2, "Y": 2, "A": 512, "D": "<base64>", "C": "A1B2"},
    {"U": "5F20", "S": 16, "W": 14, "H": 14, "X": 1, "Y": 1, "A": 256, "D": "<base64>", "C": "9C3D"}
  ]
}
```

字段含义（与本工程 `lv_font_fmt_txt` 字形描述一一对应，见 `lv_customer_font_simhei_32.c` 里的 `box_w/box_h/ofs_x/ofs_y/adv_w`）：

| 字段 | 含义 |
|---|---|
| U | Unicode 码点（十六进制，4~6 位） |
| S | 字号 px：16 或 32（目前姓名只用这两个，见 §1） |
| W/H | 点阵宽高（`box_w/box_h`） |
| X/Y | 左偏移、底偏移（`ofs_x/ofs_y`） |
| A | 前进宽度（`adv_w`，单位 1/16 px，32px 字通常是 512） |
| D | 点阵数据，**1bpp、无压缩、每行按字节对齐、高位在前**（实测：本工程 32px 字 29×29 的字形占 4 字节/行×29 行=116 字节），base64；字节数 = ⌈W/8⌉×H |
| C | 该字形 CRC16（对 U、S、W、H、X、Y、A、D 原始字节） |
| Seq | 单调递增版本号，设备只接受 ≥ 当前的 |

大小估算（1bpp）：32px 字 ≤ 128 字节，16px ≤ 32 字节；三个字两套字号共约 480 字节，base64 后约 640 字节，整条 JSON 约 1~1.2 KB。**MQTT 单条没有问题**。

### 3.2 平台要做什么

- **字形生成服务**：输入 Unicode 码点和字号，输出上面的 W/H/X/Y/A/D/C。生成方法见《方案二》的字形生成器（同一套逻辑可直接当后台服务或离线脚本）。
- 后台**每次下发姓名都带上该姓名全部字的字形**（不用判断设备缺哪个字，省掉查询往返）；设备对已有本地字体的字直接忽略。
- 同一终端同一 `Seq` 重发结果必须一致（幂等）。
- 字形来源与字体授权要留存（评估里已提：生成所用字体的嵌入/转换/下发授权，**SimHei 是否允许这样分发需要法务/客户确认**）。
- 不要把居民姓名写进平台日志的明文公开位置（隐私）。

### 3.3 回执（设备→平台）

CAT1 在 GR 回 `ack` 后上报：`{"MsgType":"residentNameReply","Seq":…,"Result":"ok|crc|full|busy|bad","Missing":["5F20"]}`。平台以此判断成功、重发或告警。

## 4. 设备端实现（分三段）

### 4.1 CAT1（Lua，`mqtts_receiver.lua` + 新模块）

1. `mqtts_receiver` 增加 `residentNameMsg` 分支：`pcall(json.decode)` 后做**严格检查**：字符数 ≤ 8、单字形 ≤ 200 字节、总 ≤ 3 KB、`S ∈ {16,32}`、U 是 BMP 且非控制字符、CRC 正确；任一错误整条丢弃并回 `bad`。
2. 校验通过后拆成**短行**发给 GR（每行 < 400 字节，GR 解析缓冲 512）：
   ```
   BUS_EVT={"op":"name_begin","id":N,"n":3,"g":6,"name":"张秀华","room":"…","campus":"…"}
   BUS_EVT={"op":"glyph","id":N,"i":0,"u":"5F20","s":32,"w":28,"h":29,"x":2,"y":2,"a":512,"d":"<hex或base64>","c":"A1B2"}
   … 共 g 行 …
   BUS_EVT={"op":"name_end","id":N,"crc":"…"}
   ```
   全部是**一层平铺 JSON**（GR 解析要求深度 ≤2、不得重复键）。逐行发送、等 GR 回 `BUS_CMD ack` 再发下一行（背压）；超时 2 s 重发，最多 3 次，失败回平台 `busy`。
3. **不落地**：不写 CAT1 文件系统，不生成新目录。
4. 受保护文件（`ota_*`、`business_*`、`update.lua`…）**不改**；新逻辑放在新文件（如 `resident_name.lua`）和 `mqtts_receiver.lua`，由同事实现并过 OTA 规则检查。UART1/UART4 注册只能在 `uart_app` 做，所以发送走已有 `_G.uart_send_raw`。

### 4.2 GR（C）

1. `yp_business_handle_line()` 里新增 `op` 分支 `name_begin / glyph / name_end`（沿用同一函数的校验框架，不另开解析）。
2. **RAM 暂存区**：固定大小静态缓冲（建议总计 ≤ 4 KB；8 字 × 2 字号 ≈ 8×(128+32)=1280 B，加索引留余量），分"暂存"和"活动"两份（乒乓）。
3. 逐字形校验：U/S/W/H 范围、`⌈W/8⌉×H` 与数据长度一致、CRC16；数量、总量、重复项检查；全部通过且收齐 `n`×2 个字形后才在 `name_end` **原子切换**为活动缓存，并调用 `yp_business_set_resident()` 更新姓名。中途失败：丢弃暂存，旧姓名/旧字形不动。
4. 回 `BUS_CMD={"op":"name_ack","id":N,"i":k,"ok":1}`，最终 `name_done`（含缺字列表）。

### 4.3 LVGL 动态字体适配层（GR，`gui/`）

- 新建 `dyn_font_16`、`dyn_font_32` 两个 `lv_font_t`：`get_glyph_dsc` 先查活动缓存，命中就填 `lv_font_glyph_dsc_t`（`box_w/box_h/ofs_x/ofs_y/adv_w/bpp=1`），**未命中不处理，交给 `fallback = &font_cn_32 / &font_cn_16`**，这样本地常用字仍走原来的 Flash 字体，生僻字走缓存。
- `get_glyph_bitmap` 返回缓存里的点阵指针（缓存常驻 RAM，LVGL 8.3 绘制期间可持续使用）。
- 把 `epaper_ui.c` 里用于姓名的字体换成这两个动态字体；`safe_text()` 改为按动态字体判断（见 §5 的缺字策略）。
- **兼容性要点（必须实测）**：本工程字体文件里，1bpp 字形实测是"每行按字节补齐"（如"张" 32px：`box_w=29, box_h=29`，两个字形的 `bitmap_index` 相差 116 = 4×29）。动态数据必须同格式，否则出现错位/斜纹乱码（我用连续位流去解读时就得到斜纹，改成按行补齐后与 PIL 渲染的"张"一致）。验证方法见 §6 的 T0。

### 4.4 重启/掉电之后

GR 不保存字形 → 重启后姓名文字（NVDS）在，但字形缓存空：
1. 姓名里的字，本地字体有的正常显示；
2. 缺的字，GR 在 CAT1 联网就绪（收到 `hello`）后发 `BUS_CMD={"op":"name_need","u":["5F20","79C0"]}`；
3. CAT1 向平台上报 `residentNameNeed`（带缺字列表和终端 IMEI），平台回一条 `residentNameMsg`；
4. 断网期间缺字显示按 §5 的策略处理。

> 这是"不保存"的代价：**首次开机必须联网一次**，断网重启后生僻字显示不出来。若客户不能接受，再单独评估"字形写 GR 的 NVDS/Flash"（评估里有空间和寿命要求），那是下一阶段，本方案不做。

## 5. 需要客户/产品先定的显示策略

| 场景 | 建议默认 | 备选 |
|---|---|---|
| 字形已收齐 | 正常显示姓名 | — |
| 个别字缺（断网重启、尚未收到） | 缺字位置显示"□"，其余字正常 | 整串显示"--"（当前行为）；或显示拼音 |
| 姓名超长 | 按 `font_cn_32` 宽度截断/自动缩到 16px 行 | 两行显示 |

当前 `safe_text()` 整串变 `--` 的行为在动态字形接入后应改成"逐字替换"，否则一个字没到整个姓名都不显示。

## 6. 怎样测试（分层，由易到难）

| 层 | 目的 | 做法 | 通过标准 |
|---|---|---|---|
| T0 离线格式自检 | 证明生成的点阵与本工程字体格式一致 | 用方案二的字形生成器，对**本地字体已有的字**（如 0x5F20"张"）生成 32px 字形，与 `lv_customer_font_simhei_32.c` 中该字的 bitmap 逐字节比较 | 完全一致或只差可解释的抗锯齿阈值；差异要记录 |
| T1 主机单元测试（C） | 验证 GR 解析/校验/原子提交 | 仿 `tools/business/test_gr_business.c`，喂正常、坏 CRC、错长度、重复字形、缺 `name_end`、超量、乱序 | 坏数据一律不改状态，正常数据一次提交 |
| T2 CAT1 主机测试（Lua） | 验证校验、拆行、重试 | 仿 `tools/ota/bench` 里的 Lua 测试，喂 MQTT JSON | 拆行 < 400 B、无落地写文件 |
| T3 串口注入（不接平台） | 只测 GR 显示 | 把方案二生成的 `BUS_EVT=` 行送进 GR。**注意**：COM26 是 GR 的调试 CLI，现有 CLI 不会把输入当 `BUS_EVT` 解析，所以需要二选一：①在 GR 加一条仅测试用的 CLI 命令（如 `busline <文本>`）把整行交给 `yp_business_handle_line()`；②在 CAT1 与 GR 的 UART4 之间用 USB-串口模块接入（需先让 CAT1 不发送，且注意电平和 GR 对 CAT1 在线状态的判断）。推荐①，改动小、可在发布版去掉 | 电子纸显示"张秀华"，生僻字也正确 |
| T4 CAT1 模拟平台 | 测 CAT1→GR 全链路 | 用 MQTT 客户端（如 mosquitto_pub / MQTTX）向设备下行主题发 `residentNameMsg` | GR 显示更新，平台收到 `residentNameReply: ok` |
| T5 故障注入 | 验证不坏旧数据 | 中途断 UART、坏 CRC、重复包、同一 Seq 重发、更小 Seq、存储满、CAT1 复位、GR 复位 | 旧姓名保持；无花屏；不卡死；报警/按键仍响应 |
| T6 真实平台联调 | 验收 | 正式平台下发 | 同 T4 |
| T7 OTA 回归 | 保证不破坏 OTA | 改完 CAT1 代码跑 `tools/ota_oneclick` 的 OTA 规则检查和一次整机 OTA | OTA 规则 0 阻断；LuaDB 余量够；升级后姓名/字形链路仍正常 |

怎样**构造测试姓名**：先用常用字（本地有的）测通链路，再换 2~3 个确认本地字体里**没有**的字（如"薇""珺""昀"，需先用方案二的生成器核对它们不在 `unicode_list` 里），最后测"常用字+生僻字混排"。

## 7. 风险与待确认

| 风险/待确认 | 说明 |
|---|---|
| 平台是否能生成字形 | 评估里就是前置条件；如果平台只能发文字，需新增字形服务（或先用方案二的工具离线生成一批） |
| 字体授权 | SimHei 的分发授权不明；可改用客户确认可用的字体 |
| 报文字段未冻结 | 评估 C-06；本文第 3 节是草案，需客户/平台书面确认 |
| 首次/断网重启显示 | 因"GR 不保存"，生僻字依赖联网重拉 |
| CAT1 空间 | 新 Lua 模块会占 LuaDB（余量约 41 KB，见空间文档），实现时用小模块（估计几 KB）并做 OTA 空间检查 |
| 电子纸刷新 | 姓名变更触发整屏刷新，要走现有显示调度，不能阻塞报警（评估已提） |
| 受保护文件 | CAT1 侧新逻辑不得改 `ota_*`/`business_*` 等；GR 侧改动要重新编译、签名、整机 OTA 实板验证 |
| 未验证项 | LVGL 动态字体在本工程配置下是否可行、显示速度、RAM 余量——**都还没验证**，建议先做 T0+T3 做最小原型再投入 |

## 8. 建议实施步骤（里程碑）

1. 冻结：报文字段、字号、缺字显示策略、字体授权（客户/平台确认）。
2. 方案二的字形生成器做出来，完成 **T0** 自检。
3. GR 最小原型：串口注入一个字形 → 动态字体 → 屏上显示（T1+T3）。
4. GR 完整：多字形、校验、原子提交、`name_need`。
5. CAT1：`residentNameMsg` 校验与转发（T2、T4），过 OTA 规则检查。
6. 联调与故障注入（T5、T6）。
7. 整机 OTA 回归（T7），再交付。

## 9. 本轮没有做的事
