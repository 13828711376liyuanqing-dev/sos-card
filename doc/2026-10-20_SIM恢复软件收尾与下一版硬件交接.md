## 下一版硬件需要提供的条件

1. 硬件人员给出最终卡座检测电路、检测脚/有效电平、供电及芯片推荐热插拔连接。当前软件不猜测卡座 GPIO，不照搬参考板 WAKEUP 引脚。
2. 确认该底包在新硬件上拔/插会产生哪些 SIM_IND、IP_LOSE/IP_READY，记录实际顺序和时间。mobile.setAuto 调用成功不等于电路和底包事件已经验证。
3. 如需新增 GPIO 检测，先核对实际引脚复用/去抖及厂商接口，再做单独适配；本轮不提前写未知引脚的代码。

## 下一版硬件验收表

| 操作/场景 | 必须观察 | 通过条件 |
|---|---|---|
| 在线拔卡 | SIM 丢失、IP/MQTT 退役、GR 网络状态 | 不沿用旧在线状态，不清报警/用户参数，不连续重启 |
| 保持无卡 | 软件任务、看门狗 | 不反复重启，不伪造注册成功 |
| 插回原卡 | RDY→注册→蜂窝 IP→MQTT→QoS1 SUBACK | 自动恢复并重新订阅；记录每阶段耗时，不先承诺固定秒数 |
| 更换卡/PIN 卡 | 状态、旧客户端/旧回调 | 锁卡不放行业务；旧事件不能恢复新卡业务；不自动尝试 PIN |
| 网络丢失但卡仍在 | IP_LOSE→IP_READY | 自动重建连接，不依赖再次插卡 |
| 五分钟等待末尾恢复 | generation、启动次数 | 新会话不继承旧超时，不被立即重启 |
| 三秒缓冲内恢复/喂狗 | 取消日志、启动次数 | 旧重启取消 |
| 重复快速事件 | 客户端数、订阅、内存/串口状态 | 无重复连接失控、无旧回调恢复，长时间压力另行记录 |
| 报警/通话期间丢卡 | 报警持久状态、音频与 SIP | 保留报警；旧电话不自动重拨；通话错误不等于取消报警 |
| 已有用户数据 | 号码/参数、待报任务 | 前后合法数据保持；不得格式化 fs/KV/NVDS |

## 仍然明确保留的边界

- 真实热插拔推迟到下一版硬件，当前不作为软件现场阻塞项反复要求用户操作。
- 主机事件是模拟的，不能证明底层事件完整、有序，也不能证明换卡后无标记的迟到 IP 事件属于新会话。
- 普通 RAM 发送队列不是所有业务的持久补报；只有已实现的持久待报路径有相应测试。
- 没有新增真实 SIP 拨号/双向音频证据；没有进行双端 OTA 异常恢复验收。下载成功、UART ACK、MQTT 在线分别记录。
- 下载助手连续烧写和成功后自动重烧属于另一项工具验收，不因本报告通过而关闭。
