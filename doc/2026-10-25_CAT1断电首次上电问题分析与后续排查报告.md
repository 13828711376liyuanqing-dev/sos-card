## 2. 正确的硬件和软件控制关系

| 对象 | 项目对应关系 | 能证明什么 / 不能证明什么 |
|---|---|---|
| PC → GR 调试串口 | COM26，CH340；GR UART0，GPIO28 TX / GPIO29 RX，115200 / 8N1 | 端口能打开仅证明 PC 驱动可用，不证明 GR 应用正在执行命令 |
| CAT1 受控供电 | GR GPIO6 → Q1201 / Q2，对 VCC_4G 提出供电请求 | GPIO/命令成功回执不是实际 VCC_4G 电压测量 |
| CAT1 开机键 | GR AON_GPIO0 → Q4，反相控制 Air780EGH PWRKEY | 当前 GR 命令按下约 1600 ms 后释放；执行回执不是 PWRKEY 实际波形 |
| GR → CAT1 业务串口 | UART4，AON_GPIO2 TX / AON_GPIO3 RX | CAT1 断电时本来就可能完全不响应，不能用它的回复作为供电的前提 |
| CAT1 USB | 模块原生 USB，交给 Luatools | 枚举只证明 USB 设备出现，不代表烧写完成或业务联网通过 |

当前固件入口为 `ble_app_uart_c/Src/platform/user_periph_setup.c` 的 `cat1_debug_power()`：

- `cat1_power on`：配置 GPIO6 并请求供电。
- `cat1_power key`：配置 AON_GPIO0，执行约 1.6 秒 PWRKEY 脉冲。
- 两者均受现有 GR OTA 电源变更保护约束；被拒绝时应停止，不能绕过。

板上 USB VBUS 还可能影响模块供电路径，故不能仅以 GPIO6 请求关闭、无 AT 回复或 USB 消失认定 VCC_4G 已为 0 V。之前拆件/测量记录不作为当前实物状态的自动认定。

## 3. 旧工具为什么不适合直接证明冷启动

旧 `FirstPowerOn()` 的调用顺序：

```text
ConnectSerial()
  → 发送 help，未识别 GR 回显则异常退出
ProbeCat1()
  → 在供电请求之前发送 cat_at AT_INFO
检查电脑串口
  → 发现任何其他串口则退出
cat1_power on
等待 200 ms
cat1_power key
```

因此截图里的“未取得 GR CLI 回显；未发送电源命令”表示：本次操作在第一层就停止，**CAT1 上电命令没有发送**。这个截图不能用于判定 Q2、GPIO6 或 CAT1 硬件上电失败。

旧检查意在防止误操作已运行模块、误重复 PWRKEY。但“其他串口存在”不能判断本模块状态；首次供电也不能依赖断电模块的回复。另一个问题是只写出命令后便推进状态，没有严格核对 GR 是否接受供电请求。

候选工具当前流程：

```text
用户明确选择“首次上电”，GR 本身有电并运行可接收命令的应用
  → 打开所选 GR UART0
  → 直接发送 cat1_power on
  → 最多等待 2500 ms，要求：
      [CAT1 POWER] rail_request=on code=0x0000;
  → 等待 200 ms
  → 若供电回执期间已经收到真实 CAT1 RX：跳过 PWRKEY
  → 否则在供电后做一次有界 AT_INFO 检查（最多 1500 ms）
      有实际 CAT1 RX：跳过 PWRKEY
      无实际 CAT1 RX：继续启动，不把无回复当成上电失败
  → 发送一次 cat1_power key
  → 最多等待 4000 ms，要求：
      [CAT1 POWER] manual_key code=0x0000;

```

命令已经请求但回执丢失时，结果应记为未知，不自动重复 PWRKEY。流程保持占用状态，须由操作者确认实际状态后明确取消本轮。工具本身不能测量模块电压，也不能保证用户误选“首次上电”时每一种下载态/异常态都能被 UART 识别；安装或下载过程中不得使用首次上电入口。

## 5. 本轮实板证据

### 5.1 第一轮直接请求供电：GR 确实执行了命令

日志：`logs/cat1_power_issue_20261025/cold_power_on_actual.txt`，约 17:28。

关键记录：

```text
TX cat1_power on
[CAT1 RX] [MQTT_STAT] ... state=CONNECTED
[CAT1 POWER] rail_request=on code=0x0000; ...
TX cat1_power key
[CAT1 POWER] manual_key code=0x0000; ...
```

结论：

- 当时 COM26 双向通信正常，GR 执行了供电请求和一次 PWRKEY 请求。
- **在 PWRKEY 前已经收到模块 MQTT 状态，因此该轮不是确认断电状态下的冷启动试验。** 这轮曾向已有回传的模块发送开机脉冲，不能当成安全冷启动通过。
- 因此随后增加“供电后收到真实模块回传则跳过 PWRKEY”的保护，并增加主机断言。
- 此后 Windows 曾列出 CAT1 COM21 / COM22 / COM23 为 Started，但没有连续 USB 插拔时刻记录，不能证明该脉冲导致了哪一次枚举或重启。

### 5.2 最新候选流程实板验证：GR 无回执，正确停在 PWRKEY 之前

日志：`logs/cat1_power_issue_20261025/cold_flow_live_guard_actual.txt`，约 17:34。

```text
TX cat1_power on
FAIL ... 未收到 GR 的 rail_request=on code=0x0000 回执 ... 未发送 PWRKEY
```

结论：新入口确实不再卡在 `help` 或 CAT1 回复之前，已发出供电请求；但 GR 没有返回执行结果。该轮没有发送 PWRKEY，不能确认 GPIO6 是否实际改变，也没有完成完整上电。

## 6. 必须纠正的前期判断

1. **窗口标题不等于 EXE 日期。** 用户确实选择了 `20261025_1558.exe`，旧标题硬编码“20261020”。此前因此判断用户打开旧版不成立；新版已改成显示实际 EXE 构建名。
2. **延长 `help` 等待到 2 秒没有解决现场问题。** 38 项主机测试只证明延迟读取逻辑，不证明现场 GR 能响应，更不证明 CAT1 能冷启动。
3. **前期直接映射 Flash 读到全 FF，不足以认定 Flash 已擦空。** 当时目标运行阶段、Flash 映射初始化和读回有效性没有完整核实；含旧字符串的前期描述也不能当作当前读回身份结论。
4. **UART0 LCR 先后读到 0 与 3，应结合取样时的运行阶段。** 本轮已经看到应用可响应与下载阶段静默两种状态。仅换 J-Link 设备名称或单个寄存器读数变化，不能证明修复了 UART。
5. **暂不应安排重复测 TX/RX 或拆硬件。** 应先确认 GR 已退出下载算法、正在运行预期应用；否则线路正常也收不到应用回执。
