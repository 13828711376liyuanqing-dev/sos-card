# R5空间根因：实板闭合结论

SAM | 2026-10-26 +08:00

用户完成空间诊断脚本下载后，助手经COM26执行一次 `cat_at OTA_SPACE=FILES`，收到真实返回：

```json
{"free_bytes":49152,"install_enabled":false,"total_bytes":524288,"current_bytes":0,"ok":true,"retired_bytes":429256,"used_bytes":475136}
```

## 已确认的直接原因

1. R4旧候选确实仍存在，物理大小429256字节。
2. R5新hash候选确认不存在，大小0。
3. R5原生签名GR组件432328字节，空间检查要求再留16384字节，合计448712。
4. 当前可用49152，少399560字节，必然返回COMPONENT_SPACE。
5. R4退役流程仅保留旧候选与退休历史，未接入现有pending_cleanup。此前真实manager离线复现已经确认该生命周期缺口。

因此，R5本次零进度拒绝不是待猜测的旧候选占用问题，已得到直接文件大小证据。空间门本身正确拒绝不足，错误在于新旧候选迁移与预检顺序未闭合。

## 为什么R4能进传输，R5却不能

R4可复用自己的已有候选，其existing抵扣剩余空间需求。R5是新hash、新候选，existing=0；又保留着R4完整候选，所以无法写入。不能让新任务继承旧hash文件或299008字节GR进度。

## 修复目标及边界

- 针对有精确退休凭证的旧OTA候选建立可重入回收流程；保留任务历史、次数、凭证和用户数据。
- 删除前需冻结确切旧hash路径、备份/证据策略及授权范围，不能清LFS或任意o*.p文件。
- 回收后以实际fsstat再次验证可用空间，不能只把429256加到free就宣布可用；LittleFS块回收和元数据占用需实测。
- 增加消费票据前只读空间预检，运行阶段仍保留预算与身份检查。
- 现有R5票据保持SPENT，不通过清状态、重启或再次ARM获得机会；下一次实板OTA仍须单独批准。

## 本轮实际操作

仅发送一次只读命令并保存返回，没有删除候选、修改用户数据或执行OTA。
