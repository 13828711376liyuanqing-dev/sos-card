# GR5526 官方 OTA 方案核对与当前项目取舍

SAM | 2026-10-27 +08:00 | 官方 SDK 1.0.4 源码核对；本轮未改固件、未编译、未烧录、未执行 OTA。

## 结论

当前不适合临时整体替换成官方 DFU。应保留现有 R6、分区、签名和独立 Boot，采用官方明确的阶段边界：接收候选、完整校验、授权激活、重启后安装。业务健康确认及回退是项目额外职责，不能把官方 Double Bank 当成已具备这些能力。

本报告依据项目唯一活动 SDK 内的官方实现；官网在线指南本轮未成功读取，不将在线页面内容当证据。SDK 来源记录见 `2026-10-14_SDK目录完整统一到1.0.4.md`。部分 DFU 核心在库/ROM，公开 C 源码不能说明其全部时序。

## 官方实际怎样做

| 阶段 | 官方实现及证据 | 对本项目的意义 |
| --- | --- | --- |
| 模式 | `SDK/components/libraries/dfu_port/dfu_port.h:54–55`：Copy=Double bank/Background；Non-copy=Single bank/Non-background | 本项目需要业务继续运行，方向接近 Copy；Single bank 不满足保留旧程序回退要求 |
| 接收 | 模板 `Src/platform/user_periph_setup.c:107–156`：UART 接收回调交给 DFU 解析，然后异步重挂；发送也为异步 | 官方模板并未提供本项目共享 UART 的业务仲裁、首错恢复与许可协议；不能声称照抄即可解决溢出 |
| 调度 | 模板 `Src/user/main.c:73` 持续调用 `dfu_schedule()`；`dfu_port.c:1352–1433` 快速 DFU 使用环形缓冲、分次写入和调度状态机 | 必须保证前台调度得到运行，不能被屏幕等待或长业务循环饿死。快速缓冲路径主要为 BLE，不能直接断言 UART 使用同一缓冲机制 |
| 缓冲 | `dfu_port.c:56–62`：2048B DFU 缓冲、1024B 单次写、4096B Flash cache，最小环形缓冲5120B | 是容量/吞吐设计参考，不构成460800 UART在关中断时不会丢数据的保证 |
| 结束 | `dfu_port.c:1120` 起的 `program_end_replace`：校验、更新元数据，按 reset_flag 决定后续，flag1自动复位 | 不能把默认完成回调直接接入本项目，否则可能绕开最终业务提交门 |
| Boot安装 | `bootloader_boot_vendor.c:518–564`：验证DFU信息→验证候选→复制到活动区→更新应用信息→清DFU信息→复位 | 安装有明确独立阶段，候选收齐不等于安装完成 |
| 复制窗口 | 同文件 `284–354`：RAM代码，4KB页复制，复制循环关闭全局异常，刷新看门狗 | 官方也没有保证安装期间持续接收UART；必须先让发送方停止、确认边界，再进入安装。不能由此反推本次故障就是该函数导致 |
| 启动验证 | 同文件 `576–601`：应用验证后才跳转 | 独立Boot是可信安装/启动边界，应保留 |

## 不可直接照搬的三点

1. **分区冲突**：官方 DFU 信息默认 `0x203000`（dfu_port.h:48），Boot 示例暂存默认 `0x240000`（bootloader_config.h:107），GR5526应用模板暂存 `0x260000`（user_periph_setup.c:65）。这些地址与本项目 A 区 `0x202000–0x26E000` 重叠。不是修改一个宏就能安全切换；用户数据和当前候选均禁止迁移覆盖。
2. **Double Bank不等于健康回退**：所查 Copy 流程是暂存后覆盖活动区，没有本项目的试运行120秒、确认、失败自动恢复旧A职责。复制期间候选仍在与健康失败可回退，是两种不同能力。源码也不足以宣称所有断电切点都已安全。
3. **签名配置不可照默认值**：官方Boot示例 `BOOTLOADER_SIGN_ENABLE=0`（config:73），并提供更新后验签配置。示例默认值不等于产品安全配置；本项目不得关闭签名或用持久跳过验签换速度。官方镜像尾部长度与YPGR相近也不能证明格式兼容。

## 对当前卡点的判断

现有实板记录表明：R6的432328字节已在GR持久收齐；owner处于INSTALL_PENDING，而Boot仍PREPARED，实际GR仍1.0.2。因此当前最后阻塞属于**应用授权提交到Boot安装的交接**，继续优化下载速度或重传完整镜像不能关闭这个缺口。

官方源码支持上述阶段划分，但没有证明当前自建状态机每个失败的根因。此前UART FIFO溢出、静默期限、前台调度与本次提交交接，必须按各自证据分别处理，不能合并成一个“硬件问题”或“官网方案能自动解决”。

## 最短落地路径

1. **冻结现R6，不换包、不改布局**。接受用户已完成的编译结果时核对真实输入和产物；控制入口后续改动尚未进入旧GR产物，旧产物不能充当新源码验收。
2. **闭合唯一提交交接**：校验在静默租约前分阶段完成；结果严格绑定本次owner与A/B身份；短提交仅写Boot安装意图，成功后才允许复位。Boot独立认证继续保留。PREPARED换维修基线必须使用已限定作用域的衔接逻辑，不能手改日志。
3. **交付一套匹配集合**：CAT脚本、签名GR应用、匹配Boot及读回清单。当前控制入口修正未编译，最终集合尚不可称可部署；Boot代码已编译，不因应用指纹变化重复编译Boot代码。
4. **先只读核对部署和正常启动**：确认SCA进入Boot、A/Boot匹配，B/owner/用户区保持；确认GR CLI、CAT1真实供电及版本回应。明确区分维修PREPARED重绑与真正安装。
5. **最后一次获批验收**：同步短段逻辑仪和RAM时间线，验证Boot进入INSTALL、目标启动、健康确认、结果持久化，再串行完成CAT1。既有机会不重复消费，新增机会按原授权边界办理。

## 当前边界

本轮关闭了“官方方案是否能直接替换当前方案”的分析：不能直接替换；可采用其阶段划分和持续调度原则。未证明双端OTA完成。现R6目标保留旧恢复逻辑，通路测通也不等于最终产品修复版验收。
