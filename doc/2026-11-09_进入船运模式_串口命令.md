# 进入船运模式：GR 调试串口命令

SAM | 2026-11-09 | 读者：工厂/测试人员、项目负责人 | 依据：固件源码（`yp001_charger_cli.c`、`yp001_charger.c`、`yp001_shipping.h`、`cli.c`）+ 11-08 实板测试记录。固件版本：1.5.25 及以后（已随 1.5.26 真实 OTA 上板）。

> **会让板子断电。** 命令成功后约 10~12 秒，电池与系统断开，卡片熄屏、调试串口和 CAT1 的 USB 口都会消失；要恢复必须**插 5V 适配器**。没有"取消"和"重试"。

## 一、连接

| 项 | 值 |
|---|---|
| 串口 | GR 调试口（CH340），**COM 号会变，以设备管理器为准**（11-09 台架是 COM30） |
| 参数 | 115200，8N1，命令以回车换行（CRLF）结尾 |
| 其他口 | 不要用 CAT1 的 USB 口（COM21/22/23）发这些命令 |
| 用脚本发 | `python tools/ota/gr_cli.py --wait-ms 3000 "charger ship start"`（不带 `--port` 会自动识别 GR 口） |

调试串口平时每秒会打印一行 `[BAT] raw=… BAT=…mV EST=…%`，属正常，会夹在命令输出中间。

## 二、进入前的条件（工厂出厂前配置）

- **电池必须接好并有电**（BAT 读数正常，例如 4100 mV 以上）。拔掉 USB 后卡要能靠电池继续运行；拔完就停说明电池路径有问题，先解决再测。
- **卡端 USB（5V 输入）必须拔掉**，否则不会进入关断。
- 固件会**强制**关闭 CAT1 电源、释放工厂保电、清掉按键标记，不需要手工处理。
- 唯一会拒绝的情况：**OTA 正在进行**（原因码 `OTA_guard`），此时不能断电。
- 其他外部条件（报警、通话、找人、通信链路、OTA 布局等）**都不检查**（出厂前配置，强制执行）。

## 三、推荐用法：一条命令（强制一键）

### 1. 发命令

```
charger ship start
```

### 2. 命令返回（立即）

设备在等你拔 USB 时：

```
[SHIP] auto=WAIT_USB_REMOVED reason=remove_card_USB attempted=0
[SHIP] state=IDLE token=0 attempted=0 reason=not requested
[SHIP] REG07=4C REG0D=1C REG08=A4 REG0A=80
```

如果 USB 本来就没接，会直接进入检查：

```
[SHIP] auto=CHECKING reason=remove_card_USB attempted=0     （首条状态；随后推进）
```

（`REG07`/`REG0D`/`REG08`/`REG0A` 是充电芯片 ETA69631 的寄存器原始值，`REG07=4C` 表示 BATFET_DIS=0，没有遗留关断状态。）

### 3. 拔掉卡端 USB

固件每个节拍自己推进：**等 USB 拔掉 → 检查 → 准备（至少 2 秒稳定）→ 确认 → 写 BATFET_DIS**。等 USB 的上限是 **60 秒**，超时失败（`USB_wait_timeout`）。

成功时会打印（确认后）：

```
[SHIP] BATFET_DIS readback=1; delay ~12s; accepted, physical cutoff UNVERIFIED
[SHIP] auto=SENT reason=BATFET_readback_confirmed attempted=1
[SHIP] state=SENT token=0 attempted=1 reason=command accepted; SYS/current require measurement
[SHIP] no cancel/retry; measure SYS and battery current; insert 5V to restore
```

### 4. 之后（不会再有串口输出）

约 **10~12 秒**后板子断电：卡片熄屏，COM30 无输出，CAT1 的 COM21/22/23 消失。11-08 实测：确认后约 10~11 秒断电，与 ETA69631 手册（BATFET_DLY=1，约 10 s，规格 12 s）一致。

### 5. 恢复

**插上 5V 适配器**，板子重新上电（手册里的其他恢复方式：清 BATFET_DIS、REG_RST、nQON 低 ≥ 1.15 s）。

## 四、查状态（只读，随时可发）

```
charger ship status
```

输出两到三行：

```
[SHIP] auto=<自动任务阶段> reason=<原因> attempted=<0|1>     （只有一键任务启动过才有这一行）
[SHIP] state=<底层阶段> token=<令牌> attempted=<0|1> reason=<原因>
[SHIP] REG07=.. REG0D=.. REG08=.. REG0A=..                     （还没写 BATFET 时才有）
```

| 字段 | 取值 |
|---|---|
| `auto=`（一键任务） | `IDLE` / `CHECKING` / `SENT` / `FAILED` / `UNKNOWN` / `WAIT_USB_REMOVED` |
| `state=`（底层） | `IDLE` / `CHECKING` / `READY` / `SENT` / `FAILED` |
| `attempted` | 1 = 已经写过 BATFET 关断（不能取消、不能重试） |

### `auto=` 与 `reason=` 对照

| reason | 含义 | 怎么办 |
|---|---|---|
| `remove_card_USB` | 命令已接受，等你拔 USB | 拔掉卡端 USB |
| `qualifying` | USB 已拔，正在检查/稳定 | 等 |
| `BATFET_readback_confirmed` | BATFET 关断位已写入并读回确认（`auto=SENT`） | 等 10~12 秒断电；之后插 5V 恢复 |
| `USB_wait_timeout` | 60 秒内没拔 USB | 失败，需重新发起（见下面"注意"） |
| `input_state_unknown` | 读不到充电芯片输入状态（I2C 失败） | 失败，检查板子后重来 |
| `prepare_rejected` | 准备阶段被拒绝 | 失败 |
| `qualification_failed` | 检查/稳定期间条件变化（`state` 回到 FAILED/IDLE） | 失败 |
| `confirm_rejected` | 确认被拒绝，没写 BATFET | 失败 |
| `BATFET_write_uncertain` | **BATFET 写入回读不确定**，硬件可能已断（`auto=UNKNOWN`） | 当作可能已关断；用 5V 恢复，不要重复发 |
| `OTA_guard` | OTA 事务正在占用 Flash/电源 | 等 OTA 结束再发 |
| `CAT1_power_off_failed` | 强制关 CAT1 没成功，为安全不断电 | 失败，检查 CAT1 电源命令 |
| `cancelled` | 被 `charger ship cancel` 取消 | — |

### `state=` 的 reason（底层）

`not requested`、`qualification`、`ready; confirm within 30 seconds`、`confirmation expired`、`business/key/CAT1/OTA guard`、`I2C read failed`、`BATFET already armed`（芯片里已经武装了，不能再写）、`input/charge/OTG/watchdog/ID guard`、`guard changed during I2C`、`delay setup/final guard failed`、`BATFET write/readback uncertain; restore with 5V`、`command accepted; SYS/current require measurement`、`cancelled before BATFET write`。

## 五、其他命令

| 命令 | 作用 | 说明 |
|---|---|---|
| `charger ship status` | 查状态 | 只读 |
| `charger ship cancel` | 取消 | **只在 BATFET 还没写之前有效**；写过以后返回失败，不能取消 |
| `charger ship prepare` | 旧的手动准备（第 1 步） | 沿用原来的严格条件，**出厂前请用 `start`**；被拒绝时打印 `[SHIP] prepare refused: lock/tick/offline/key/OTA/ID guard`；一键任务运行期间被拒绝 |
| `charger ship confirm <token>` | 旧的手动确认（第 2 步） | 令牌来自 `prepare` 后的状态行（`[SHIP] confirm within 30s: charger ship confirm <数字>`），**30 秒内**有效；一键任务运行期间被拒绝；失败打印 `[SHIP] confirm refused or write unconfirmed` |
| `charger ship <其他>` | — | 打印 `Usage: charger ship start|prepare|status|cancel|confirm <token>` |

**手动 prepare/confirm 的限制（根据代码推断，没有实测）：** 手动路径仍要求"未配置 OTA 端口、无报警、不在线、无通话"等严格条件，而 OTA 过的板子 `fw_version` 里 `ota_provisioned=1`，所以**手动路径在已 OTA 的板子上多半会被拒绝**。出厂请只用 `charger ship start`。

进入船运锁定后（`prepare` 通过，或一键任务运行中），其他 `charger …` 命令会被挡：

```
[SHIP] command blocked; use charger ship status/cancel
```

## 六、一次完整的串口会话（示例）

下面是按代码和 11-08 实测记录整理的示例，数值只用于说明格式，不是逐字抓取：

```
> fw_version
[FW_VERSION] YP001_FW|GR5526|001.005.026|30|END product=1.5.26 ...
> charger ship status
[SHIP] state=IDLE token=0 attempted=0 reason=not requested
[SHIP] REG07=4C REG0D=1C REG08=A4 REG0A=80
> charger ship start
[SHIP] auto=WAIT_USB_REMOVED reason=remove_card_USB attempted=0
[SHIP] state=IDLE token=0 attempted=0 reason=not requested
[SHIP] REG07=4C REG0D=1C REG08=A4 REG0A=80
（此时拔掉卡端 USB）
[SHIP] BATFET_DIS readback=1; delay ~12s; accepted, physical cutoff UNVERIFIED
[SHIP] auto=SENT reason=BATFET_readback_confirmed attempted=1
（约 10~12 秒后串口断开，板子断电）
```

11-08 实板（用 BLE 工具发 `FT SHIP_START`）的真实应答：先回 `ok=1 auto_phase=5 reason=remove_card_USB`，约 1.5 秒后查询得到 `state=3 attempted=1 auto_phase=2 reason=BATFET_readback_confirmed`（`state=3` 即 SENT，`auto_phase=2` 即关断已确认）。

## 七、注意

1. **失败后重新发起：** 代码里一键任务一旦进入 `FAILED/UNKNOWN`/`SENT`，我没有找到把它清回 `IDLE` 的路径，`charger ship start` 会直接失败。推断：需要**重启 GR（断电重上电）**再发；这一点没有逐字实测。
2. **量电压/电流前，把所有调试线拔掉**（UART 适配器、J-Link）：它们会通过 IO 保护二极管反灌 SYS，量出来的 SYS 不是真实值。
3. 实物验收（SYS 降到接近 0 V、电池侧微安级电流、插 5V 后能正常重启）**还没做**；"确认后约 10~11 秒断电"有实测证据。
4. 工厂工人用的是 BLE 工具（`YP001_BLE_Setup`，COM31 的 nRF 抓包器 + 卡端蓝牙）：点"进入船运模式"，绿色"命令已下达 · PASS"→ 拔卡端 USB → 绿色"PASS · 船运成功"。串口命令是它底下同一套逻辑，供调试和排查用。
5. 命令名里的 `ship` 是 `charger` 的子命令，必须写成 `charger ship …`；单独 `ship` 不存在。
