# 双端 OTA 第2步：容量与后端边界

SAM | 2026-10-20 +08:00

## 当前结论

当前镜像不能直接按旧内部 A/B 提案进入实机写入。此次完成静态容量核算及SDK数据区规则核对；实物Flash容量/ID、运行时NVDS地址没有读出，不能标成实测。无烧录、擦除、地址迁移或用户数据读取/写入。

## 可复核预算

主/交付HEX均逐记录验证长度和校验和，数据511328字节，范围 `[0x00202000,0x0027ED60)`，跨度511328字节。4KiB对齐槽位512000字节（500KiB）。两份HEX的hash不同，容量相同，不声明二进制一致。

按手册所载GR5526RGNIP内置1MiB Flash、假设4KiB擦除扇区：

| 区域 | 字节 |
|---|---:|
| 两个500KiB应用槽 | 1024000 |
| 一个交换扇区 | 4096 |
| 两份Boot事务日志 | 8192 |
| 暂定用户/NVDS保留区 | 8192 |
| 合计 | 1044480 |
| 1MiB剩余 | 4096 |

仅剩4KiB供Boot和全部其他区域，未计额外签名封装、仲裁日志和新增接收代码。若Boot暂按32KiB占位估算，已超28672字节；32KiB不是实际编译结果，8KiB也不是完整用户数据清单。故不能以此冻结量产布局或声称只差28KiB即可完成。

原始数值及当前HEX SHA256：`logs/ota_preflight_20261020/gr_capacity.json`。手册来源：`logs/ota_plan_20261012/datasheet_selected_pages.txt`，说明1MB内置Flash和8MB PSRAM；PSRAM不能当断电备份。实际器件/扩展Flash仍待确认。

## 用户数据保护核对

- custom_config.h 里旧0x0027E000 NVDS地址是注释，不能当有效布局；现应用已跨过此地址。
- gr_soc.c 在未指定NVDS_START_ADDR时调用 nvds_init(0,NVDS_NUM_SECTOR)，当前配置为1。
- SDK/components/sdk/gr55xx_nvds.h 明确NVDS另用一个GC扇区；start_addr=0时放到Flash尾部。若真实容量为1MiB且扇区4KiB，应保留尾部两扇区，但实际地址仍需运行时读取，不能只靠推算写入。
- NVDS_ALLOW_DESTRUCTIVE_RECOVERY=0；初始化异常不自动擦除。此保护保留。
- SDK/算法写16MB仅是支持/链接声明，不证明现板容量；现有scatter不能直接作为OTA擦写白名单。

SDK已有只读 hal_flash_get_info(id,size)，NVDS运行时地址接口可用于后续诊断；当前CLI尚无对应输出。此轮未为诊断强行下载新固件，也没有把可能暂停CPU的J-Link操作当无影响读取执行。

## 选择边界

1. 内部双槽：先获得独立Boot真实大小和完整保留区，按预算决定是否有可行空间。不得擅自删业务、去掉回退、压缩用户数据区或扩大到实际Flash之外。
2. 外部非易失备份：若下一版增加NOR，需确认容量、引脚、电压与供电，再实现相应Boot后端；外部复制方案与客户要求的A/B翻转、重启时长仍须评审，不自动等价。
3. 只靠CAT1存旧包、GR应用自覆盖：不能提供独立可启动回退，不作为当前安全升级方案的替代。

## CAT1自升级可以独立推进的准备

update.lua 禁止旧FOTA_CHECK和CAT1_FOTA_REQ旁路，只暴露状态查询。ota_platform.default尚未接通发布映射、签名/安全门、厂商激活和真实健康确认，因此当前不能实际安装。

libfota2.request使用厂商HTTP FOTA路径；仅源码有此API，不能证明可先普通文件完整校验、在安全窗内延迟激活，亦不能证明任意复位不会提前安装。下一步需按当前V2052底包确认包型、激活控制、fs/KV保留、失败后可恢复边界，再准备真实N→N+1试验包。不得以直接调用旧库绕开GR授权作“验收”。
