## 实测经过

1. 用 0.2.2 工具点"进入船运模式"，按提示拔掉卡端 USB。工具界面显示红色"失败 / 结果未知"，详情是 `Device disconnected`（蓝牙断开）。
2. 板子调试串口 COM30 此后无任何输出（发 `fw_version` 无回应），CAT1 的 COM21/22/23 消失 → 板子已断电。
3. 工具缺陷：蓝牙断开被当作错误事件，覆盖了设备已有的结果，船运本就以断开收尾 → 0.2.3 改为：命令已下达（绿 PASS）、关断已确认（绿 PASS · 船运成功，断开后保持）、未确认断开（黄色待确认）、拒绝（红 FAIL + 原因）。
4. 万用表测 SYS：**2.14 V**（当时仍有外部在给板子供电，用户确认去掉外部供电后），随后 **0.8 V 并在下降**。

## 判读（已有 / 还缺）

- 已有：SYS 低于电池电压，外部供电去掉后持续放电 → 与 BATFET 断开、SYS 与电池隔离一致；COM30 无输出、CAT1 掉电。
- **还缺**：SYS 是否降到接近 0 V 并保持；电池侧电流（应为微安级，需串电流表）；**插 5V 后板子能否正常重启**（恢复路径）；0.2.3 工具上"命令已下达 · PASS → PASS · 船运成功 → 断开仍保持 PASS"的实际显示；用 0.2.3 重测一次完整流程。

## 补充：第二次测试（工具 0.2.3）的诊断记录分析（21:23–21:24）

证据：工具"诊断记录"保存的 `YP001_COM31.log`（时间戳精确到毫秒）。

| 时间 | 事件 |
|---|---|
| 21:23:58.77 | 发 `FT SHIP_START` |
| 21:23:59.4 | 设备回 `ok=1 auto_phase=5 reason=remove_card_USB`（命令已接受，等待拔卡端 USB）→ 工具显示绿色"命令已下达 · PASS" |
| 21:24:00.5 ~ 21:24:06.6 | 每秒查状态 5 次，设备均回 `auto_phase=5`（仍在等拔 USB，**设备一直在线、响应正常**） |
| 21:24:07.7 | 发第 6 次状态查询，**设备无任何回应** |
| 21:24:10.7 | 链路监督超时 `BLE_HCI_CONNECTION_TIMEOUT`（监督超时 4 s），工具显示黄色"已断开 · 结果待确认" |

**结论：**
1. **这次没有走到关断。** 设备从未回过 `auto_phase=1`（检查中）或 `2`（关断已确认）。关断流程要先"准备"（至少等 2 秒）再"确认"，然后再延迟约 10~12 秒才断电；而设备在最后一次回应后约 1 秒内就**无声消失**，来不及走完。
2. **设备是在你拔掉卡端 USB 的那一刻失去电源的**，不是 BATFET 关断的结果。蓝牙断开原因是链路超时（无线电突然消失），不是正常断开。
3. 所以板子此刻"熄屏、串口无输出"是**断电，不是成功船运**。工具的黄色提示是正确的，没有误报成功。
4. 手册（ETA69631 REV1.0）确认退出船运的条件：插适配器、清 BATFET_DIS、REG_RST、nQON 低 ≥1.15 s；BATFET_DLY=1 表示写关断位后约 10~12 s 才断。

**最可能的原因（待用户确认）：** 拔 USB 时电池没有给板子供电——（A）电池线没接在卡上（例如测 SYS 时拆过）；（B）上一次测试遗留的 BATFET 关断状态使电池路径仍被断开（手册说插适配器会恢复，但未验证）；（C）电池连接器接触不良。电池电压 4.1 V 只能说明电池本身有电，不能说明它接到了卡上。
**验证办法：** 接好电池，用 USB 把卡供电启动，再拔 USB，看卡是否继续运行（COM30 持续有输出、蓝牙不断）。拔完立刻停了 = 电池路径有问题，先解决再测船运。

## 补充：第三次测试（工具 0.2.3，USB 已拔、电池供电）——设备确认关断

测试前只读核对：卡片靠电池运行，BAT=4173 mV（86%），VBUS=0；`REG07=4C`（BATFET_DIS=0，未遗留关断状态）；`charger ship status` = IDLE、attempted=0。第二次失败的原因基本落在当时电池没有给板子供电。

证据：工具诊断记录 `YP001_COM31ok.log`（`logs/ship_forced_flash_20261108/tool_diag_third_run_ok.log`）。

| 时间 | 事件 |
|---|---|
| 22:08:57.93 | 发 `FT SHIP_START` |
| 22:08:58.3 | 设备回 `ok=1 auto_phase=5`（命令已接受）→ 工具绿色"命令已下达 · PASS" |
| 22:08:59.47 | 第一次状态查询：**`state=3 attempted=1 auto_phase=2 reason=BATFET_readback_confirmed`**（SENT，BATFET 写入回读确认）→ 工具绿色"PASS · 船运成功" |
| 22:09:13.9 | 链路监督超时 `BLE_HCI_CONNECTION_TIMEOUT` |

判读：
- 从点击到"关断已确认"约 **1.5 秒**（USB 已不在，直接进入检查、准备、确认）。
- 设备在确认后约 14 s 失联；扣除监督超时 4 s，**断电发生在确认后约 10~11 s**，与手册（ETA69631 REV1.0：BATFET_DLY=1 时延迟约 10 s，规格 12 s）一致。这是"确认之后才断电，且延迟符合手册"的时间线，不是上次那种拔 USB 即无声消失。
- 这次工具按预期：确认之前不报成功，确认之后断开不改变 PASS。

观察（未解释，不影响结论）：同时记录的 GR 调试串口 COM30 在 22:08:41 就不再有输出（最后一行 `[CHG] INPUT ABSENT; auto rearmed`），早于点击 16 s，但 GR 在 22:08:58 仍正常回应蓝牙，推测与低功耗/日志策略有关，**未验证**。因此这次没有 GR 侧时间线，船运判读只依据工具诊断记录。

**仍待验收（需要万用表）**：SYS 降到接近 0 V 并保持；电池侧电流（微安级）；插 5V 后板子能否正常启动（恢复路径）。其中"设备确认关断 + 延迟符合手册"已有证据，"实际断电并可恢复"只差上面三项物理测量。
