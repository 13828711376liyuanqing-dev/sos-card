## 1. 哪些结论成立，哪些必须收窄

| 原判断 | 本次复核结果 | 证据边界 |
|---|---|---|
| 原始错误0x2是UART接收FIFO溢出 | 成立。SDK定义与第7次首错一致；软件环丢弃为0 | 说明硬件FIFO没有及时得到接收服务，不等于器件、焊接或电平损坏 |
| abort已经成功，却被前台等待时间判成超时 | 成立。实板abort_result=0、done=1、phase=3、没有重挂；冻结生产函数已离线复现 | 这是确定的软件恢复缺陷，不是再延长超时即可正确解决 |
| 299008/429256字节已经持久化 | 成立，是第7次停止时的有效协调记录，generation=78、epoch=2 | 本轮没有重新连接设备；这是保留的实板快照，不冒充本轮实时值 |
| GR运行应用、Boot、保护区和NVDS保持 | 第7次前后快照逐字节比较成立 | 不扩大为CAT1全部KV已验收，也不说明OTA已安装 |
| 溢出的具体服务延迟源尚未闭环 | 仍成立，但调查已有明确方向 | 已找到实际ROM全局关中断分支和发送并发缺口；缺故障瞬间波形、实际屏蔽时间及当时FIFO占用 |

实际ROM保护参数为0，扇区擦除分支设置PRIMASK，UART中断也被屏蔽。CAT1生产发送队列会在DATA之后、不等对应ACK继续提交普通业务文本。SDK FIFO为128字节，460800/8N1下，从空到满约2.78ms。

**不能越过的一步：**现有队列复现仅证明又提交了36字节，36字节本身小于128字节；没有当时FIFO占用、其他发送量和实际屏蔽时间，不能单凭这36字节宣称第7次的唯一原因已经完全证明。2.78ms也是理论容量时间，不是已测到的擦除耗时。

因此结论分两层：

- **已确定的软件问题：**恢复误超时、Flash操作与串口发送缺少完整协调。
- **仍待实板定位的物理时序：**第7次具体哪一个服务空窗造成OE。当前没有证据要求换板、改电路或换芯片，也不能宣称电气问题已经排除。

## 2. 本次新发现的关联缺口

### 2.1 旧R4目标会重新带回旧接收逻辑——必须改变交付范围

核对的对象是R4实际GR目标，不是当前工作区源码：

- 文件：`firmware_releases/gr_usb_bench_20261024/target/target_signed.bin`
- SHA256：`96bc08c57633b4a820fa2ed0b2df57860eefefa85596aff338b407454c1a5139`
- 本轮重算二进制和反汇编文件哈希，与冻结`BUILD_VERIFIED.json`一致。
- 目标反汇编：`uart4_evt_handler`在`0x0022f8a6`跳入错误分支，`0x0022f92e`读取错误，随后`0x0022f94e`直接调用`app_uart_receive_async`；没有当前前台`cat_uart_recovery_poll`修复。

**影响：**即使新基线把旧R4传输、安装成功，运行的1.5.0仍会带回旧错误恢复路径。继续保持R4目标不变，最多验证旧包的安装通路，不能算本次修复完整交付。

推荐修正：基线1.0.2和目标1.5.0使用同一套已审查修复；生成一个新的签名包（拟标R5，实际哈希生成后冻结）。不只改ZIP文件名，不在R4原哈希下替换内容，不凭包名冒充目标已更新。

### 2.2 “DATA发出后等ACK”只覆盖了一部分Flash写入

当前存在至少三类写入：

| 写入点 | 当前调用链 | 需要的协调 |
|---|---|---|
| B槽扇区及持久进度 | `yp_receive_data → flush → erase/write → checkpoint`，最后才回ACK | 在对应请求完成前禁止追加CAT1字节，覆盖B槽和协调页整个事务 |
| 请求触发的协调/Boot记录 | `OTA_CTL REQUEST/PREPARED/ACTIVATE/COMPLETE`等 → `save`或Boot日志 | 普通文本形式的OTA控制消息也必须纳入发送仲裁 |
| 新GR启动后的健康确认和结果持久化 | `yp001_ota_poll → yp001_ota_port_result → yp_boot_confirm`，然后`save(result)` | 属于GR主动写入，不能依赖“当前DATA尚未ACK”；需要显式取得CAT1静默确认再写 |

R4目标反汇编也存在`yp_boot_confirm`调用。因此此项会影响“GR装完后能否继续CAT1升级”，不是可推迟到以后的性能优化。

### 2.3 发送状态和业务队列不能用一个busy标志草率处理

当前源码确认：

- `ota_gr_transfer.lua`在**入队时**计`sent_at`并消耗帧尝试，尚无实际出队/发送完成通知。新增等待窗口后，排队延迟会被误算成应答超时，可能重复排入相同帧。
- `uart_app.lua`发布`OTA2_TX_FAILED`，当前`ota_runtime.lua`没有对应订阅。失败目前主要靠之后的超时显现。
- `ota_uart_cancel()`仅移除待发二进制，不区分“已交给UART的帧”和“仍在队列的帧”，也不处理待发OTA控制文本。
- legacy `dfu_transfer.lua`直接写UART1，不能让它越过新仲裁；GNSS的独立UART不应误受影响。
- legacy DFU还会注册UART1的`sent`回调；新增发送完成通知必须由统一入口分发，避免两个模块互相覆盖回调。匹配ACK可能先于任务消费`sent`事件到达，也必须保留，不能因此丢掉有效回复。
- 业务队列有64项/32768字节上限；满时返回失败，而`business_runtime.emit`没有处理这个返回值。延长静默窗口后，不能声称“入队就一定不会丢”。

这些是本次新增发送窗口必须一起处理的实现条件，不是要求重做网络下载器或所有业务状态机。

### 2.4 旧任务不是空任务，不能套用现有CANCEL_EMPTY

当前`yp001_ota_port_cancel_empty()`明确要求持久进度为0且B槽全FF。R4已有299008字节，正确行为就是拒绝该接口。

**换修复目标必须新增受限的安装前退役流程，不能删journal、改hash、清retry或伪造进度为0。** 新包和旧包哈希不同，旧299008字节不得作为新包已完成进度。重新传输新目标属于更新不同程序，不是重复验证旧下载通路。

### 2.5 现有修复与容量仍有明确边界

- 完成时间修复已存在于4个GR平台源码文件，并通过11组主机模型检查；本轮核对回调和恢复函数与当时测试输入一致，未重复跑这11组。**尚未Keil编译或部署。**
- 新的恢复记录由28字节变成36字节；下一版签名/读回工具必须从新AXF取地址和长度。现有`pair_gr_uart_recovery.py`仍检查28字节，不能原样用于新产物。
- `yp001_uart_clock_ms()`是10ms SysTick服务计数。全局关中断期间可能少计时，不能用它宣称物理100ms时限或测量Flash屏蔽时长；恢复完成判定与物理时序测量要分开。
- 第7次CAT1脚本实际占524269/524288字节，仅余19字节。新增协调逻辑必须先完成等价缩减和实际原生打包；不能先让用户刷半成品再发现放不下。不能靠删业务/安全功能、挪KV或改分区解决。

## 3. 最终推荐的技术方案

### 3.1 一套代码同时覆盖基线、目标和安装后的运行阶段

保留现有UART帧校验、512字节DATA、4096字节持久提交、签名、owner/epoch和安全门。主修复是“接收状态生命周期正确”和“Flash操作期间双方确认发送边界”，不通过抬高重试上限、放宽许可或简单加大超时掩盖问题。

1. **GR恢复：**采用已完成的abort开始/完成时刻修复；原始首错锁存不覆盖。abort返回后由前台重挂一次；失败闭锁。重挂成功只发起新hello，不直接设网络/许可为真。
2. **CAT1统一UART1写入口：**二进制、OTA_CTL、业务文本共享仲裁。引入待发、已交UART、等待回复三个明确状态；应答计时与尝试计数以实际发送事件为依据。部分写/失败进入明确传输错误，不能悄悄等到多次超时。
3. **请求型事务窗口：**正在处理的OTA请求完成前不追加后续业务或OTA字节。只接受完整校验且身份匹配的回复，旧ACK、错误sequence/offset、无关STATUS不能释放窗口。控制请求匹配job/hash/epoch/op及预期phase；需要新关联标识时只定义为内部UART合同，不能伪称后台已有该字段。
4. **GR主动写入窗口：**新增内部“请求静默→CAT1队列排空并发最后确认→GR执行单个有界写事务→完成释放”。确认必须关联本次会话和唯一token；GR收到确认前不开始写。健康确认、结果记录等主动写入也走此入口。不能在同步Flash包装里递归处理业务/协调器以等待确认，使用前台状态机延后该事务。
5. **超时和紧急业务：**等待静默期间发生SOS/来电/运动/SIM丢失，取消尚未开始的OTA写入，业务优先。已开始的单个Flash事务结束后立即释放并让出业务，不锁住整个镜像、120秒健康期或完整OTA。等待/发送/Flash完成分别有时限和故障记录；超时停止OTA，不自动清busy后继续发送。若写状态不明，先重新握手确认GR已退出Flash临界段，不能盲目向可能仍忙的GR灌数据。
6. **失链接续：**损坏字节和旧回复隔离；重新hello→双方实际业务状态→owner/epoch和许可确认→读取持久进度，才能接续。MQTT连接恢复本身不授予UART传输许可。

静默窗口必须有可验证的最大不可用时间。现有2秒帧应答超时不是“紧急业务可以被扣住2秒”的批准。实现时据实际驱动上限、分段写入和板上测量给出最坏窗口；超出业务要求就不得进入交付。计时使用经核对可跨IRQ屏蔽运行的计数来源，不能用本轮SysTick函数冒充物理时间。

本轮不选择提高UART优先级：PRIMASK会屏蔽它。不直接改BASEPRI策略或换DMA：Flash忙时ISR的XIP依赖、DMA短帧/低功耗和缓冲归属没有闭环，改这些会扩大修改面。

### 3.2 用新的修复包验收，旧R4保留为证据

**这是对上一版“R4目标不变、继续299008”的明确修订，待用户批准。** 原因是已核实旧目标带回缺陷，不是重新下载可以改善当前问题。

退役只允许：确切R4 job/hash/epoch匹配；GR仍DOWNLOADING；Boot没有PREPARED/INSTALL/TRIAL/交换或回退中的事务；没有已排定复位；两端没有原生安装提交。任一条件未知或不满足即拒绝。

事务顺序：

1. 在主机保存现有任务记录、候选身份、7次历史和持久进度证据；不读取或打印密钥。
2. CAT1先持久化“请求退役此确切旧任务”，停止它的新发送，不删除旧候选或历史。
3. GR在受控静默窗口将确切旧owner记为安装前终止；不擦B槽、不写用户区，不伪装安装成功。掉电后可查询同一终止结果。
4. CAT1收到并持久化匹配的终止凭证后，才允许新任务注册；旧发布的CAT1后续组件不得被自动接续。保留终止原因和已消耗次数。
5. 新包使用新job/hash，由GR授予新epoch；新GR接收进度从0开始，逐扇区验证后提交。已经退役的旧B槽候选只在新任务获得授权、实际写到相应扇区时被替换，不做全区预擦。

需要新增并验证以上流程；现有CANCEL_EMPTY保持原语义，不取消它的空槽保护。B槽所有权标志、Boot回退候选用途和旧/新owner切换必须纳入掉电矩阵。不能只复制一段CANCEL_EMPTY然后删掉durable检查。

最终仍以1.0.2→1.5.0作为首次真实版本升级；更换的是修复后的组件内容和签名哈希。若现有发布身份规则不允许同目标版本的未发布修订，先报告具体规则冲突，不擅自改设备版本或用同版本升级充当验收。
