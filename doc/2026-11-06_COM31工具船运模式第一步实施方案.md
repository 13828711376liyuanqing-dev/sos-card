## 目标和范围

通过 COM31 Nordic USB Dongle，在现有上位机输入船运相关串口命令，收到设备的结构化结果，并完成一次船运断电与插入 5V 恢复验证。其他电脑可选择实际分配的 Dongle COM 号，不依赖电脑内置蓝牙。

第一步仅接入船运命令及必要查询、授权和 CAT1 下电步骤。持续运行日志、任意 CLI、老化调度另行实施。界面保存 TX/RX、完整回应、状态变化和时间，明确这仍是通信及操作记录。

## 方案选择

| 路线 | 改动与代价 | 选择 |
|---|---|---|
| 复用现有 FT 船运协议，工具翻译串口命令 | 已有前台执行及船运控制器；主要补工具流程、回应解析和拒绝原因 | 推荐 |
| 新增通用 BLE CLI 与输出路由 | 可逐步覆盖 COM30，但涉及输出归属、权限和多命令调度 | 后续独立阶段 |
| 手动输入原始 FT 指令 | 可以发送，但需人工管理序号、token、准备时间和状态 | 保留用于诊断 |

## 工具的具体行为

新增“船运模式”操作区：状态查询、按键授权、CAT1 下电、准备、确认、准备取消。状态区显示当前阶段、拒绝原因、授权剩余时间及确认剩余时间。

命令框同时支持下列输入；工具明确打印转换后的 FT 原始帧，输入其他串口命令时提示当前未支持，不冒充透传成功。

| 用户输入 | 发送到设备（seq 由工具分配） |
|---|---|
| `charger ship status` | `FT SHIP_STATUS <seq>` |
| `charger ship prepare` | `FT SHIP_PREP <seq>` |
| `charger ship confirm <token>` | `FT SHIP_CONFIRM <seq> <token>` |
| `charger ship cancel` | `FT SHIP_CANCEL <seq>` |

授权、INFO 与 CAT1 下电使用已有 `FT UNLOCK <seq>`、`FT INFO <seq>`、`FT CAT_OFF <seq>`。手动 FT 输入与按钮共用单请求调度，避免交错；自动分配序号与手动输入的已用序号保持协调。

接收端按换行重组通知分片，严格匹配协议版本、连接会话、op 和 seq，再更新界面。收到写入完成仅显示“已发送”；收到 ok=1 后显示具体操作已受理，不等同物理断电成功。

## 实际操作流程

1. 确认 GR 正常运行、CAT1 实际启动，再开始本轮测试；随后主动执行 CAT1 下电属于本测试预期动作。手机退出连接，工具通过 Dongle 连接 YP001 并查询 INFO/船运状态。
2. 接好电池。单独按住左键，在工具点击授权；授权成功后松开左键。现有授权有效期为 60 秒，准备和确认时两键必须松开。
3. 工具下发 CAT1 下电，明确显示当前返回的 `rail_request_only` 只证明电源请求状态。核对模块实际下电、网络离线，不把 GPIO 状态当成物理供电测量。
4. 拔掉卡端 USB/外部 5V，电脑端 Dongle 保持连接。仅 USB、无电池时，拔线直接掉电，不能据此验证船运功能。
5. 点击准备，设备检查业务、OTA、CAT1、按键及充电芯片条件；工具轻量轮询状态。现有控制器持续检查至少 2 秒后给出 READY 与 token，token 有效期为 30 秒。
6. 用户点击确认或输入带 token 的确认命令，工具只发送一次。设备再次检查条件、消耗 token 并设置 BATFET 延迟关断。界面显示“已受理，预计约 12 秒关断，待实测”。
7. BLE 断开仅记录断开，不能判定船运成功；测量 SYS 电压及电池电流，并核对实际断电。插入 5V 后重新扫描连接，验证设备恢复和现有姓名等数据仍在。

## 已发现的代码限制与实施落点

- `ble_app_uart_c/Src/user/factory/yp001_factory_protocol.h` 已有上述操作白名单；`yp001_factory_ble.c` 已在前台执行，BLE 回调仅收包。继续沿用，不在回调执行业务、打印或调用 QP。
- `yp001_charger.c:ship_business_guard()` 要求 `!yp001_ota_port_provisioned()`、允许电源变更、无报警/找人/通话、网络链路未就绪、CAT1 电源请求关闭及双键释放。仅 OTA 当前空闲并不足以通过，已配置 OTA 的设备也会拒绝。
- 第一阶段保留这些条件。若当前板被“已配置 OTA”条件阻塞，记录为该板真实断电验收阻塞项；不清配置、不降级 OTA 限制。面向已配置产品的船运支持须另行审阅在线数据收尾与 OTA 事务策略。
- 现有 FT 船运回应仅含 state/token/attempted/delay_s，详细原因只在 UART。拟补充有界、无空格的原因码及必要条件状态，向后兼容保留现有字段，便于工具显示具体拒绝原因；不改变充电配置或船运资格。
- 现有状态值为 0=IDLE、1=CHECKING、2=READY、3=SENT、4=FAILED。SENT 表示寄存器操作已受理，FAILED 在写入不确定时也可能实际触发关断。
- 工具修改集中在 `tools/ble_console/nordic/com31_console.py`、`worker.js`、`protocol.js` 及配套测试/说明/安装版本。固件只补必要诊断，不增加通用串口桥或运行日志镜像。

## 失败和对现有功能的影响控制

- 超时、断线、确认回应丢失均不自动重发副作用命令。重新连接先查询状态；无法确认时显示“结果未知”，由实测和插入 5V 恢复消歧。
- token 与连接会话绑定使用，断线即清除工具中的 token。现有设备端 token 不宣称具备完整会话绑定或请求去重能力；工具不重放旧确认。
- 只允许在尚未尝试 BATFET 写入时取消；`attempted=1` 后禁止工具重试/取消，按插入 5V 恢复处理。
- 查询轮询保持低频，单请求串行；定位和 OTA 保持优先，可短暂中断维护连接。查询超时不重复启动准备/确认。
- 船运本身会有意终止定位、BLE 和系统供电；执行前保留 OTA 电源资格、报警和通话等拒绝条件。此次不修改 OTA 状态机、用户数据或电源参数。
- 原扫描回调固定队列修复保留，禁止重新在 SDK 回调调用 QP。不上报“零影响”，通过实板观察正常查询期间扫描及 OTA 拒绝路径。

## 交付与验收顺序

先完成协议解析、状态机界面和针对性的分片/错序/超时/旧 token/重复点击测试；完成拒绝原因码和原协议兼容性检查。用户在原主工程 F7 增量编译，保留缓存和已验证下载配置；按已授权的保护下载流程核对姓名、用户区和 NVDS。

实板先验证查询与条件不满足时拒绝，再在接电池、无外部 5V 条件下执行准备/确认，测量真实关断及 5V 恢复；没有实测前只标记工具通信或命令受理通过。供电状态和硬件 nQON 装配按当前板核对，不把历史装配记录当成本板证据。

最后更新完整安装包、快捷方式和使用说明。异机安装与对应 Dongle 收发须在其他电脑单独验收；本机打包成功不能替代。
