## 1 先看结论

**本轮只做一件事：兼容现有平台下发的 OTA 指令，接入已经调通的主动 OTA 链路，完成升级并把实际结果报回平台。平台基本不会为我们改，兼容工作在终端侧完成。**

不重新设计 OTA，不更换 GR Boot、Flash 布局、HTTP 下载器或 CAT1 原生安装方案。本轮不升级用户新提供的 V2055 底包，不修改充电参数，不清理用户数据。

目前实机已收到平台 OTA 指令，但在开始升级之前返回 **`HTTP_PORT_ERROR`**，仍为 **IDLE**。因此，本轮“平台下发→升级→结果回报”**尚未通过实板验收**。

## 3 平台和终端的职责

| 环节 | 平台负责 | 终端负责 |
|---|---|---|
| 连接 | 提供现有 MQTT 服务及设备下行通道 | CAT1 建立网络和 MQTT 连接，订阅本机下行主题 |
| 触发 | 自动、手工、单设备或批量任务均由平台选择 | 对收到的有效 otaMsg 走同一受理入口，不区分后台如何点击触发 |
| 文件 | 上传/保存升级包，生成下载地址和 MD5 | 按地址下载，校验整包和组件身份、签名、版本及空间 |
| 受理 | 接收 otaReplyMsg | 由 GR 编排，任务可靠保存后回接收结果 |
| 执行 | 不指定设备必须何时重启，不提供强制绕过安全条件 | CAT1 负责联网下载和传输；GR 负责安全判断、跨端编排和授权；两端严格串行 |
| 完成 | 接收、保存并展示结果 | 核实实际运行版本和健康状态，再发 otaResultMsg |

“单卡、手工下发”是平台操作方式，不是终端另起一种 OTA。终端不需要填写后台网站页面地址，连接参数和升级包下载地址是不同的东西。

### 4.2 六字段必填

| 字段 | 类型 | 必填 | 含义与检查 |
|---|---|---|---|
| MsgType | string | 是 | 必须为 otaMsg |
| CurrentVersion | string | 是 | 升级起点，归一后与实际版本、签名清单一致 |
| TargetVersion | string | 是 | 目标版本，归一后与签名清单一致，并高于起点 |
| Address | string | 是 | 实际升级包纯 HTTP 下载地址，不含聊天 Markdown 的方括号/圆括号包装 |
| Md5 | string | 是 | 实际整包的 32 位十六进制 MD5，不是随意填写，也不是组件单独的 MD5 |
| Time | long | 是 | Unix 秒级时间戳，发送时由平台提供真实时间 |

**四字段 JSON 示例漏了 CurrentVersion、TargetVersion，与参数表不一致。本轮按用户补充后确认的六字段执行，不从文件名或包内信息自动补缺失字段。**

### 4.3 已观察到的平台版本格式

| 平台实际值 | 终端归一值 |
|---|---|
| CurrentVersion = YP001_1.5.10 | 1.5.10 |

终端兼容这两种已观察到的、角色对应的完整装饰格式。标准版本号也照常接受。不是任意删字符串：未知前后缀、重复装饰、版本夹杂 ZIP 扩展名等仍拒绝。

归一只为接入平台格式，不能取消实际版本和签名清单校验；原始消息不被修改。Address、Md5、Time 继续走原检查。

## 5 两类回执的要求

| 消息 | 必要字段 | 什么时候发 | 不能误解为 |
|---|---|---|---|
| otaReplyMsg | MsgType、otaReply=success/fail、Time | 收到有效任务并完成可靠保存，或拒绝指令时按既有协议回报 | 下载完成或安装成功 |
| otaResultMsg | MsgType、Status=success/fail、Version、Time | 完成安装、重启和本地确认后；失败则报告实际结果 | 把目标版本直接当作实际版本填上去 |

上行主题为 `/iotplat/datapush3/notsos/WARNCARD3/{deviceid}`。

OTA 回执/结果不额外等待平台应用层确认；MQTT QoS/PUBACK 和断线补报仍需正确处理。协议中把接收回执示例的 MsgType 误写为 periodicMsg 的内容，不作为生成依据。

## 6 设备执行和安全要求

1. **先确认 GR 正常运行，再确认 CAT1 已实际启动。** GPIO、上电 ACK 或串口发送成功不能替代 CAT1 启动日志/版本回应。
2. 平台回调只负责接收和派发。可能执行 HTTP 等待的受理逻辑进入任务，调用现有 OTA 实例；同一时刻最多一条受理任务，避免重复下发创建无界任务。
3. 平台受理开始即使用现有 CAT1 保电机制，后续按既有信标续锁与释放；不能只靠“发过上电命令”宣称锁电成功。
4. GR 与 CAT1 的下载、传输、安装、确认严格串行，不能一边升级 GR 一边预下载 CAT1。
5. 下载支持 HTTP Range 续传；运动、报警、通话等高优先级事件应按原设计暂停/让出。不能把重新从零下载写成断点续传通过。
6. 提交安装前必须重新确认：稳定静止、正在充电、电量至少 70%、无报警，且无通话/用户活动冲突。无 Force，不允许平台降低 70% 门槛。
7. GR 使用既有 A/B 与 Boot 试运行/确认/回退；CAT1 使用既有厂商常规 FOTA。不能把 CAT1 说成自建 A/B 回滚。
8. 升级、失败恢复和回退都不清空用户数据，不格式化 FS/KV/NVDS，不恢复旧快照覆盖用户最新合法配置。
9. 失败按既有限次重试/退避和坏包限制处理，不为方便重测删除事务、改票或强行断电。

上述是要求，不代表本轮全部实板验证完毕。当前 GR 仍启用 USB 台架宏，因此本轮可验证平台接入链路，不能据此宣称量产充电门槛等全部通过。
