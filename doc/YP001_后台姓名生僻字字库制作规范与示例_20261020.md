# YP001 后台姓名生僻字字库制作规范与示例

- 日期：2026-10-20（北京时间）
- 适用对象：后台平台、字库服务、字体资源制作方，以及 GR5526/LVGL 联调人员。
- 目的：规定姓名里本地字体缺失的字符，从字体选择/描字到输出设备可用字形数据的制作流程。
- 状态：**后台接口字段、最终字号、字库容量上限和设备存储位置尚待双方确认。本文为接口评审用的候选制作规范，不等同于已冻结的线上协议或已实现功能。**

## 1. 结论和推荐规模

不建议一开始生成并下发“全汉字大字库”。本项目只需为居民姓名中本地字体没有的字符补字，推荐采用：

> **后台保留可生成字形的字体资源；设备端按缺字请求，接收缺失字符的 1-bit 点阵字形；GR5526 校验并缓存，后续离线复用。**

建议先以**24×24 像素、1 bit/像素**作为首轮原型规格。24×24 单字点阵为 72 字节；10,000 个字符点阵约 703 KiB（不含索引、度量、协议和存储开销）。如果客户要求姓名字号为 32 px，则改为 32×32，每字 128 字节，10,000 字约 1.22 MiB。全汉字集合实际字数须按所选字符集统计，且不包含索引、字形头、字体授权费用或闪存文件系统开销。

本项目现有 GUI 中有 24 px 中文字体源，且使用 LVGL 8.3.1；这只是选择 24 px 做首轮验证的依据，不代表客户主屏最终姓名字号已冻结。后续定版要以姓名标签实际字号及 DEPG0150 实板可读性为准。

## 2. 两种建库模式

| 模式 | 后台准备什么 | 网络下发什么 | 适用场景 | 建议 |
|---|---|---|---|---|
| A. 按需缺字包 | 有授权的字体文件/字形生成器、版本信息、字符映射索引 | 仅下发该设备姓名所缺的单字字形及度量 | 姓名字符集合不可预知、罕见字少、流量/Flash有限 | **推荐** |
| B. 固定字符集完整字库 | 选定字符集全部字形、索引及发布版本 | 首次批量下发完整字库或固件预置 | 业务字符集合明确且容量、下载流量已验证 | 暂不推荐，需先做容量核算 |

“后台建一个几万字的大库”可作为后台生成资源库，不表示把整库灌入每台设备。若设备只显示姓名，按需字形可以将每台设备实际缓存控制在姓名所需字符数附近。

## 3. 从选字体到生成单字数据的制作流程

### 3.1 确定使用场景和字形规格

字库制作方开始描字前，先与产品/固件方确认：

1. 显示用途只包含姓名，还是包括房号/其他中文信息。
2. 实际字号（建议先验证 24 px；若版面或可读性不满足，再评估 28/32 px）。同一姓名显示链路尽量只选一种动态字号，减少设备缓存种类。
3. 目标屏幕为 200×200 黑白电子纸；目标点阵为 1 bit/像素，黑/白极性和位序必须在样例中明确。
4. 字符编码统一使用 Unicode 码点，接口文本使用 UTF-8；禁止用字形序号或本地代码页作为跨端身份。
5. 需要支持的字形是简体/繁体、异体字/Unicode 变体序列还是仅单一规范码点。异体字可能是多个 Unicode 标量组成的序列，必须明确处理策略。

### 3.2 选择字体来源

- 选择支持目标字符的字体文件；制作方应确认字体覆盖目标码点。
- 留存字体名称、版本、文件 SHA-256、授权/嵌入/转换/下发许可证明。
- 建议后台使用同一套固定字体及固定渲染参数，避免不同服务器或升级后同一字符字形变化。
- 如采用人工描字，应保留原始矢量/点阵文件、描字人员/版本、审校记录；单字应由中文审核人员核对结构和笔画，不可只依赖自动找形。
- 不得将字体文件本身未经许可直接下载到设备；本规范传输目标是经过授权生成的单字点阵及必要度量。

### 3.3 按码点取字并栅格化

对每一个缺失 Unicode 字符，后台生成以下固定规格字形：

- 字符身份：Unicode 码点，例如 `U+9FA5`；同时提供 UTF-8 字节仅用于诊断/联调，设备查找以码点为准。
- 栅格化画布：首选 24×24 或冻结后的字号方框；若字体字面框不足全框，记录有效字面宽高与偏移。
- 像素：1 bit，建议 `1=黑色前景、0=白色背景`；该约定必须与固件解码一致。
- 行存储：每行单独向上补齐到整字节，24 像素宽一行 3 字节，32 像素宽一行 4 字节；每行末尾填充位写 0。
- 扫描次序：从左上角开始，按行从左至右、从上至下；每字节位序统一规定为 MSB first（bit7 对应最左像素）。
- 度量信息：`box_w`、`box_h`、水平前进宽度 `advance`、水平偏移 `ofs_x`、相对基线垂直偏移 `ofs_y`、字体 `line_height` 和 `base_line`。
- 不允许抗锯齿灰度直接混入 1-bit 数据；如源字体抗锯齿，必须用固定阈值二值化，并由实屏确认笔画没有断裂或粘连。

字形栅格可从授权字体自动光栅化产生；如果具体偏僻字缺字体轮廓而需要人工描字，按目标像素网格逐格绘制，再走同样的审核、打包和校验流程。后台不得只提交 PNG 截图，因为设备需要可验证、可索引的规范点阵数据。

### 3.4 生成清单、版本和校验

每批字形应生成机器可读清单，至少记录：

| 字段 | 说明 |
|---|---|
| `format_version` | 字形二进制格式版本；格式变化必须递增 |
| `font_id` / `font_version` | 字体系列和固定版本 |
| `glyph_id` | Unicode 码点；若支持变体序列，另定序列键格式 |
| `pixel_size` | 名义字号，例如 24 |
| `bpp` | 位深，首版固定 1 |
| `box_w` / `box_h` | 有效字面框像素尺寸 |
| `row_bytes` | 每行实际字节数，必须等于 `(box_w + 7) / 8` 向下取整 |
| `advance` / `ofs_x` / `ofs_y` | 排版度量，单位为像素或统一定点单位；协议必须固定一种 |
| `bitmap_length` | 点阵字节数，必须等于 `row_bytes × box_h` |
| `bitmap_sha256` | 单字点阵摘要，用于内容身份/制作校验 |
| `bundle_length` / `bundle_sha256` | 批次总长度及摘要，接收端完成后校验 |

`SHA-256` 用于完整性和版本比对，不是身份认证或防伪签名。若需防止伪造更新，应另由正式安全方案定义签名/鉴权，不能把摘要当作签名。

### 3.5 导出设备字形包

候选字形包按以下逻辑顺序组成，具体 JSON/二进制线上封装须由后台与固件双方冻结：

```text
文件头（格式版本、字体版本、字形数量、总长度）
字形目录（码点、度量、每字偏移、每字长度、单字校验）
点阵数据区（按目录顺序连续存放）
批次校验摘要/签名（如安全协议要求）
```

传输层再切成有界 UART 数据帧，包含事务 ID、包序号、总包数/总长度、帧校验和确认语义。字库制作工具生成的文件包不得自行等同 CAT1-UART 帧协议；协议由两端联调定版。

## 4. 点阵容量怎么计算

对于方形、1-bit、按行字节对齐的位图：

```text
row_bytes = ceil(width_px / 8)
bitmap_bytes_per_glyph = row_bytes × height_px
raw_font_bytes = bitmap_bytes_per_glyph × glyph_count
device_cache_bytes = raw_font_bytes + glyph_index + glyph_metrics + version/header + alignment/atomic-update reserve
```

常见规格的位图本体如下（不包含目录、协议和文件系统开销）：

| 字号/画布 | 每行字节 | 每字点阵 | 1,000 字点阵 | 10,000 字点阵 |
|---|---:|---:|---:|---:|
| 24×24，1 bpp | 3 | 72 B | 70.3 KiB | 703.1 KiB |
| 28×28，1 bpp | 4 | 112 B | 109.4 KiB | 1.07 MiB |
| 32×32，1 bpp | 4 | 128 B | 125 KiB | 1.22 MiB |
| 40×40，1 bpp | 5 | 200 B | 195.3 KiB | 1.91 MiB |

容量例子：假设一台设备最多缓存 100 个 24×24 缺字，点阵本体为 `100 × 72 = 7,200 B`（约 7.03 KiB），另加目录/版本和安全切换空间。若按 10,000 个 24×24 常用汉字预建整库，光点阵约 703 KiB；这还未计算双份原子更新、Flash 擦除粒度和文件系统管理开销。设备可用空间尚未完成审计，因此**100 字仅为容量计算示例，不是承诺上限**。

姓名的字符大多使用本地字体。后台可以持有更大的候选资源库，但每台设备只下载当前姓名缺失字符及其必要版本，避免把 10,000 字包强制放进设备。

## 5. 单字示例：`𠮷`（U+20BB7）

以下是假定 24×24、1 bpp 的示意流程。**点阵数据为说明格式的虚构示例，不代表 `𠮷` 的正确字形**；正式文件必须由目标字体/人工校对产生。

1. 后台收到姓名 UTF-8 字符串，解码出 `U+20BB7`。
2. 查询设备声明的本地字体版本/缺字清单，确认本地未覆盖 `U+20BB7`。
3. 使用授权字体与固定渲染配置把该码点栅格为 24×24；人工校对其部件和笔画。
4. 导出 24 行，每行 3 字节，点阵长度为 `24 × 3 = 72` 字节。
5. 填写度量，如 `box_w=24`、`box_h=24`、`advance=24`、`ofs_x=0`、`ofs_y=0`（这些是占位示例，实际值以统一基线规则生成）。
6. 对 72 字节计算 SHA-256，生成字形目录条目并进入字形包。
7. 后台服务将包经 CAT1 分帧传给 GR5526；GR 校验、暂存并提交后，姓名显示层以 `U+20BB7` 查到该字形。
8. 在实板确认字形方向、黑白极性、行位序、垂直位置、笔画清晰度和电子纸刷新结果；断电重启后再次确认缓存生效。

## 6. 推荐数据库/资源库组织

后台可按以下概念组织资源（实现上可用数据库表、对象存储加索引或版本化文件仓库）：

| 逻辑实体 | 建议主键/索引 | 存储内容 |
|---|---|---|
| 字体版本 | `font_id + font_version + size + bpp` | 字体来源摘要、授权信息、渲染参数、状态 |
| 字形 | `font_version + Unicode codepoint + variation_selector + size` | 点阵、度量、单字摘要、人工审核状态 |
| 发布包 | `bundle_id + format_version` | 字形目录、内容摘要、创建时间、测试状态 |
| 设备缺字任务 | 设备/绑定标识 + 姓名数据版本 + 缺字集合摘要 | 请求状态、成功/失败、重试次数；避免日志记录不必要的完整姓名 |

同一字体版本和码点对应的结果应可复现；修改字体或渲染参数必须生成新字体版本，不能原地替换旧点阵而不改变版本号。

## 7. 质量检查和交付物

字库制作方每次交付应包含：

1. 字体来源/授权和字体文件摘要（不一定向设备发布字体原文件）。
2. 字形格式说明和版本号，含位序、行序、极性、尺寸、度量单位。
3. 字形清单：码点、字号、有效尺寸、字节数、校验摘要、审核状态。
4. 原始矢量/描字源文件及生成工具版本，便于复现。
5. 可视化校样图：正常比例、放大网格图及本地字体对照图；人工核对字形正确性。
6. 机器可读设备字形包及包级清单/摘要。
7. 至少一份包含本地已有字、本地缺失字、混排姓名的回归样例；不在生产日志中暴露真实居民数据。
8. 生成和验证日志，明确失败/缺字/字体回退情况。

自动验收应至少检查：码点合法且无重复冲突、尺寸在固件规定范围内、`row_bytes`/长度公式正确、填充位符合规范、摘要正确、目录偏移未越界、总包大小不超限制。实板验收另检查结构正确、位置/大小、屏幕可读性、下载后重启可显示和下载期间业务不被阻塞。

## 8. 尚须共同冻结的参数

以下项目是正式开发前置条件，本文不擅自定义为线上定稿：

- 姓名及房号的后台消息字段和版本语义（需求冲突 C-06 尚未解决）。
- 姓名字号和布局宽度；24 px 仅是首轮候选规格。
- 固定字符集全库的字符范围，或按需缺字接口的请求/应答格式。
- 最大姓名长度、单次最大缺字数、单包/单事务最大字节数和超时重试策略。
- 字形度量基线、是否固定等宽 advance、异体字序列处理方法。
- 设备缓存总量、替换/清理规则、Flash 分区/存储位置及原子更新策略。
- 缺字未返回/下载失败/字形审核失败时的用户可见回退方式。
- 字体授权、服务鉴权、传输安全及后台数据保留策略。

## 9. 验收步骤建议

1. 后台制作者用授权字体生成一个本地已有汉字和一个代表性偏僻字的样例包。
2. 主机工具解包并核对码点、每行位序、点阵尺寸、度量、长度与 SHA-256。
3. GR5526 测试桩接收一个字形，验证拒绝错误码点、超长数据和错误摘要；合法数据写入后掉电/重启仍保留。
4. LVGL 将本地字与动态字形混排显示；确认相同姓名不需每次联网取字。
5. 接上后台和 CAT1，测丢包、乱序、重复包、超时、断网、断电和重试，确保旧缓存原子保留。
6. 在主工程及交付副本分别编译，再做实际 DEPG0150 显示验收；构建、串口成功、电子纸 BUSY 结束均不能单独替代显示验收。

## 10. 本轮评估边界

本文件为后台字库制作与交付规范草案，仅新增文档，没有修改固件、CAT1代码、正式平台协议或 Flash 布局。24×24、1 bpp 及容量例子用于原型评审；最终参数须由客户/后台、固件和屏显实测共同冻结。当前尚无后台产物、协议联调、设备持久化或实板字体显示验收证据。
