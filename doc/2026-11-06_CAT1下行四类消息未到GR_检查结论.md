# CAT1 四类平台下行到 GR 的路由检查

SAM | 2026-11-06 +08:00 | 按用户截图检查；“蓝牙端”按 GR5526 固件端理解，经 CAT1 UART 转交，不是 PC 的 GUS 调试工具。本轮只读核对和离线复现，未改固件源码、打包、烧录或收发真实平台消息。

## 结论

确实存在原始业务下行无法到 GR 原处理器的问题，但不能直接删除 `return true` 或入口的 `then return end`。本地已处理、允许转发、拒绝非法消息目前共用一个布尔返回值，导致不同职责混在一起；同时 UART 订阅者还单独屏蔽了客户下行 topic。

## 实际链路

1. `Air780EGH/mqtts_receiver.lua:205`：runtime 返回 true 后，既不发布 RECV_DATA_FROM_SERVER，也不进入旧 mqtts_receiver_test。
2. `Air780EGH/business_runtime.lua:121`：核对本机精确 topic；phoneBindMsg 的原始 JSON 数组校验失败也返回 true，表示拒绝后消费，不能改成 false 让非法包流入旧处理器。
3. `Air780EGH/business_core.lua:294`：四类类型均返回 true，但实际动作不同，见下表。
4. `Air780EGH/uart_app.lua:245`：即使放开前面的短路，客户 `/iotplat/render3/WARNCARD3/` topic 仍被拒绝，无法进入 uart_async_push。
5. GR UART 按 OTA/BUS_EVT/旧文本分流；旧 MQTTS_EVT 路径还取决于 FEATURE_USE_CAT1_SVC。应核对实际构建，不从源码存在推断实机一定运行该路径。

| MsgType | CAT1 当前动作 | GR 当前情况 / 风险 |
|---|---|---|
| phoneBindMsg | 校验、保存呼入/呼出绑定，维护持久化 phoneBindReplyMsg 回包 | 原始消息没进入 GR 绑定处理器；直接放开还会执行旧 CAT1 回包代码，造成重复/错误回包 |
| paraSetMsg | 只发 PARAMETERS_NOT_READY 通知即返回 true | GR 参数解析与配置回复没有被这条原始消息触发，属于被占位逻辑吞掉 |
| personSearchMsg | 只发 SEARCH_ACK_UNDEFINED 通知即返回 true | GR 找人状态机未收到这条原始消息；不能把“通知已发”算作找人已处理 |
| sosReplyMsg | 校验成功状态、活动报警及时间，持久化 alarm_acked，再发 BUS_EVT alarm_ack | 原始消息未转发，但有效 ACK 已经有另一条到 GR 的路径；GR business 入口当前只打印 ALARM ACKNOWLEDGED，与旧 MQTTS_EVT 投递 SOS_REPLY_SIG 是两种处理，不能描述为完全没有任何 GR 通知 |

## 为什么不能直接去掉

- 对 phoneBindMsg，旧 `mqtts_receiver_test()` 会另发一份 phoneBindReplyMsg，且把 CmdType 写死为 0、Result 写死为 true；可能与新逻辑的解绑/校验结果相反。
- 对 sosReplyMsg，若直接让原始 success ACK 进入旧 GR 处理器，会绕过 CAT1 当前的活动报警与时间关联校验；原始 ACK 和 BUS_EVT 还可能形成两个事件入口。ACK 不能被当成取消报警。
- 对 paraSetMsg/personSearchMsg，改返回值也绕不过 UART 端的 topic 拒绝。
- GR 旧绑定解析也有独立缺陷：CallInList 用 cJSON_IsString 判断，随后却当数组遍历；复制取的是父对象的 valuestring 而不是数组元素，且解绑未明确清除旧值。仅恢复传输不能保证绑定功能正确。
- GR 文本行上限为 YP001_OTA_FRAME_MAX=1024，CAT1 UART 可接受一条 4096 字节；大参数包不能直接透传后截断。旧 GR JSON 处理还在校验 MsgType 类型前解引用，需要随新入口一并核对。

## 推荐落地方式

将 downlink 结果改成明确的路由决定：本地消费、转 GR、本地状态同步并转 GR、拒绝。把“识别/受理”“允许转发”“处理成功”分开，禁止用一个 true 表示全部结果。

- paraSetMsg/personSearchMsg：去掉 CAT1 占位消费，由一个明确、经过字段与长度校验的 GR 下行入口接收并处理；回复沿现有业务协议，不新增未冻结的平台 ACK 字段。
- phoneBindMsg：第一步保留 CAT1 已有持久化、实际呼叫白名单与唯一平台回包；给 GR 同步已验证绑定，修复 GR 数组/解绑解析。同步不得再执行旧 CAT1 回包函数。若要改成 GR 唯一绑定持久化与回包 owner，应作为独立迁移，不能顺手删掉现有 CAT1 状态。
- sosReplyMsg：保留 CAT1 的校验、持久 ACK 与重启恢复能力；把经过关联校验的 ACK 明确交给 GR 所需的业务事件处理。优先复用已有 alarm_ack 通道，核对 GR 后续动作，而不是重新放入未经关联校验的原始 success 分支；不结束持续报警，不重拨。
- 原始 MsgType 若必须在 GR 保留，使用一个白名单明确、带关联信息的专用下行入口；可以兼容旧 MQTTS_EVT 的业务解析语义，但不要整体解除当前通用 topic 拦截，也不让四类消息再落入 mqtts_receiver_test。
- 所有转发复用现有统一 UART 队列及 OTA writer/window；队列拒绝要保留待发状态并报告失败，不把入队当 GR 执行成功。长包明确拒绝或增加分片重组，不能静默截断。

对应需求：F-019（参数/绑定）、F-018/F-033（找人及 ACK）、F-002/F-033（报警 ACK 不取消报警），并保留 U-OTA-01/U-DATA-01。

## 离线复现

用实际 mqtts_receiver.lua 与 business_core.lua，模拟 runtime 的 topic 适配及平台/UART依赖：四类输入均被 core 消费，未发布旧 RECV_DATA_FROM_SERVER。模拟仅取消短路后，phoneBindMsg 确实触发额外旧回包；执行实际 uart_app 的订阅函数，客户下行 topic 仍未调用 UART 入队。

这些是主机复现与源码证据，不是实机 MQTT→UART→GR 已通过。完整闭环还需验证绑定/解绑只回一次、参数查询/设置、找人只触发一次、有效/陈旧 SOS ACK、队列压力、长包，以及 OTA 期间业务通道仲裁。
