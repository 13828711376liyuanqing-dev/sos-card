# GR5526 OTA 中运动与业务事件的处理建议

SAM | 2026-10-28 +08:00 | 源码与现场证据分析；尚未修改固件、下载或执行新 OTA。

## 原厂示例明确内容

- 当前唯一 SDK 为项目 `SDK`，基于 GR5526 SDK 1.0.4。`SDK/projects/ble/dfu/app_bootloader/Src/user/main.c` 顺序调用 bootloader DFU、校验、跳转任务，再在循环中处理调度/超时；这些名称本身不能证明本项目的 A/B 回滚细节。
- `SDK/projects/ble/dfu/dfu_master/Src/platform/user_dfu_master.c` 的事件处理区分升级开始、Flash 进度、升级结束、擦除，以及 ACK 超时与编程失败；超时和失败会重置 DFU 解析状态。示例没有定义本产品的运动、SOS、充电规则，不能说原厂要求忽略这些数据。
- 本项目采用自己的 GR Boot 事务：`ble_app_uart_c/Src/user/ota/yp001_ota_boot.c` 中 prepare 与 activate 分离，activate 后进入 `YP_BOOT_INSTALL`；resume 负责 INSTALL/ROLLBACK，之后才进入 TRIAL/REVERTED。这是项目实现，不冒充 SDK 示例。

## 当前卡点

- 实板逻辑采样中，R6 身份匹配的 QUERY/STATUS 形成双向通信，GR 返回 `INSTALL_PENDING`、`commit_safe=false`。后续只读 RAM 快照显示静止计时多次短于 60 秒，且运动标志为 1 时重置；Z 轴两次可见变化 69/77 mg 超过 50 mg 阈值。不能确定是物理运动、噪声或采样间隔，也不能将之后的快照当作同一时刻的逻辑仪记录。
- `OTA_INSTALL_PENDING` 不等于 Boot 已进入 `YP_BOOT_INSTALL`；它可能只是待提交意图。当前 `safe(true)`、`safe(false)` 在多个时段重复检查，`advance_quiet` 的健康观察也以 `safe(false)` 为条件；是否导致具体已提交事务无法结束，需要用实际持久 Boot 状态与调用链逐项证明。
- 昨晚 `INSTALL_RECOVERY_QUERY_FAILED` 是发送拒绝分支未留痕，不能用这次静止门状态解释历史查询失败。

## 建议的按阶段策略

1. 接受任务和下载：校验包和身份，后台事件不清任务、不清候选。单次运动样本不消耗安装票据；传输应有持久进度及有界通信恢复。报警/通话事件进入业务待处理队列，不在 Flash 临界操作中交错写入。
2. 台架明确授权进入本次安装：用户已要求 USB 供电并希望进入 OTA 后不被运动数据反复打断。这与旧产品要求 F-031 的稳定静止/报警门存在冲突；必须将台架策略与正式产品策略明确区分，不能把测试策略默认为产品策略。不得伪造充电、运动或传感器读数。
3. 确认签名、目标、owner/epoch、完整候选与供电后，在不可逆提交前持久化一次事务；具体哪些业务事件可以延后、紧急事件如何处理应按用户最新要求和产品实际用途明确。通信错误、校验失败、存储错误及设备断电仍需停止或恢复，不能静默忽略。
4. 只有真实 Boot 已持久进入 INSTALL/ROLLBACK 后才按已提交事务接续或回退；运动、普通状态/网络更新不应反复撤销该事务。恢复不代表新的安装机会，原 SPENT 历史不能清除。
5. 启动后核实真实运行镜像、版本、业务健康和可读取数据；确认/回滚遵循 Boot 状态机，两个目标严格串行并先持久化结果再上报。

## 落地顺序与验证

- 先只读确认当前 R6 的 Boot 持久状态、GR 进度与 owner，不能根据 `INSTALL_PENDING` 猜测已提交。
- 对照 GR/CAT1/Boot 的状态转移和每次 `safe()` 调用，定位真正导致已提交事务被运动或网络打断的位置，先做有故障对照的主机验证，再修改唯一活动主工程。保留 Keil Objects 并由用户按原工程 F7 增量编译；Boot 有源码变化才重编。
- 在样机或获准范围验证：一次授权、运动/噪声、通信中断、关键 Flash 阶段断电恢复、不丢用户数据；不能以主机或编译结果替代实板。
- 这不授权增加新的 R6 安装机会；过去 SPENT 的票据与用户数据保留。

## 2026-10-28 当前 Boot 与 GR owner 实读

- J-Link 仅读取 `0x2F7000–0x2F8FFF` Boot 双日志及 `0x2F9000–0x2FAFFF` owner 双日志；没有 halt、reset、写 Flash 或写 RAM。结束 DHCSR `0x01010001`，S_HALT=0。
- 按现有工程 layout、magic、CRC 和提交字校验，Boot 两页有效，最新 generation=3，状态 `PREPARED`、index=0、stage=0、attempts=0。故当前并未持久提交为 `INSTALL`。
- owner 最新有效 generation=192，epoch=4，phase=3 (`INSTALL_PENDING`)，R6 job/hash 匹配，持久进度 432328/432328。`INSTALL_PENDING` 与 Boot `INSTALL` 是不同状态。
- 当前重复运动门主要拦在 `safe(true)` 的查询提示、激活前判断和最终提交；GR Boot `yp_boot_resume` 在已持久 INSTALL/ROLLBACK 时按日志完成扇区交换，不引用业务运动输入。GR `advance_quiet` 在安装结果观察路径仍有 `safe(false)` 门，这可能影响结果处理，但尚未通过已提交实板事务证明发生。
- CAT1 runtime 在 SIM/IP/业务忙事件会执行 `pause`，清除临时授权并暂停传输；该路径与 Boot 已提交后的恢复不是同一逻辑。是否发生已提交后被阻断，要以对应状态和对照测试确认，不能只因为存在 `pause` 就下结论。
- 用户希望受控 OTA 后不受普通运动等数据反复打断；这与旧 F-031 产品要求存在明确差异。应以用户当前台架要求制定隔离策略，但不得将当前 `PREPARED` 误当已提交、抹去 SPENT 历史或把测试策略默认为产品策略。

## 已提交后仍受业务条件影响的明确代码路径

- GR `advance_quiet` 仅在 `safe(false)` 为真时调用 `yp001_ota_port_result_pending`。即使 Boot 已进入 TRIAL/CONFIRMED/REVERTED，活动、报警、呼叫或对端状态不满足时，结果观察路径也会暂缓；这是代码事实，本次 Boot 仍是 PREPARED，尚无已提交实板验证。
- 在 Boot TRIAL 的 `health_observe` 中，`inputs.activity`、报警、呼叫、网络/链路未知会清 `health_started`；观察间隔超过 3 秒也会重新开始连续 120 秒。因而连续运动或反复短间隔事件可能让确认持续等待。这与用户希望受控 OTA 后普通数据不反复中断的台架策略不一致。
- Boot `yp_boot_resume` 本身不依赖上述业务输入，但启动健康确认及结果持久化仍由应用状态机管理。不能仅移除外层 safe 而保留内层重置逻辑，也不能因此删除签名、真实版本、事务一致性、回退及用户数据校验。
- 本轮仅记录代码路径；未更改安全门、未发送 ACTIVATE、未重试 OTA。

## 进一步的完整链路拆解

1. **提交之前**：GR `safe(true)` 将运动、按键、业务、对端状态与充电/USB、电量绑定；CAT `fresh_safety()` 同时要求业务空闲、3 秒内身份匹配的 GR 提示。台架策略若只放宽 GR 运动门，CAT 的 `business_idle`、GR 的 `quiet_safe` 及复验路径仍可能拒绝，不能只改一个条件并称链路闭合。
2. **真正提交**：`yp_boot_activate()` 将 Boot 日志持久为 `YP_BOOT_INSTALL`；当前实读是 PREPARED，不能把 coordinator 的 INSTALL_PENDING 当作已提交。提交前仍应保持固件身份、签名、布局/数据兼容、事务幂等与真实供电约束。
3. **Boot 断电恢复**：`yp_boot_select_start()` 对 INSTALL/ROLLBACK 调用 `yp_boot_resume()`；Boot 扇区交换过程不直接依赖运动/MQTT。它仍要求签名与存储成功，不能将读写错误忽略为普通业务数据。
4. **TRIAL 确认**：外层 `advance_quiet` 的 `safe(false)` 可阻止开始观察，内层 `health_observe` 还会因 `inputs.activity`、报警、呼叫、MQTT/链路失效或观察中断重置 120 秒。如果只移除外层门，内层仍可无限延期；重复开机可能触发 Boot 限次回滚。此为确定源码逻辑，不是本次已发生的实板后果。
5. **CAT1 后续阶段**：GR 完成后 CAT1 的 native 安装与重启走单独授权；runtime 的 `business_idle`、`paused` 和 GR 重启许可仍参与其状态，不能仅改 GR 就假设双端 OTA 闭环。厂商 FOTA 激活和重启/断电边界仍须按当前底包实测。

台架建议将普通运动/普通业务状态从已授权事务的传输及 TRIAL 确认门中解耦；保留本次执行的独立授权、身份与签名、真实供电、Flash 完整性、Boot 恢复和最终真实版本/数据核验。业务紧急事件的实际服务保证和正式产品是否允许该策略仍需单独确认，不能把忽略事件理解成已处理事件。当前并未实现这一策略，也没有新安装机会。
