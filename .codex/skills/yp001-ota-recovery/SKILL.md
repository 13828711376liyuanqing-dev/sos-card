## 先回答现在实际发生了什么

用最少必要证据确定：

1. GR是否实际运行、实际版本/build；CAT1是否有本轮真实启动/版本/信标，而非GPIO或VTref。
2. Boot状态；owner的job/hash/epoch/target/source/target、phase、total/durable、CRC/commit及合法最新代。
3. CAT1 manager/native状态、io2归属、试装票、结果队列；当前接收端属于维护还是正常。
4. 实际构建与实际刷入的指纹，是否只是同名或改名；网络到底到达哪一阶段。

只有新证据、阶段变化或新代码需要时才重复检查；复用已有有效日志，不为写报告重跑实板。

## 几个必须分开的判读

| 现象 | 正确分流 |
|---|---|
| `activation_validation_failed`且新GR未运行 | 查预校验是否执行、入口门控、收据和准确首错；不能直接认定HTTP或签名坏 |
| 新GR已运行，重复ACTIVATE报stage11 | 核对同owner、Boot TRIAL/CONFIRMED及old/new版本；已存在源码/主机修复，但已验收b18仍是原程序。先绑定实际镜像判断，不能清票重来或泛化忽略验证失败；修复细节见[专项记录](D:/CODEX/sos-card/doc/2026-11-07_GR安装后重复ACTIVATE误报修复.md) |
| `G0`但有DATA记录 | 单个记录只证明曾发生传输；核对同任务至少两个有时间顺序的有效样本，offset递增才支持仍在推进。查PSRAM accepted与durable区别 |
| io2存在 | 先匹配当前job.id。其他任务合法历史不等于当前正在安装，仍须真实manager/native验证 |
| `AUTO_FAULT`或旧快照08 | 重新看当前状态读取的FAULT_NOW、VIN/PG/THERM/POWER，历史与当前分开 |
| IDLE/outbox0 | 支持设备侧收尾；不能单独证明平台页面或应用层结果已收到 |
| 接收端改文件名 | 比实际LuaDB成员、成功烧写和真实启动；字节相同无需因改名重刷 |
