## 1. 同事先看这几条

1. 当前可以通过串口命令进入有门禁的深睡测试；唤醒后整机重新启动，UART打印BOOT。
2. 主入口为bsp.c的cmd_sleep_test()；真实执行点为QV_onIdle()内的pwr_mgmt_ultra_sleep()，中间必须完成sleep_test_prepare()。
3. 当前没有公开的sleep_enter()业务API，cmd_sleep_test和prepare/finish均为static内部函数。其他模块不要直接调用SDK接口或直接修改s_sleep_test。
4. 活动SDK只用根目录SDK（1.0.4）；交付副本使用其同步SDK。主工程、交付源码对应修改必须同步。
5. 当前默认运动配置：0x26、CHIPID13、阈值08、持续时间03、低有效推挽01、AON7下降沿。
6. UART睡眠期停用，UART4丢帧为本次诊断允许行为。串口命令不是睡眠中的唤醒源。
7. 按键/运动已反复实测，用户明确不要重复要求相同动作。复用现有日志；新测试必须针对未解决问题。

## 2. 直接用串口进入

### 串口设置

- 当前实板COM26；换电脑或USB口后按实际端口选择，历史日志COM5不代表当前端口。
- 115200 baud，8数据位，无校验，1停止位。
- DTR/RTS关闭，发送结束符CRLF。
- 关闭占用同一串口的其他终端。可以用现有上位机发送下列文本，不依赖特定EXE按钮。

### 推荐命令

```text
sleep_test status
sleep_test enter low long
```

默认混合模式：KEY1、KEY2、G-sensor；请求300秒救援。当前实际约407秒，不把请求时长当精确定时。

| 命令 | 作用 | 期望AON掩码 | 请求救援 |
|---|---|---:|---:|
| sleep_test status | 查询诊断标志/模式/计数 | — | — |
| sleep_test enter | 默认低有效混合 | 92 | 60秒 |
| sleep_test enter low | 显式低有效混合 | 92 | 60秒 |
| sleep_test enter low long | 推荐长窗口混合 | 92 | 300秒 |
| sleep_test enter keys long | 仅两键可外部唤醒，传感器供电保留 | 12 | 300秒 |
| sleep_test enter motion long | 仅运动可外部唤醒，两键不作为唤醒源 | 80 | 300秒 |
| sleep_test enter high long | 高有效推挽/上升沿对照 | 92 | 300秒 |
| sleep_test exit | 清醒、CLI仍运行时取消测试标记 | — | 不能从已超深睡状态唤醒 |

keys/motion/high不加long时为60秒请求。`sleep_test enter long`不是合法形式，long前必须有low/high/keys/motion。

其他辅助命令：

```text
charger status
charger stop
cat1_power isolate
cat1_power status
gsensor_probe
gsensor_wait low
```

charger status读取故障寄存器会消费锁存；先保留首个故障日志。cat1_power isolate明确阻止UART4后台lazy-init，不等于USB硬件供电必然已断。gsensor_wait为清醒态采集，不是进入睡眠，其提示语要求动作时应按本次测试目标处理；测静止则不要照着move提示晃动。

## 3. 入口函数与调用关系

```text
UART0收字节/接收缓冲
  → QV_onIdle()
    → debug_uart_cli_poll()
      → cli_process_char() / CLI命令分发
        → cmd_sleep_test(argc, argv)       [检查并置诊断标志]
    → if (s_sleep_test)
      → sleep_test_prepare()              [一次性准备]
      → 检查 ready/source/timeout
      → app_aon_wdt_deinit()
      → pwr_mgmt_ultra_sleep(rescue_ms)    [SDK真实睡眠入口]
        → 硬件源或定时器唤醒
        → SDK soc_init()
          → ultra_deep_sleep_wakeup_handle()
            → 保存预复位证据
            → AON_SW_RST整机复位
        → 正常启动main()
          → debug_uart_boot_init()
          → 打印并消费ULTRA PRE-RESET
          → BSP_init / BSP_start / QF_run
```

若准备失败、观察到入睡前事件、超时或SDK意外返回，后续QV空闲路径调用sleep_test_finish()恢复外设并报告原因。正常超深睡唤醒走重启，不保证返回原sleep函数，也不依赖旧RAM业务标志继续执行。

## 4. 入睡门禁和准备过程

### cmd_sleep_test首先检查

- 测试未在运行，运输锁未锁定，OTA允许电源改变。
- 无报警、找人、拨号、来电、通话占用。
- KEY1/KEY2未按住。
- GPIO7传感器电源按“先初始化输出、再置高”方式设置，读回DATAOUT/OUTEN/MUX。
- gsensor_sleep_motion_arm成功，AON7按所选极性注册成功。
- 停止充电且读回成功，再设置s_sleep_test并选择睡眠策略。

### sleep_test_prepare随后检查/执行

- 保持诊断用全SRAM策略；保存SysTick及恢复所需状态。
- 设置两键和G-sensor回调；保存原AON使能，屏蔽全部8路再只开选定掩码，读回核对。
- 启动同一救援时长的应用定时路径。
- 混合/运动模式要求传感器空闲稳定约500ms，最多观察2秒；keys模式跳过GS资格，但保留其他门禁。
- 暂停UART0 RX，暂停/反初始化UART4，TX/RX置输入无上下拉；拒绝抢占其他UART4拥有者。
- 关LED（低有效，输出高mask0D）、停LCD接口并关LCD、关CAT1受控电源。
- 停SysTick，检查busy及extra状态、传感器电源锁存/复用、睡眠PAD状态、最终唤醒掩码。
- ready且无入睡前唤醒事件才调用SDK；准备失败走恢复。

这里是诊断门禁，不等于正式产品的静止时间、消息flush、离线交付、持久化与跨重启业务协议已经完整接入。

## 6. 日志怎样判读

正常入睡前应见：

```text
threshold=08 duration=03 (4 ODR periods) low-active PP config=01
AON before=92 enable=92 expected=92
pins k1=1 k2=1 gs=1 extstat=00 raw=00000000
rail_latch_ok=1
```

随后持续静默；entering不是最终成功凭据，后续仍可能entry_failed。深睡时串口不响应是预期，唤醒后重新出现BOOT。

恢复后重点看：

```text
[ULTRA PRE-RESET] valid=1 io=... ctl=... event=... raw=... enable=...
```

| 字段/数值 | 含义 |
|---|---|
| valid1 | magic/校验有效，记录来自SDK二次复位前 |
| valid0 | 冷启动或记录保留失败，来源未知；不能按全零断言定时成功 |
| io/ctl02 | AON1，KEY1位 |
| io/ctl10 | AON4，KEY2位 |
| io/ctl80 | AON7，GS_INT位 |
| io/ctl82 / 90 | 多位并存，不能认定只有某一个源 |
| event01 | 睡眠定时器事件 |
| event02 | 外部AON事件 |
| event03 | 两类均被记录，先后未确定，不称纯定时 |
| enable92 | 配置使能掩码，不是实际触发源 |

main原有BOOT WAKE DIAG四项仍可能全零，因为SDK先做一次整机复位；优先看有效PRE-RESET。AON7有事件不等于已证明真实运动，可能还需区分传感器事件与线路/供电扰动。

### 常见失败

- refused busy/locked/key held：查业务/OTA/运输锁和按键，不能强行跳过。
- GS setup失败：先查电源、0x26地址、CHIPID13和I2C占用。
- entry_failed：看busy/extra、GS空闲资格、UART拥有者、掩码和电源核对，不先改栈。
- 无BOOT到超时：长窗口实际约407秒；不要把300秒整当失效。先查日志，不立即强制擦除/复位。
- 电流仍高：核对CAT1 USB强制供电/R82、UART隔离是否保持、LED/LCD及ETA输入供电条件。

## 7. 功耗和硬件交接必须说明

本次用户临时拆R82，解除USB经Q10强制开CAT1 Q2的路径。原装板不拆R82时，GPIO6拉低可能仍关不了CAT1；不能只复制软件就承诺相同电流。保留Q10/R78，未要求进一步拆器件。

当前USB5V整机睡眠约4mA是用户单点读数，不是GR5526或电池待机。ETA69631 USB降压本身有毫安级消耗；现场允许PFM，停止充电仍供SYS。电池侧测流是另一项独立任务。普通睡眠不能用BATFET运输断电，否则两键/运动唤醒供电可能消失；无电池USB供电不能盲开HIZ。

启动后充电管理重新初始化、CAT1默认上电，状态和睡眠负载不同。PC诊断脚本会在BOOT后约15秒发charger stop、cat1_power isolate，这是主机动作，不是固件唤醒后自动永久隔离策略。

## 8. 业务代码想接入应该怎么做

当前推荐先用CLI验证，不把static CLI函数当稳定公共API。若同事要实现“业务条件满足后自动入睡”，应在平台层提取统一的请求/准备接口，由QV空闲上下文执行，复用现有门禁与回滚；不要在中断、QP事件处理中直接调用pwr_mgmt_ultra_sleep，也不要人为绕过忙状态。

提取前必须补齐：静止资格、消息下线与失败补报、报警/SOS唤醒源保存、用户数据保护、重启后的CAT1上电与联网恢复、OTA未完成任务恢复、充电监测和输入切换。诊断救援定时不能不经业务要求就变成产品周期唤醒。

此节是后续集成建议，当前未新增公开接口、未声称已经实现自动业务睡眠。
