# YP001 GNSS 保热启动可控模式：硬件配合与两端软件实施方案

**文档状态：实施设计稿。当前功能尚未实现；本轮仅创建文档，没有修改固件、编译、烧录或实板验收。**

## 1. 功能定义与业务控制入口

### 1.1 客户要实现什么

在 Air780EGH 内置 GNSS 停止定位期间，允许选择是否保持 GNSS 备电，从而在星历、时间及位置条件有效时支持再次定位热启动。

- 保热启动开启：保留 Air VBAT 供电及内部 GPIO23 高电平；GNSS 主电源可以关闭；模块进入适当低功耗状态。
- 保热启动关闭：允许停止 GNSS 后关闭备电，或按产品原流程真正切断整个 CAT1 电源。
- 本功能不等于蜂窝注册、MQTT、VoIP 或 Lua 的快速启动，也不保证任何环境下固定秒数定位。
- 重新开启备电不能恢复已丢失星历；需要先获得有效定位/辅助星历数据。

### 1.2 谁决定、谁执行

**GR5526 决定业务策略，通过现有 UART 通知 Air780EGH；Air 执行其内部 GPIO23、GNSS 电源和工作模式控制；GR 执行板外 VCC_4G 电源保持。**

可以采用 AT 风格自定义命令，但不是合宙现成标准 AT。当前工程实际已有 `BUS_CMD=<JSON>\r\n` / `BUS_EVT=<JSON>\r\n` 业务链路，优先复用它，避免创建第二套互相冲突的模式控制入口。

本文所有新增 op/字段/状态均为**拟新增内部接口**，未存在于当前固件，也不是平台协议字段。后续实现时在两端共同加入并验证；不得直接宣称设备现已支持这些指令。

### 1.3 选择策略和立即睡眠是两件事

1. 选择策略：记录“后续允许保热启动”，不立即终止定位、通话或进入睡眠。
2. 进入待机：GR 根据静止、报警、通话、定位、OTA及待报消息等状态发起握手。
3. Air 复核自身占用，完成准备并确认；GR保持电源后才提交待机。
4. 运动、按键或报警出现：取消准备或唤醒，恢复活动态。

客户本轮没有规定通过哪个实体按键、BLE界面或平台字段选择策略。因此第一阶段采用本地调试入口验证，正式产品入口另行确定；不擅自增加云端字段、不复用SOS键为模式切换键。

### 1.4 与现有客户要求的关系

| 要求 | 本功能涉及的处理 |
|---|---|
| F-003/F-007 | SOS定位与呼叫并行；日常不因保备电自动启动GPS搜星，不增加周期定位业务 |
| F-009/F-010 | 静止判定、待报消息flush、offline消息和失败持久补报仍须遵守；只有实际转离线才按离线流程处理 |
| F-011 | 原要求静止CAT1真断电；保热启动模式要求VBAT保留，二者不能同时满足。需要记录为客户可选供电策略；本文不修改既有需求基线 |
| F-012 | 活动态保持低功耗可达；不能因选择保热启动策略就直接进入断网的PSM+ |
| F-031/U-OTA-01/U-DATA-01 | 保留OTA电源仲裁、双端串行和用户数据保护，不能利用本模式绕过提交门槛 |

### 2.4 现板要不要改

第一阶段不割线、不短接Q2、不更换管脚、不从外部给PIN99供电，先验证软件控制是否成立。

必须测量GR低功耗期间GPIO6是否持续高。其为普通GPIO，需按SDK1.0.4验证睡眠配置/保持能力；不能把运行时DATAOUT当作睡眠保持证据。GPIO6复位变输入后，板上使能下拉可能关闭CAT电源，GR重启也可能破坏备电。

若只要求正常待机保备电，睡眠保持通过即可使用现板。若客户要求跨GR复位也必须连续供电，而实测掉电，则评估电源使能锁存/独立保持电路；原理图、极性、失效关断和工厂运输关断需要单独审查。若要求Air VBAT彻底断电仍保备电，现有公开外部接口不能满足，需厂商认可的独立备电接口或替代模块方案。

## 3. 模式、状态与优先级

### 3.1 策略和运行状态分开

策略仅两个：`HOT_RETAIN`（待机保备电）与`HARD_OFF`（允许真断电）。是否选择策略、是否已应用、是否实际进入低功耗要分别记录。

| 运行状态 | VBAT | GPIO23 | GNSS主电源 | 蜂窝/工作模式 |
|---|---|---|---|---|
| 活动态业务 | 有电 | 按策略；如GNSS运行不关闭备电 | 按业务请求 | 常规0或在线低功耗1 |
| 保热启动在线待机 | 有电 | 高 | 无请求时关闭 | 低功耗1，仍要求网络可达能力验收 |
| 保热启动静止离线待机 | 有电 | 高 | 关闭 | 第一阶段验证低功耗1；第二阶段评估离线PSM+3 |
| 原硬断电睡眠 | 实测应断电 | 无有效保持 | 关闭 | 模组停止，重新上电走正常启动 |
| 准备/唤醒/异常 | 有电或未知 | 不额外主动关闭 | 不抢占业务请求 | 先恢复通信和真实业务状态 |

PSM+不是普通低功耗的同义词；唤醒可重启程序、恢复网络需要时间，不能承诺保留原MQTT连接或原Lua RAM。

### 3.2 优先级

电气安全/已存在OTA安装保护 → SOS/持续报警/通话 → 定位及其他已占用业务 → 正常网络补报 → 模式切换和静止待机。

“SOS优先”不授权绕过安装期电源保护。OTA期间如何服务紧急业务沿已存在OTA仲裁处理，本功能不新增强制重启。

活动态选择HOT_RETAIN后不能切PSM+；静止离线前须保存消息、保持SOS/运动/按键唤醒，不增加为GNSS星历或OTA周期唤醒CAT1的策略。

## 4. 拟新增两端内部协议

### 4.1 复用当前业务帧

请求：`BUS_CMD=<JSON>\r\n`；响应：`BUS_EVT=<JSON>\r\n`。由GR业务UART发送，由Air business_runtime路由，不是直接写GPIO的标准AT命令。

| 拟新增操作 | 发起方 | 含义 |
|---|---|---|
| `hot_policy_set` | GR | 设置策略；繁忙时可拒绝或仅记录desired，不立即关闭电源 |
| `power_status` | GR | 查询desired/applied/phase及备电请求状态 |
| `standby_prepare` | GR | 请求待机准备，含HOT_RETAIN和目标在线/离线场景 |
| `standby_ready` / `standby_reject` | Air | 已完成准备或拒绝及原因 |
| `standby_commit` | GR | 确认GR将保持GPIO6，提交待机 |
| `standby_accept` | Air | 接受提交；发完回执后才请求低功耗，不能声称实测已睡眠 |
| `standby_cancel` | GR | 取消尚未进入或正在准备的事务 |
| `resume` / `resume_ready` | GR/Air | 唤醒后的通信、模式和状态重同步 |

协议需包含会话标识`session`和事务编号`req`。会话标识由GR在有效hello同步时建立，Air保存本次会话；两端重启/重新同步作废旧待机事务。`req`仅用于本会话关联和幂等，不是平台消息ID。

示意帧（拟新增接口，不能向当前设备发送后期待生效）：

```text
BUS_CMD={"op":"hot_policy_set","session":17,"req":1,"policy":"HOT_RETAIN"}
BUS_CMD={"op":"standby_prepare","session":17,"req":2,"policy":"HOT_RETAIN","target":"OFFLINE"}
BUS_EVT={"op":"standby_ready","session":17,"req":2}
BUS_CMD={"op":"standby_commit","session":17,"req":2}
BUS_EVT={"op":"standby_accept","session":17,"req":2}
```

实例省略帧末CRLF；实现需实际附加。不得将这些新增字段加入客户平台的paraSetMsg等协议。

### 4.2 回执必须表达实际能力边界

- `desired_policy`：GR希望的策略。
- `applied_policy`：Air已完成合法软件设置的策略。
- `backup_requested`：Air备电输出请求，不等同于测量PIN99电压。
- `rail_requested`：GR电源请求，不等同于实际VBAT。
- `phase`：active/preparing/committed/resuming/unknown。
- `hot_eligible`：只能unknown/可能具备/已失效；没有有效星历证据不得填“热启动保证”。

第一阶段不新增VBAT传感器，运行状态只能报告请求/未知，电压保持和实入低功耗使用外部测量验收。

### 4.3 丢包、重复、过期与串口约束

相同session/req及内容的重复请求返回当前结果，不重复切电源；同编号不同内容拒绝。旧会话、旧req的ready/commit不能驱动新状态。

准备有效期、回复超时、重试次数及唤醒等待值由实测确定；开发阶段可以使用明确标注的临时有限值，不作为客户承诺。准备超时回活动态，GPIO6维持高，不通过硬断电“修复”握手。

进入准备后有SOS/通话/运动/OTA占用，Air撤销ready，GR递增或取消事务；commit处理时两端再检查占用和事件代次，防止ready后发生业务却仍睡眠。取消迟到或已提交时，按唤醒流程恢复，不等待旧cancel回包。

当前UART为文本JSON帧，没有新协议CRC/认证保证；长度、枚举、会话、状态检查不能代替物理链路正确性。GR TX→Air RX已有字节异常排查背景，实施前必须重新验证当前链路，`TX ok=1`不能证明接收正确。DFU二进制独占时拒绝模式事务，不插业务文本、不切电源。

## 5. 两端配合的完整时序

### 5.1 首次上电和策略同步

1. GR初始化板级IO，释放AON_GPIO0/PWRKEY；GPIO6按合法启动策略供电，不先制造不必要的关开脉冲。
2. Air在最早可安全执行GPIO操作的位置保持GPIO23默认高，避免启动先清GPIO再读取策略；保持已有OTA日志恢复顺序和用户数据保护。
3. GR等待有效hello，不将串口写成功当作Air就绪；确认本次会话、双方版本及功能能力。
4. GR同步当前用户策略；Air合法校验并回applied/desired。旧固件无能力时返回不支持，不能靠普通OK推断成功。
5. 保留现有hello之后电量重同步、时间校准及待报恢复。若网络恢复，按既有online消息流程；SOS不等待普通上线/策略同步完成才起呼。

持久策略建议由GR单一权威保存，在自然唤醒时同步Air，避免两端独立持久值打架。存储位置与默认值须在用户数据盘点中确定；只在用户真正改变策略时写，不每次sleep/hello写Flash。未受控掉电后热启动资格标unknown。

### 5.2 进入保热启动待机

1. GR确认静止条件及无报警、无通话、无按键/运动新事件、无受保护OTA状态；发起prepare事务，GPIO6仍高。
2. Air核对真实业务占用，包括GNSS tag、天线测试、音频、网络发送、HTTP/OTA/DFU和待报记录。
3. 在线目标不发offline、不停必要MQTT下行；离线目标按原要求先flush再offline，失败有限重试并保存待报数据。业务补报不因为待机丢失。
4. 定位占用结束后关闭GNSS主电源；保持GPIO23高。不要直接强制close_all抢占仍合法的GNSS客户端。
5. Air在无音频占用时关闭GPIO24/20，并准备低功耗；此时仍不能睡眠到收不到commit。
6. Air发送ready。GR重新检查运动/SOS等事件，确认电源保持请求，发送commit。
7. Air收到匹配commit后再次复核，发送accept；确认UART软件队列为空且底层发送完成后再请求WORK_MODE=1。
8. GR收到accept后进入计划待机态，停止该状态下的周期hello和失联超时；保留真实紧急事件处理和唤醒源。GR进入自身睡眠时GPIO6必须保持高。

accept仅表示提交已接收。实际休眠取决于Lua任务、定时器、网络栈、USB和固件；用电流测量判定是否真正进入，不以accept作为功耗验收。

TX排空不是当前send_queue长度为0：uart.write已把最后一帧交底层后仍可能发出。需验证底包可用的TX完成/排空接口；没有可靠接口时以实测建立有界安全等待，且整个等待允许紧急取消，不能武断加固定延时宣称可靠。

### 5.3 运动、按键、SOS唤醒

1. GR记录事件，保持GPIO6高；待机事务立即失效。
2. 第一阶段验证低功耗UART唤醒；不能把业务首包当唤醒包后立即认为Air已收到。先唤醒，再等待hello/探测回包，再重发实际业务。
3. 若采用PWRKEY唤醒，配置Air端合法唤醒源；GR高经Q4拉低PWRKEY，随后释放。脉宽/边沿按实际底包验证，不能直接套用1600ms手动开机阻塞动作。
4. Air恢复WORK_MODE=0并回resume_ready/hello，恢复必要任务；PSM+时程序可能重新启动，需重新建立会话和业务同步。
5. SOS优先恢复通话/报警与定位并行，不能等待GPS fix才拨号。日常运动只恢复既有业务，不因保热启动启GPS。
6. 需要定位时通过exgnss打开主电源；备电一直保持，且条件有效时才可能热启动。

唤醒失败采用有限重试并记录unknown。是否允许最终硬断电救援必须单列策略，受OTA保护且明确会丢失备电；不能无限循环切电或伪报热启动成功。

### 5.4 从保热启动切回省电

用户修改desired后，先等待合法安全窗口。关闭GNSS主电源、保存待报和用户数据，再按官方方法将GPIO23切输入关闭备电。若选择真断电流程，再由GR在OTA保护许可下关闭GPIO6，并在无USB条件下验证VBAT实际掉电。

GPIO23的输入配置及LuatIO复用须核对当前底包/API；不要不加核对写成`gpio.close`或随意输出低。策略重新打开后，先恢复GPIO23，再按业务需要定位获取有效星历；不额外周期上电刷新星历。

### 6.3 GPIO操作原则

官方支持保持备电的输出高方式；关闭备电按Vref文档切输入。初始化输出保持高后，后续合法电平变化优先避免重复setup造成不必要毛刺；输入/输出模式转换则需明确重新配置。底包兼容性和PIN99实测必须验证。

所有模块都调用电源管理器，禁止音频/天线测试/watchdog各自修改GPIO23、GPIO6或WORK_MODE。省电demo中默认关闭备电、批量释放AGPIO、切飞行模式等行为不能整段照搬。

## 7. 异常处理矩阵

| 异常 | 必须行为 |
|---|---|
| prepare无回执/JSON损坏 | 有限重试，回活动/unknown；保持供电，不根据写入成功直接睡眠 |
| ready之后发生报警/运动/通话 | 事务失效，禁止commit；已进入则唤醒，业务优先 |
| OTA/DFU占用 | 拒绝或延后切换，不触发重启/硬断电，不混业务回包到二进制通道 |
| accept丢失 | 重复同req查询/提交幂等；按可能已待机处理，使用合法唤醒恢复，不发新事务直接关电 |
| prepare后GR重启 | 旧会话无效，Air准备到期取消；若GR复位导致VBAT丢失标备电资格unknown |
| Air异常重启 | 不声称星历必丢或必保；保持GPIO23默认高，重新hello和策略同步，复核实际供电 |
| 用户切省电但正在定位 | 仅记录desired或拒绝繁忙，不能直接切备电中断业务 |
| 网络/SIM故障 | 有限恢复和持久补报，不能用模式切换清绑定/参数/报警 |
| USB插入/拔出 | Q10旁路可能改变VBAT；按实际供电记录，分别测试；不能插USB测到常开就判GPIO6保持正确 |
| 电池耗尽/运输断电 | 热启动资格失效/unknown，保持现有运输与5V唤醒规则，不承诺无电源备电 |
| UART实际字节错误 | 停止本模式实板准入，先完成物理通信修复；不通过降低门槛绕开握手 |

## 8. 按阶段实施与验证

### 阶段A：先验证现板保持能力

- 确认板版/BOM、底包和部署Lua，记录原始功耗及正常定位情况。
- 只用电池，测GPIO6、VBAT、PIN99、VDD_PA、8311_3.3V；再测插USB状态。
- GR当前睡眠/唤醒/复位分别记录GPIO6及VBAT波形。复位保持要求不成立时单列硬件改动候选，不直接短接开关。
- 检查UART两方向完整帧、分包/粘包、首包和重复帧，确保当前物理链路正确。
- 此阶段不修改业务规则，不将J-Link寄存器/CLI返回值当电压证据。

### 阶段B：独立实现备电策略查询与设置

先实现desired/applied和GPIO23控制，不进入低功耗、不改主电源状态机。有效定位后保持/关闭备电，再开GNSS对比，验证控制可重复、繁忙拒绝和重启恢复。第一片功能通过再扩大到握手。

### 阶段C：两端低功耗模式1握手

接入prepare/commit/cancel/resume、GPIO6保持、音频关闭、心跳暂停、TX排空，逐一验证成功、失败、迟到回执、报警抢占。在线和静止离线分开测，确认Lua任务不阻止真实休眠。

### 阶段D：静止离线PSM+评估

只有模式1及唤醒链路通过后再做PSM+。验证合法PWRKEY/UART唤醒、软件重启、GPIO23无关断窗口、用户策略恢复、网络重新注册和SOS不可用窗口。不能把模式1验收自动扩展为PSM+通过。

### 阶段E：产品入口和发布

确认默认策略和实体/BLE/平台控制入口；平台字段若新增另行协议确认。同步两份GR工程、Air交付文件和受控发布清单，保留原始可恢复包。正式发布与烧录授权单独执行，本方案不授权改动用户数据。
