## 二、失败问题及原因

| 问题 | 现场表现与原因 | 最终处理 |
|---|---|---|
| 同事工程产物缺少项目 Boot | 原 HEX 只包含 APP。Keil 能写入并直接运行 APP，不能据此推断板上已有 OTA Boot | 增加受控的“首次初始化 Boot”，写入配套 Boot 并检查启动配置 |
| 初始化条件过于笼统 | 早期把 OTA 区任何非空内容都判为不允许初始化，无法区分未分配接收范围的旧 GR 任务与安装中任务 | 按 CRC、commit、代次、阶段、目标、进度和 B 所有权检查，仅允许规定的安全初始状态 |
| 非空 B 槽与下一次 OTA 冲突 | 固件首次取得 B 所有权前要求 B 为空。保留未知非空 B 会阻止后续接收，不能仅看接收器会逐扇区擦除就认为可用 | 用户明确批准“允许备份并确认后清空”，工具保存整片和 B 槽备份后再执行 |
| XML 路径解析错误 | 把 `JLinkDevicesXMLPath=.\` 当成相对于日志工作目录，实际解析基准与 DLL 路径有关 | 对 XML 使用明确的绝对 ASCII 路径，中文目录优先使用短路径，必要时使用 TEMP 算法目录 |
| 先暂停、后设置设备库 | 首次 `h` 会触发隐式芯片连接并选择通用 Cortex-M4，设备列表可能已被缓存。之后设置 XML 不能保证新设备生效 | 在任何首次 `h` 或隐式目标连接之前，先设置 XML，再明确执行 `device YP001_GR5526` |
| v1.4.2 的运行文件复制方案失效 | 复制出去的 Commander 实际仍读取安装目录设备库。直接加载复制 DLL 的离线测试，与 Commander 真正使用的加载路径不一致 | 删除该复制方案，使用安装目录 Commander，并通过真实 SDK 日志核对实际 XML、设备选择和调用顺序 |
| “擦除结束”被误当作擦除成功 | J-Link 会在 `No Flash bank within given address range` 后继续打印 `Erasing done.` | 每段擦除分开执行，检查错误信息，并要求收到对应精确地址范围的 `deleted` 回执后才继续 |
| 新板运行时读取 APP 出现不一致 | 首次实板运行发现 476 字节 APP 读取错位，比较门禁在擦写前拦截。暂停后连续两次全片读取一致 | 整片备份和回读统一先 `h` 再 `savebin`。现有证据支持暂停读取可解决本次不一致，尚未进一步定位芯片内部总线或缓存机制 |
| 界面文字重叠 | 同事截图出现说明文字压字 | 调整标签自适应、说明行、间距和最小窗口尺寸，主机缩放检查覆盖 100%、125%、150% |

## 三、这次应当记住的教训

1. **设备名称能查到，只能证明设备库中存在定义。** 后续还需要证明 Commander 实际加载了该配置、选中了正确设备，并使用对应 Flash 算法完成操作。
2. **验证必须经过用户真正使用的执行链。** 直接调用 DLL、模拟成功日志、编译通过和 ZIP 校验各有作用，但都不能替代实际 Commander 的连接、擦除、写入和回读。
3. **前两次修复在验证不足时就提供了新版。** 后续出现同类问题时，应先补齐实际路径、完整参数、SDK 调用记录和最小实机证据，再判断修改是否有效。
4. **请求参数和实际状态必须分别核对。** `.runtime.txt` 中写着期望设备，不代表运行日志中实际选择的设备正确。必须读取实际 `Device ... selected` 记录。
5. **暂停命令也有执行顺序。** `h` 会触发隐式连接。设备库和设备名配置应先于首次芯片连接，不能只检查脚本中“有没有这些命令”。
6. **错误信息优先于笼统的完成文字。** 出现 `No Flash bank`、写入失败、校验不符或缺少规定回执，必须停止后续步骤。
7. **备份必须可信且可追溯。** 检查长度、实际内容、探针编号和摘要。读取不一致时停止，不能删掉比较门禁以求烧写继续。
8. **备份成功与在线数据保持是两个结果。** 未知 B 内容清空后不会自动恢复。即使存在备份，恢复也要重新核对当前事务和最新用户数据。
9. **单次成功的范围要明确。** 本轮验证了首次初始化路径和启动，不能因此填写完整 OTA、字库升级或所有电脑兼容性已经通过。
10. **沟通要同步实际阶段。** 出现长时间等待时及时查看进程和落盘日志，明确当前是连接、擦除、写入还是回读。本次流程完成后，状态反馈一度没有及时跟上日志，后续应避免让使用者误以为仍卡在连接。

## 五、B 槽、字库与初始化的边界

### 5.1 两种“A/B”不能混淆

| 区域 | 当前地址范围 | 用途和本次处理 |
|---|---|---|
| APP A 槽 | `0x202000–0x26DFFF` | 写入签名 APP |
| OTA B 槽 | `0x280000–0x2EBFFF` | OTA 接收及安装/回退流程使用，本次初始化清空 |
| 项目 Boot | `0x2EC000–0x2F5FFF` | 写入配套 Boot |
| scratch、Boot 日志及 owner | `0x2F6000–0x2FAFFF` | 本次受控初始化清理 |
| 姓名字形存储页 A/B | `0x2FB000–0x2FCFFF` | 与 OTA B 槽不同，本次复位前核对保持 |
| NVDS | `0x2FE000` 起 | 本次复位前核对保持 |

这份地址表对应当前布局。将来修改分区时，必须同时检查固件布局、签名合同、Boot、算法和工具边界。

### 5.2 初始化的含义

首次初始化会改变启动配置，写 A 和 Boot，清空 B 及规定的 OTA 任务区。B 中的旧内容不会自动迁移或回填，后续合法 OTA 会按协议重新使用空 B 槽。已清理的旧下载任务不能继续沿用，须按合法流程重新发起。

工具要求 Boot、scratch 和 Boot journal 满足规定条件。对 owner，仅允许为空，或符合规则的、尚未分配接收范围的 GR 旧任务。损坏、冲突、已分配 B、有进度、安装中或不允许的目标状态应被拒绝。

“首次初始化”不应作为任何错误的通用处理按钮。B 内容未知时，必须保留备份并明确确认删除风险。本次“保留字库”的证据适用于已识别的保护区，不能据此保证未知 B 内容不存在其他业务价值。

## 六、后续使用这个工具要注意什么

### 给使用者

1. 使用完整解压的 **v1.4.3** 工具包。EXE、FLM 和说明按原目录放置，并安装 SEGGER J-Link 软件及驱动。当前默认安装路径为 `C:/Program Files/SEGGER/JLink`。
2. 后续仍用同一个 Keil 主工程 F7 编译，再由签名工具生成签名 BIN，最后交给烧写工具。正常流程自动加载设备和算法。
3. 日常烧写不勾“首次初始化 Boot”。只有确认缺少 Boot、并通过工具安全检查时才勾选。已经初始化过的板子按正常流程使用。
4. 要保留姓名、房号、园区和字形时，确认“出厂清空”未勾选。普通模式该选项默认勾选，初始化模式会自动关闭它。
5. 需要串口版本回应时选择实际 GR 串口。“不读版本”可以执行有线烧写，但少了实际启动版本这一项证据。
6. 出现未知设备窗口、`No Flash bank`、写入失败、校验失败或快照变化时，停止后续操作并保留整套日志。出现未知设备窗口时取消，不手动选 Cortex-M4 后强行继续。
7. 烧写失败后，保留稳定供电和现场，记录失败阶段。不要盲目复位、整片擦除或把旧 `pre.bin` 整片回写。
8. `logs` 是运行自动生成的。对外分发前从交付副本中排除历史日志和个人串口记录，内部仍需保留失败现场、成功证据和初始化备份。Luatools 的 `_temp` 中有运行依赖，不能按普通临时垃圾统一删除。
9. 本机通过后的下一项是同事电脑验证，重点核对 J-Link 安装版本、路径、实际设备选择、擦写回执和启动结果。

## 七、当前仍需注意的限制

- **本次完整实板流程覆盖首次初始化路径。** 已有 Boot 的普通烧写路径本轮有主机回归，尚未单列新的完整实板闭环。

- **独立只读连接检查不能完全替代同进程门禁。** 当前后续会话重复显式设备配置，并检查擦写回执；未来如加强同进程控制，仍需单独评审和验证。
- **数据保持证据截至首次启动前的回读。** 首次启动后的业务迁移、断电重启和字库实际显示，需要对应业务验收。
- **GR 启动和 CAT1 启动分开确认。** 本次 CAT1 经过人工供电和一次 PWRKEY 后才取得真实回应，烧写工具本身没有因此获得自动保证 CAT1 启动的能力。
- **完整双端 OTA、下一次连续 OTA、字库直推、URL/NAME_URL、缺字补发和两个顺序的并发测试仍待完成。** B 槽为空只是后续 OTA 接收所需条件之一。
