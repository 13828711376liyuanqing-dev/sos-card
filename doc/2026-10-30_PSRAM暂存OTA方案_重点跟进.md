# 用 GR 的 8 MB PSRAM 暂存 OTA 升级包（重点跟进项）

SAM | 2026-10-30 22:30 +08:00 | 读者：本项目开发团队和 D:\SVN 代码维护者。来源：同事 10-30 的建议；背景是 CAT1 文件区只有 512 KB，整机 OTA 时 GR 镜像要先整个存进去，现场整机用久了会升不了级（见 `2026-10-30_CAT1文件区空间方案_待评审.md`）。
**状态：方案阶段，没有任何代码改动。** 标“待确认”的是还没有验证过的假设。

## 一、目标

1. CAT1 文件区不再暂存 GR 镜像，OTA 与 CAT1 文件区的占用无关，现场整机怎么用都能升。
2. GR 镜像大小只受 GR 的 A/B 槽（442368 字节）限制，不再受 CAT1 文件区限制。
3. **先验证、后写 Flash**：GR 收完整个镜像并验签通过后才写 B 区（现在是边收边写）。

## 二、现状（实测与读代码）

| 项 | 现状 |
|---|---|
| CAT1 | 下载整个升级包 ZIP（约 700 KB），GR 组件先整个存进文件系统的候选文件 `/o<hash>.p`（`ota_candidates.lua`，每次 4096 字节，上限 479232），验证整包 MD5、签名、清单、组件摘要，再启动传输 |
| 传输 | `ota_gr_transfer.lua` 把候选文件经 UART 用 `OTA2` 二进制协议（`ota_wire.lua`、`ota_uart_window.lua`）发给 GR，每块带序号，GR 回复确认；约 6 分钟 |
| GR | `yp001_ota_receive.c`：按块把数据写进 B 区（擦除→写→读回），定期把 owner、hash、总长、偏移**原子持久化**（断电可恢复），全部收完后整体验证（摘要、签名、模型、布局、数据、版本） |
| CAT1 自己的包 | 约 250 KB，走 `ota_native_fota.lua`（原生 `fota.init/run/isDone/finish`），也先暂存 |
| 空间需求 | `已签名镜像 + 904 + 16384`，1.5.3 是 455760；OTA 发起后设备多写约 16 KB 状态文件，现场可用空间可能不足 |
| GR 的 PSRAM | `yp001_psram_mem.c`：基址 0x30080000，共 8 MB，`yp_psram_alloc` / `yp_psram_free`（基于 `app_graphics_mem`），现在只有墨水屏和 LVGL 的缓冲在用（几十 KB） |

## 三、新流程（建议）

```
平台 --(HTTP 顺序流)--> CAT1 --(UART OTA2)--> GR PSRAM(暂存) --验证--> GR B 区 --> 重启切换
```

1. CAT1 开始下载 ZIP。ZIP 的顺序是：清单 `bundle.json`、签名 `signature.json`，然后是各组件；`ota_seq_zip.lua` 已经能顺序解析。
2. CAT1 先收到清单和签名，**先验签**，得到 GR 组件的大小和 SHA-256。
3. CAT1 向 GR 发 `STAGE_OPEN`（任务号、大小、期望摘要、版本）；GR 检查自己能不能收（OTA 所有者合法、电量、静止等安全门），`yp_psram_alloc(大小)`，回复接受。
4. CAT1 遇到 GR 组件的数据，**每收到一块就经 UART 转发**（不落 CAT1 文件系统）；GR 写进 PSRAM 缓冲并确认。
5. GR 组件结束，CAT1 发 `STAGE_CLOSE`；GR 对整个 PSRAM 缓冲算 SHA-256，核对期望摘要，并按现有流程验签、模型、布局、数据保护、版本等检查。
6. **全部通过**，GR 才把缓冲写进 B 区（擦除→写→读回→持久化），之后沿用现有的激活、重启、健康观察流程。失败则 `yp_psram_free`，B 区一个字节都没动。
7. CAT1 自己的组件仍走原生 FOTA；也可以让它同样流式写入原生 FOTA 区（原生 FOTA 本来就是边收边写专用区，**待确认**是否不占文件系统），验证通过再 `finish`。

## 四、需要改的地方

### CAT1（Lua）
| 文件 | 改动 |
|---|---|
| `ota_download.lua`、`ota_http_range.lua`、`ota_seq_zip.lua` | 不再把组件写候选文件，改为回调给“转发器”；保留整包 MD5 校验（流到尾再算） |
| `ota_candidates.lua` | GR 组件不再使用；CAT1 自己的组件视情况保留 |
| `ota_gr_transfer.lua`、`ota_uart_window.lua`、`ota_wire.lua` | 新增 `STAGE_OPEN/DATA/CLOSE/ABORT` 帧；流控按 GR 的确认节奏发送 |
| `ota_runtime.lua`、`ota_manager.lua` | 状态机加“流式转发中”，去掉对“候选文件已落盘”的前置条件和 `COMPONENT_SPACE` 检查（GR 组件部分） |
| `ota_bundle.lua` | 清单和签名先验，组件摘要由 GR 核对，CAT1 记录结果 |

### GR（C）
| 文件 | 改动 |
|---|---|
| `yp001_ota_wire.c/.h` | 新增上述帧的解析和应答 |
| 新增 `yp001_ota_stage.c/.h` | PSRAM 缓冲管理：分配、写入、偏移校验、整体 SHA-256、释放 |
| `yp001_ota_receive.c`、`yp001_ota_port.c`、`yp001_ota.c` | B 区写入改为从 PSRAM 缓冲读；状态区分 `STAGING`（易失，复位即丢）和 `B_WRITING`（持久化） |
| `yp001_psram_mem.c/.h` | 需要同事配合：OTA 用的分配/释放、是否保持供电 |

## 五、必须想清楚的问题

| # | 问题 | 说明 |
|---|---|---|
| 1 | **PSRAM 睡眠时是否断电（待确认）** | `mem_pwr_mgmt_mode_set` 的设置；OTA 期间整机必须不进入会丢 PSRAM 的睡眠 |
| 2 | **PSRAM 易失，断电和复位后缓冲就丢了** | 流程必须“失败就从头来”。平台没有 Range（只能顺序流），断线后本来也要重下，所以退化不大；但原来“已暂存的部分文件跨 CAT1 重启仍在”的好处没有了 |
| 3 | **不能破坏回滚和用户数据保护** | B 区写入、激活、重启切换、健康观察、回滚这些已验证的路径不动；只改“数据怎么到 B 区”这一段 |
| 4 | **第一次引入新协议怎么升级** | 现在设备上的 GR 和 CAT1 都不懂新帧。**新协议只能先用现有流程升级进去**（一次整机 OTA，用旧协议），之后的升级才用新协议；`OTA_TRIAL_*` 的版本范围要允许这一步 |
| 5 | **新旧混合** | 升级到一半时 CAT1 新、GR 旧（或相反）必须明确拒绝并退回旧流程，不能出现半新半旧的静默失败 |
| 6 | **PSRAM 堆碎片** | `app_graphics_mem` 要分配 442 KB 连续块；LVGL 和墨水屏的缓冲先分配，8 MB 应该够，但要在实板上确认（OTA 开始时能不能一次分到） |
| 7 | **UART 速率和吞吐** | 现在 CAT1 的 UART4 可设 115200 或 460800；流式后下载速度和转发速度要匹配，需要缓冲区和背压（GR 确认才发下一块） |
| 8 | **GR 的内存/时间** | 整体 SHA-256 442 KB 的计算时间和 GR 看门狗喂狗（看门狗必须在前面修复的 5 秒窗口内被喂）要实测 |
| 9 | **安全** | GR 在收到验签通过的清单摘要之前，不信任 CAT1 发来的任何“已验证”；验签、模型、布局、数据保护的检查全部仍在 GR 本地完成（现有的 `yp_receive_verify`） |

## 六、验证计划

1. **主机测试**：Lua 的流式下载和帧编码；GR 的暂存缓冲（C，主机编译）；断线、错序、重复、超长、摘要不符、签名错、PSRAM 分配失败等异常。
2. **实板**：① 用旧协议把新协议固件升进去（整机 OTA，沿用已验证流程）；② 新协议整机 OTA 一次；③ 异常注入（下载中断电 CAT1、GR 复位、断网、错摘要）；④ 回滚。
3. **空间验收**：OTA 全程 `cat_at OTA_FS` 的已用块数不随 GR 镜像变化；故意把文件区填到只剩 4 KB，OTA 仍然能成功。
4. 每一项都要如实记录“主机/实板”，不能把主机测试写成实板通过。

## 八、与其他方案的关系

- **现在的合并版**用 `-Oz` 放进现有流程（体积 422240，余 19224；CAT1 暂存需要 439528），这是**过渡**。
- 本方案落地后，`-Oz` 不再是必需，CAT1 文件区的占用与 OTA 脱钩，现场整机久用也能升。
- 其他方案（缩小 GR、外挂 SPI Flash、让合宙定制更大的分区、设备端自动清理历史）仍可并行做，其中**设备端自动清理（方案 E）仍有价值**，因为 OTA 状态文件本身也占空间。
