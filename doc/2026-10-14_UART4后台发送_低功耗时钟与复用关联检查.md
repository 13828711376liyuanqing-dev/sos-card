# UART4 后台发送、低功耗/时钟与引脚复用关联检查

记录：SAM，2026-10-14，北京时间。板卡：YP001，GR5526 + Air780EGH。CAT1 源码入口仍为 `D:\CODEX\sos-card\Air780EGH`。

## 结论

本次检查没有找到错帧与后台发送重叠、持续休眠切换、持续时钟切换或持续引脚复用改写的关联。故障仍存在，不能写成“UART 已修复”。

13:22 的有效同步轮：DL32 实际为1.6 V、10 MHz、10秒；COM26下发20次固定 `cat_diag AT`，GR返回20次本地TX成功。CAT1第17脚CH1抓到20条完整四字节帧，**9条正确、11条变形**，逐位差异为10处bit0和1处bit4，全部1→0。CAT1 USB同窗继续记录错误回车等坏行。

J-Link同轮20组读取中，电源模式、核心时钟值、UART4格式、AON复用、UART驱动状态及异步队列均未出现采样可见变化。每组寄存器顺序读取，相邻组LCR读取间隔约222～431 ms，不能排除微秒级瞬态。J-Link连接可能影响CPU服务时序；9/20不用于比较调试连接是否加重故障。

## 一、后台发送路径

| 路径 | 当前代码行为 | 与诊断发送的关系 |
|---|---|---|
| `cmd_cat_diag` | 局部缓冲构造固定 `AT\r\n`，调用 `app_uart_transmit_sync` | COM26命令在前台CLI轮询中执行 |
| `cmd_cat_at` | 前台构造命令，调用同步发送 | 本轮没有使用 |
| `yp_business_port_send` | 同一桥接UART4，同步发送，超时100 ms | `yp_business_poll` 每5秒尝试hello；当前捕获确有后台长帧 |
| `yp001_ota_uart_reply` | 前台收到完整行后处理OTA并同步回帧 | 本轮没有执行OTA |
| `uart4_send_data` | 存在异步发送包装函数 | 项目源码搜索只找到声明和定义，未找到实际调用 |
| `Cat1Svr_send_async` / 旧AO | 原有异步路径仍保留 | `BSP_start` 的Cat1Svr构造、硬件初始化与启动被 `#if 0` 禁用；不能把源码存在当成运行中的第二发送者 |

当前 `main.c` 选择QP，使用QV合作式调度。`QV_onIdle` 顺序执行CLI轮询、业务服务、UI及电源调度；CLI `cat_diag` 的同步发送期间，没有调用另一次业务轮询。按键ISR使用请求邮箱，正常业务发送不在按键ISR直接执行。接收IRQ先写环形缓冲，完整行的业务/OTA处理在前台完成。

因此，现有路径更符合**同一个前台先后发送**，尚无证据支持“两条已运行的发送任务同时改同一TX缓冲”。这不等于证明底层HAL/FIFO逐位正确。

### 波形与后台长帧距离

13:03已有捕获中，4条坏AT与后台长帧边界相隔约0.32～4.16秒；首条和第6条坏AT早于捕获中的首个后台长帧。13:22有效轮中，11条坏AT与后台长帧边界的距离约47 ms～2.30秒，均形成独立四字节帧，没有观察到AT与后台长帧字节交叠。

这些结果不支持“只有hello紧邻发送才出错”。延迟打印或多行合并不能当成线上同时发送。后台记录有坏字节也表明问题不只影响诊断短帧。

## 二、低功耗与时钟

`app_periph_init` 明确执行 `pwr_mgmt_mode_set(PMR_MGMT_ACTIVE_MODE)`。当前产品源码未找到另一处切换到IDLE/SLEEP的调用。`QV_onIdle` 调用 `pwr_mgmt_schedule`，但源码选择ACTIVE且没有末尾WFI。

SDK UART确实具有睡眠保存/唤醒恢复回调；`uart_prepare_for_sleep` 会检查HAL状态，忙态拒绝睡眠。当前工程配置没有启用 `APP_DRIVER_WAKEUP_CALL_FUN`，恢复走统一唤醒回调分支。这是能力说明，不代表本轮实际发生了睡眠。

实机ROM `pwr_mgmt_mode_get` 在 `0x00097764` 的指令读取 `0x2000382C` 的模式字节。本次仅读取这些指令与RAM，未调用ROM函数或改写模式：模式字节始终 `00`，与SDK ACTIVE枚举一致。

`SystemCoreClock=0x05B8D800`，即96,000,000；MCU时钟选择寄存器同时保持 `0x10000200`，其当前选择字段为SDK定义的96 MHz。UART4 LCR保持8N1。DL32中19个仍解为T的第二字节共57个预期高脉冲，宽度为21或22个10 MHz采样点，即2.1或2.2 μs，与460800的名义位周期约2.170 μs相近，未显示大幅位宽漂移。数字脉冲宽度仍受比较器门限影响，不能用来测模拟上升沿。

源代码入口：[ACTIVE设置](../ble_app_uart_c/Src/platform/user_periph_setup.c:724)、[UART睡眠/恢复](../SDK/drivers/src/app_uart.c:136)、[电源模式枚举](../SDK/components/sdk/gr55xx_pwr.h:108)。

## 三、复用、驱动和运行快照

GR TX为AON_GPIO2，RX为AON_GPIO3，两者为UART4 MUX0。GPIO2/3的I2C定义属于普通GPIO域，MSIO_A2/A3属于另一IO域，不能只凭数字2/3判定它们抢占AON_GPIO2/3。源码未找到正常业务周期改写这两个AON复用的路径。

| 地址/字段 | 20组采样结果 | 含义及边界 |
|---|---|---|
| `0x2000382C` 电源模式 | `00` | ACTIVE |
| `0x20000360` SystemCoreClock | `05B8D800` | 软件核心时钟值96 MHz，有选择寄存器交叉核对 |
| `0x4000A000` MCU_CLK_CTRL | `10000200` | 时钟选择在采样中不变 |
| `0x4000C90C` UART4 LCR | `00000003` | 8N1、DLAB=0 |
| `0x4000EE50` AON_PAD_MUX_CTL | `77770077` | AON2/3的选择字段均为MUX0 |
| `0x4000A1E8` 起4字 | `00001A05 007E00FE 00000000 000C0000` | PAD上下拉/控制、复用覆盖状态不变；不是模拟驱动幅值证明 |
| `0x4000EE8C` 起5字 | `F27FCBAE 00000000 00000000 00001D55 0000002B` | 外设时钟控制与睡眠门控采样不变 |
| `0x200216BF` TX/RX状态 | `10 12` | HAL_TX_READY、HAL_RX_BUSY；采样未命中约百微秒的短TX不代表没有发送 |
| `0x200216F0` 驱动UART/DMA状态 | `01 00` | APP_UART_ACTIVITY、DMA未启用 |
| `0x200216F4` 异步TX环形缓冲 | `00000200 2002198E 00000000 00000000` | 容量512，写/读索引均0 |
| `0x20021784` 五个TX/刷新/中止/DMA标志 | 全0 | 采样没有异步队列活动 |
| `0xE000EDF0` DHCSR | `01010001` | 采样时S_HALT=0；没有主动执行halt/reset |

RAM字段地址依据当前AXF DWARF成员偏移与MAP核对，不依靠手工按32位枚举猜结构。实机 `cmd_cat_diag`、`QV_onIdle`、`app_uart_transmit_sync` 各16字节与当前AXF反汇编抽样一致；这只确认这三处代码样本，不代替全镜像版本校验。

坏首字节 `@` 的预期bit0窗口仍为0/21高采样，但同字节bit6为21/22或22/22高采样。错误更像局部高位丢失，不能仅由空闲3.3 V推断动态高位正常，也不能由数字记录认定某个焊盘或器件已经损坏。

## 五、下一步定位边界

本次三项检查降低了“两个后台任务争用”“持续深睡恢复”“持续复用/时钟配置跳变”的优先级。不能因此排除微秒级暂态、HAL/FIFO写入异常、UART硬件输出或板级动态高电平问题。

下一项有判别力的检查是：在发送入口保留本帧原始4字节、TX前后状态和时间，并与同一帧的引脚位流对照，确认数据在进入HAL/FIFO前是否已变化；必要时比较同一管脚上的另一受控发送方式。诊断固件需明确UART独占与恢复路径，不用全局关中断或把RX改为输出。若发送数据完全正确而引脚仍丢高位，仍需模拟波形或隔离负载才能判定线路/焊盘的电气根因。现有串口OTA不做验收。
