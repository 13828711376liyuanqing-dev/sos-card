# GR5526 COM30 功能迁移至 BLE 的评估与实施方案

## 1. 评估结论

可以实现。建议在现有 GR5526 BLE GUS 服务上增加无线 CLI 和可订阅日志，复用现有命令处理函数，并保留有线调试入口。首期建议交付 Windows BLE 调试工具，提供命令发送、回应显示、日志保存和断线重连。

实现后存在资源竞争、权限扩大及低功耗方面的影响，必须通过队列限流、业务优先级、OTA 安全门和实板回归控制。当前只能判定源码具有复用基础，尚不能承诺对 OTA、SOS、定位和续航零影响。

本方案将“COM30 的功能”解释为 GR UART0 的命令交互、命令回应、运行日志，以及由 GR 转发的 CAT1 诊断信息。J-Link/SWD、复位前启动日志、底层下载救援，以及 CAT1 USB 下载能力各有独立硬件路径。客人若要求无线升级文件传输，需单独定义包型和入口，再接入现有产品 OTA 事务。

COM30 是这台电脑分配给 USB 串口的端口号。GR5526 当前采用 BLE GATT 服务，电脑配对后通常需要 BLE 客户端读取通知、写入命令。若客人要求原串口软件直接选择 COM 口，需要另交付 BLE 至虚拟串口桥接程序及虚拟串口驱动，或配套 USB-BLE 串口适配器。该部分需要按目标 Windows 版本验证安装、签名、权限和重连兼容性。

## 3. 推荐架构

```text
Windows BLE 工具 / 手机维护工具
          │ GUS 写入、通知、流控
          ▼
BLE 协议入口 ── 原有 FT 工厂协议
          │ 新的版本化维护帧
          ▼
会话鉴权 → 分包重组 → 命令权限及状态校验 → 有界命令队列
                                                   │ 主循环串行执行
                                                   ▼
                                       现有 CLI / 业务处理函数
                                                   │
                      UART 输出 ← 回应路由与日志分流 → BLE TX 队列
                                                        │
                                             分片、背压、发送完成处理
```

### 3.1 服务与协议

优先复用已有 GUS 的注册和连接管理，避免重复初始化同一个服务。由统一入口区分原 `FT` 请求和新维护协议，原工厂工具继续按旧语义运行。新协议增加版本、帧类型、会话及请求序号、载荷长度和分片信息，具体编码在实施时冻结。

帧类型至少区分命令、接收确认、命令结束、命令输出和异步日志。普通命令保持现有文本语法，PC 工具负责封装和重组。不能依靠提示符判断命令结束，也不能将所有异步输出归给最后一条命令。

GUS 的 Write Command 无 ATT 写回应，必须另发应用层接收确认。接收确认只表示完整命令进入队列，命令结束帧表示处理结束，业务完成仍按对应业务状态判断。具有副作用的命令在回应丢失后不得由工具自动重发，须通过请求去重或状态查询消歧。

首期保持单维护客户端。输入一条命令执行完成后再接收下一条，超出容量明确返回忙。UART 与 BLE 使用各自的行缓冲，统一进入串行执行入口，避免两个来源的半行混合。断线丢弃该会话未完成输入和待执行命令，已启动业务由原有状态机继续管理。

### 3.2 输出与日志

为 CLI 增加来源上下文及输出出口，UART 请求仍返回 UART，BLE 请求返回对应 BLE 会话。日志采用独立订阅和等级过滤，可选镜像到两端。盘点 `cli_printf()`、字符回显、APP_LOG 和直接 UART 输出，逐一确定归属。CAT1 异步回应保留其通道标识，不能用简单全局开关把任意输出都改发 BLE。

BLE 输出只向有界 RAM 队列复制数据，不等待无线发送。回调只拷贝接收数据并置事件，由主循环执行命令。发送端按当前 MTU、SDK 允许长度及实际流控分片，MTU 23 时先支持 20 字节载荷，MTU 247 时 ATT 通常允许 244 字节载荷，增加协议头后再扣除其长度。

命令回应与日志分开排队，回应优先。队列不足时降低或丢弃低优先级日志并报告丢弃计数，命令输出须提供明确截断/失败状态。客户端慢读或断线不得阻塞设备业务。RAM 预算及每轮处理字节数通过 map 和实测确定，先用小容量验证，避免直接加入大型日志缓存。

持续无线日志仅覆盖订阅期间的输出。复位到 BLE 可连接前的日志存在观察空窗，如需补读早期启动记录，应另评估小型保留缓冲及隐私策略。

### 3.3 权限

无线维护会扩大附近设备可访问的范围。首期按命令及子命令白名单开放，区分只读查询、正常参数设置及受限维护操作，不能按顶层命令名粗放放行，例如 `business` 同时具有状态查询和取消等不同语义。

建议保留物理维护动作和短时会话授权，再增加经验证的 BLE 加密与设备授权机制。物理按键负责开启维护窗口，授权应绑定当前连接，超时、断线或业务抢占即失效。仅打开通知不能视为鉴权。具体配对、密钥分发及无屏设备防冒用方式需按客户工具流程冻结。

擦除、清数据、身份/密钥、任意注入、强制复位、供电切换及 OTA 内部调试命令逐项审核。普通客户权限只开放满足使用目的的操作，高风险功能进入受控维修权限并继续经过原有安全门。日志输出需过滤密钥、Token、带鉴权 URL 和居民隐私数据。

## 4. 对 OTA 及既有功能的影响

信标扫描和 OTA 为本方案的两项重点风险，具体代码落点、保护机制、降级及验收分别见第 10、11 节。两项风险关闭前，无线维护功能不得按整机交付通过记录。

| 功能 | 可能影响 | 控制措施及验收要求 |
|---|---|---|
| GR/CAT1 产品 OTA | 日志和耗时 CLI 占用主循环，电源/复位命令干扰事务，新增 OTA 入口绕开 owner | 保持现有 owner/epoch、双端严格串行和提交门槛；OTA 时只开放审核后的轻量查询，停止批量日志及受限维护命令 |
| OTA 安装和重启 | BLE 断开导致工具误判失败并重复下令 | 工具区分离线、受理和实际完成，重连后查询真实版本及事务结果，避免自动重复副作用操作 |
| SOS/通话 | 大量通知或阻塞命令延迟报警、起呼和控制帧 | SOS、通话、业务控制优先，限制单轮维护工作量；报警时撤销维护写权限并暂停批量日志 |
| Beacon 定位 | BLE 连接事件挤占扫描窗口 | 保留扫描调度，不以停止定位换取吞吐；测连接前后命中率、样本累计及上报行为 |
| GR-CAT1 UART | 将无线入口误接到内部协议或占满 UART | BLE 命令仍走 GR 业务入口；转发命令遵循现有控制协议和调度，保留业务时隙 |
| 低功耗及续航 | 常连接、快速连接间隔、持续日志使 MCU 和射频活跃 | 默认关闭日志订阅，维护空闲超时，断线释放资源；不为 BLE 调试常开 CAT1，实测电流和睡眠恢复 |
| 参数及用户数据 | 新鉴权持久化、调试命令、重试造成误写 | 优先 RAM 会话；若需保存配对数据先核对 NVDS 容量及擦除边界；OTA/回退保留现有用户数据 |
| 墨水屏、充电、供电 | 无线维护命令触发大电流动作，与日志/连接峰值叠加 | 所有入口保留业务及电源门；涉及供电或提高峰值的实现先做预算，再按接电池/仅 USB 两种条件实测 |
| 原有 FT 工厂工具 | 改 GUS 接收回调后旧协议失效 | 统一分流、复用单实例服务，回归 FT 查询、解锁和既有受限操作 |

OTA 准入继续满足稳定静止、充电中、电量至少 70%、无报警及通话等条件，禁止通过 BLE 增加 Force 绕过。升级、回退和救援均不得清空或覆盖用户数据。

首期只提供 OTA 状态查询及经审核的既有控制能力。若要求通过 BLE 传固件，应作为后续独立阶段，将分片文件接入产品已有签名校验、暂存、任务互斥和安装流程。SDK 标准 DFU 示例需验证分区、包格式及 Boot 协议兼容性后才能考虑采用。

9. 每轮 OTA/串口测试前按项目红线确认 GR 正常运行，确认 CAT1 实际启动及版本回应。供电 ACK 或 VTref 只能作为局部证据。

## 10. 风险 R-BLE-01：维护连接影响信标扫描及具体落地方案

### 10.1 调度原则

信标扫描是产品定位业务，维护传输必须让出资源。BLE 可连接外设和扫描共存能力要按当前 SDK、控制器配置和实板验证，不能仅凭存在两套 API 判断吞吐与扫描质量。

推荐首先采用“扫描窗口保护 + 窗外发送日志”。默认扫描窗口按现有参数执行，例如基线为每分钟 2 秒，失锁退避继续按现有业务规则。扫描前停止提交新的批量日志通知，窗口内保留连接及必要的短控制消息，扫描结束再恢复受限日志。日志留在有界队列，积压时丢低优先级日志并计数。BLE 连接事件仍会占用射频，暂停日志不能保证整个窗口都由扫描独占。

实施时由扫描调度提供明确的开始、结束和实际扫描状态，维护层读取该状态，禁止维护层自行调用扫描启停来争夺资源。连接参数优先选择较宽松间隔，初始可用 50～100ms 作为实验候选，最终以控制器接受结果、交互时延和扫描命中率确定。扫描 interval/window 继续使用产品配置，不为日志提速缩短扫描窗口或延长业务扫描周期。

### 10.2 共存效果不足时的降级

1. 先进一步降低通知频率和每轮发送额度，关闭详细日志，只保留命令回应。
2. 若仍无法达到同板定位基线，则在扫描窗口前主动结束维护连接，通过维护协议预告暂停原因。扫描完成后恢复可连接广播，由工具重连，工具不得自动重发副作用命令。
3. 若扫描和广播共存仍不足，扫描期间暂停可连接广播，扫描完成后恢复。每次启停需核对真实完成事件和错误返回，避免软件标志与控制器状态分离。
4. 若以上仍不能满足定位要求，停止该实现交付，先解决控制器调度或需求冲突。持续在线且满速日志与定位保障之间的取舍需客户明确。

首期建议以“允许维护短暂中断，优先保住定位”为验收策略。定位扫描周期、失锁退避、已有样本及上报计数保持原业务语义。因无线维护占用而启动失败或被取消的扫描应记录为调度失败，安排有限重试，不能直接当作环境无信标而增加失锁次数。

### 10.3 当前代码需特别核实的点

`yp001_scan_sched.c` 的 `stop_scan()` 中当前可见 `ble_scanner_stop()` 调用被注释，软件仍会更新窗口状态。`start_scan()` 还对返回值 `0x0F` 作特殊接受。实施前必须结合扫描 timeout、SDK 错误码和停止事件核对控制器真实行为，明确“逻辑采样窗口”和“射频扫描状态”的区别。本轮未修改该逻辑，不能依据 `s_scanning` 单一标志承诺硬件已停扫或已成功启动。

### 10.4 专项验收

同一块板、相同信标位置和广播参数，分别记录未连接、连接空闲、连续命令及高日志压力场景。至少覆盖完整扫描窗口、扫描启动失败、失锁退避后重新命中、SOS 定位以及维护断线恢复。比较实际扫描起止、有效广播数、目标信标命中窗口比例、首次定位时延、样本及上报计数。具体允许偏差在实施前以基线冻结，未达到即启用上面的限流或断连策略。静态方案不能给出当前板的命中率保证。

## 11. 风险 R-OTA-01：维护操作干扰 OTA 及具体落地方案

### 11.1 统一仲裁

BLE 维护权限应读取现有产品 OTA 的完整事务状态，包括持久化 owner/epoch、组件、阶段和恢复状态，UART 与 BLE 都通过同一业务安全门。当前 `yp001_ota_power_change_allowed()` 可用于已有电源资格判断，但不能将它单独当作所有命令的 OTA 权限判据，需要逐项核对其实现与事务阶段。

新维护通道只传递已授权的业务请求，最终在主循环即将执行时再次检查。接收时允许、执行时已进入 OTA 的命令必须拒绝，防止排队跨越保护边界。所有副作用操作与 OTA 提交采用同一串行仲裁点，不能用“检查一次然后异步执行”留下竞争窗口。

### 11.2 按 OTA 阶段限制维护功能

| 产品 OTA 阶段 | BLE 维护策略 | 保护目的 |
|---|---|---|
| 无执行中事务 | 按权限开放已审核命令，日志限流 | 保留正常维护能力 |
| 仅有待处理目标、尚未获得执行 owner | 可轻量查询，副作用命令执行前重新仲裁 | 待升级记录与实际占用分开判断 |
| 下载、GR-CAT1 传输、写暂存区 | 仅缓存状态/版本/进度等轻量查询；关闭批量日志，拒绝 Flash/NV 写、扫描配置变更、AT 透传、电源和复位操作 | 避免主循环、Flash、UART 和业务状态竞争 |
| 预备完成、等待提交 | 继续保护包及事务，禁止维护命令制造充电资格或绕过提交门槛 | 保持现有安全提交条件 |
| 安装、交换、重启及不可中断阶段 | 提前通知工具，停止维护命令处理；默认结束维护连接，是否暂停广播按现有 OTA 实现确定 | 减少竞争，工具接受预期离线 |
| 试运行、健康确认、失败恢复 | 只允许经审核的缓存查询，禁止复位/断电和修改运行参数 | 防止维护动作破坏健康判断或恢复事务 |
| 事务确认完成或安全结束 | 再检查报警和业务状态，重新授权后恢复维护能力 | 避免旧会话权限自动恢复 |

轻量查询只读取已有状态，不在 BLE 回调里读取大块 Flash、遍历文件、访问慢速总线或触发 CAT1 网络请求。OTA 状态接口自身若会阻塞，需要先提供缓存快照。

### 11.3 已排队命令、资源及故障处理

- 进入 OTA 执行阶段时撤销维护写授权，拒绝尚未执行的副作用命令并回明确忙状态。已执行的业务操作需由仲裁确认到达安全点后，OTA 才可获得资源。
- OTA 控制帧、业务控制帧和 SOS 高于维护日志。BLE 发送不循环等待、不占用 UART4 的 OTA 缓冲、不复用 OTA 暂存区。发送失败只影响维护会话。
- 维护断线不取消 OTA、不清任务 NV、不复位模块、不重新申请另一端 OTA。恢复连接后按真实事务查询进度。
- OTA 发生故障时保留错误和恢复状态。BLE 不能自动下发清锁、强制重启、格式化或重新初始化用户数据命令。
- 未来若增加 BLE 传固件，必须申请同一个产品 OTA owner，经过同样的包身份/签名、版本、存储边界、数据兼容和提交资格检查，禁止与 CAT1 组件后台并行传包。

### 11.4 与紧急业务的关系

下载及可暂停阶段仍按现有产品设计让出 SOS/通话/运动业务。安装中真正不可中断的 Flash/Boot 阶段须按当前 OTA 实现验证其不可用时间和中断边界，BLE 方案不能凭软件优先级承诺整个安装过程即时响应报警。维护通道不得扩大该窗口，须通过前后对比确认。

### 11.5 专项验收

对 GR OTA 和 CAT1 OTA 分别在下载、传输、等待提交、安装、健康确认和恢复阶段发送查询、供电、复位、参数写、AT 透传和重复请求，检查允许/拒绝是否符合矩阵。特别测试命令已接收未执行时 OTA 抢占，以及维护断线发生在提交前后。记录真实版本、owner/epoch、结果及用户数据一致性。涉及受控复位、掉电和烧录的故障测试须另行授权。

本次补充仍为设计方案，尚未落地上述仲裁、扫描保护和分阶段权限，也未执行实板或 OTA 测试。

## 13. 后台厂测、老化及批量指令的风险与落地方案

SAM | 2026-11-04 +08:00 | 补充厂测/老化任务管理，细分维护断线语义，防止长任务丢失及重复执行。

### 13.1 适用范围与待确认入口

后台需要下发多种厂测、老化及控制指令，采用统一命令调度和明确的厂测模式管理。当前尚未确认下发通道为 CAT1 平台、BLE 厂测工具或两者兼有，本节先规定设备内部行为。实施时分别核对现有平台协议和 BLE 维护协议，未批准的任务字段不能直接加入生产平台消息。

本节为设计方案，尚未证明当前固件已具备任务队列、任务去重及完整厂测模式。

### 13.2 运行模式及资源占用

| 模式 | 运行规则 | 进入及退出要求 |
|---|---|---|
| 正常产品模式 | 保持 SOS、定位、低功耗和产品 OTA 规则；受限厂测命令需拒绝或先进入授权模式 | 默认运行模式，不能因收到任意厂测字符串自动切换 |
| 厂测模式 | 按项目执行按键、屏幕、音频、CAT1 等测试；明确上报模式、当前项目及结果 | 授权进入、业务安全检查、记录资源占用；退出时恢复运行配置 |
| 老化模式 | 设备端执行指定循环、时长和终止条件，周期报告进度 | 授权启动、供电检查、限定执行计划；支持查询和安全停止 |

正常产品模式继续采用用户已确认的定位和 OTA 优先策略，必要时允许维护连接短暂中断。厂测/老化模式若测试需要暂停定位或改变正常业务行为，必须在逐项测试计划中明确并取得用户确认，不能将进入厂测模式解释为任意关闭 SOS、定位或安全门的授权。

### 13.3 指令分类及处理

| 指令类别 | 调度方式 | 保护要求 |
|---|---|---|
| 版本、状态、测试进度查询 | 读取缓存状态，优先回应 | 限制查询频率，不触发额外长耗时操作 |
| 屏幕、喇叭、按键等单项测试 | 校验模式及资源后入有界队列，串行执行 | 拒绝与当前业务或测试资源冲突的请求 |
| 循环刷屏、循环播放等老化任务 | 一次下发建立设备端任务，由设备推进测试步骤 | 限定次数/时长及终止条件，提供进度和停止入口 |
| 供电、重启、参数写及身份相关操作 | 单独授权并在实际执行前检查业务及 OTA 状态 | 不允许借厂测通道绕过数据保护、电源预算和升级安全门 |
| 停止测试 | 高优先级控制请求 | 在当前步骤可安全中断的位置停止，保留结果并释放资源 |
| 产品 OTA | 与资源冲突的厂测/老化任务互斥 | 先停止受理新的冲突测试，待当前测试安全退出并释放资源，再按原 OTA 条件授予 owner |

停止指令不排在普通测试长队列末尾。涉及 Flash 写入、受控断电等不可立即中断步骤时，先返回停止已受理，达到安全点后再报告已停止。工具收到停止受理后应持续查询最终状态。

### 13.4 请求编号、排队及结果

内部任务至少具有来源、权限、请求唯一标识、操作及参数、资源需求、状态和结果。具体线上编码按已有协议核对后冻结。

建议状态流转如下。

```text
接收 → 校验 → 已受理/排队 → 执行中 → 成功/失败/已停止
          └→ 拒绝并给出原因
```

- 接收确认表示设备收到完整请求，已受理表示设备接管该任务，两者需与执行完成区分。
- 唯一标识应带来源或授权客户端命名空间，结合操作及参数摘要去重。相同标识、相同内容返回已有任务状态，相同标识、不同内容应拒绝。
- 队列有明确容量和背压，满时返回忙及可查询状态，禁止静默覆盖旧请求。
- 后台收到已受理后通过查询或事件获取执行结果。网络/BLE 重连不能直接重放整批副作用命令。
- 长时间无执行进度时按测试项目的超时策略结束或进入故障状态，记录失败步骤，禁止无限重试供电、复位或擦写操作。
- 去重记录的保留范围与任务恢复策略一致。若跨重启没有可靠记录，设备应明确报告状态未知，工具先查询、核对实物或人工处置，不能假定任务从未执行。

### 13.5 断线与复位语义

本节细化第 3 节交互维护会话的清理规则。

| 情况 | 设备行为 | 工具行为 |
|---|---|---|
| BLE 半条命令尚未完整接收 | 丢弃会话输入，不执行 | 重连后可重新提交完整请求 |
| 会话型交互命令尚未受理或已明确取消 | 清理该会话待处理输入，并使旧授权失效 | 获取新会话授权，查询受理状态后决定下一步 |
| 厂测/老化任务已正式受理 | 生命周期由任务管理器负责，断线后按已声明的测试策略继续或安全停止；不能仅因清理连接队列而丢失 | 重连查询同一任务标识，显示进度及最终结果 |
| BLE 为信标扫描或 OTA 策略主动中断 | 按维护断连处理，任务仍遵循资源仲裁和状态机 | 显示暂停连接原因，重连后查询 |
| 异常复位 | 启动后重新检查供电、业务和 OTA 恢复状态，再按项目策略报告中止或恢复 | 不自动重新启动老化或重复执行副作用步骤 |

首期建议老化任务在连接断开后由设备继续执行。对于必须保持人员监护或主机心跳的项目，应明确配置为失联后安全停止，并在受理时告知工具。跨复位自动继续不作为首期默认行为，需在测试计划中单独批准。

若要保证“已受理的任务及结果”跨重启可查询，需设计独立、低频、可原子更新的任务记录。写入前核对存储布局、擦除边界、磨损及掉电恢复，不能占用 OTA 暂存、Boot journal 或用户参数区域。未具备该能力时，协议必须明确仅保证当前上电周期内的任务记录。

### 13.6 与 OTA 保护衔接

厂测任务和产品 OTA 共享资源仲裁入口。OTA 不只检查命令队列，还需检查已启动的设备端任务及其外设占用。

1. OTA 准备获得执行资源时，禁止新增冲突测试，向正在运行的任务请求安全停止。
2. 任务达到安全点、保存必要结果并释放资源后，OTA 才可获得执行资格。超时未退出时保留待升级目标并报告阻塞原因，不能强制复位或断电抢占。
3. OTA 已持有执行 owner 时，厂测/老化启动、电源控制、参数写和透传等请求按第 11 节拒绝；仅开放已审核的轻量查询。
4. OTA 安装及健康确认期间，工具接受预期离线，重连后查询 OTA 和任务实际状态。厂测任务不得自行恢复并抢占健康确认。
5. OTA 安全结束后，旧老化任务不自动重启，重新检查模式、权限和资源，再由明确请求启动。

厂测或老化模式不会降低稳定静止、正在充电、电量至少 70%、无报警及通话等产品 OTA 门槛，也不会授权修改用户数据或清除升级恢复信息。

### 13.7 电源及生产使用风险

循环刷屏、喇叭、CAT1 上电/联网/发射可能叠加峰值电流。每个测试计划需列出资源及电流预算，优先避免未经验证的峰值动作重叠。按项目红线分别验证接电池和仅 USB/电池读数异常情形，每种至少经历规定峰值并连续观察 10 分钟无复位。

进入及退出测试模式时保存并恢复临时运行配置。测试结果与产品参数分开存储，不将测试次数、临时音量、扫描策略等写回正式配置。测试退出或故障中止后需核对 CAT1、音频、屏幕及睡眠状态。
