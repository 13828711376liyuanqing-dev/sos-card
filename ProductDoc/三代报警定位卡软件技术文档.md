# 三代报警定位卡 软件技术文档

> 本文档基于《三代报警定位卡 产品需求文档（PRD V0.2）》与《三代卡与 IOT 平台的协议（V1.2）》编写，描述设备的软件架构、功能模块、通信协议与关键策略。

## 1. 文档概述

### 1.1 目的
定义三代报警定位卡的软件总体设计、各功能模块行为、与 IOT 平台的通信协议及数据格式，为固件开发、联调与测试提供依据。

### 1.2 参考文档

### 1.3 术语
| 术语 | 说明 |
|------|------|
| 活动态 | 由三轴运动**或按键事件**唤醒后的工作状态：蓝牙按策略扫描；**Cat.1 保持供电并运行于低功耗模式**（已注册网络、具备收发能力），仅在需要传输数据 / 发起 VoIP 时自动切到常规模式，传完自动回低功耗模式 |
| 静止态 | Cat.1 硬断电（0 电流）、蓝牙低功耗睡眠、由三轴传感器中断唤醒的休眠状态 |
| 低功耗模式 | Cat.1 子模式：保持网络注册与收发能力、功耗最低的待机态；采用 eDRX/轻睡并保留下行监听，平台下行指令可即时到达 |
| 常规模式 | Cat.1 子模式：进行实际数据收发 / VoIP 通话时的全功能态 |
| beacon | 园区 Seekcy iBeacon，UUID `1918FC80-B111-3441-A9AC-B1001C2FE510`，以 Major/Minor 标识 |
| {deviceid} | 设备唯一标识（建议取通信模组 IMEI） |
| {product} | 固定为 `WARNCARD3` |

## 2. 系统总体设计

### 2.1 硬件平台
| 部件 | 说明 |
|------|------|
| 蓝牙 SoC（应用主控） | **汇顶 GR5512（Goodix）BLE SoC**，自带 MCU，常驻低功耗运行，承担全部应用逻辑；扫描园区 iBeacon、驱动外设。芯片选型已确认。 |
| Cat.1 通信模组 | 4G 数据通道；承载 MQTT 与 VoIP（数据面）；由蓝牙经 GPIO→MOSFET 控制供电：**静止态硬断电（0 电流）**，**活动态保持供电并运行于低功耗模式**（传输时切常规模式） |
| 无源 NFC | 复旦微电子 CPU 卡 1208-10，餐饮消费与门禁；无源，不消耗设备电池；与 BLE/Cat.1 无事件关联 |
| 三轴加速度传感器 | 运动检测，驱动状态机切换与唤醒（挂载蓝牙侧） |
| 墨水屏 | 27 × 27 mm 正方形，厚度约 1mm（对角线约 1.5″）；挂载蓝牙侧 |
| 电池 | 500mAh |
| 双按键 | 左、右键；报警需双键同按；挂载蓝牙侧 |
| 喇叭 | 1511 型小功率优先（2512 备选）；通话外放约 70dB；**位于 Cat.1 侧** |

> **模组角色**：蓝牙 SoC（汇顶 GR5512）为**应用主控**（自带 MCU，常驻低功耗），挂载三轴、墨水屏、无源 NFC、双按键、充电管理；Cat.1 为**受控外设**，仅负责数据上传与 VoIP，由蓝牙经 GPIO→MOSFET 控制供电：**静止态硬断电（0 电流），活动态保持供电并运行于低功耗模式**（详见第 3、4 章）。

### 2.2 软件总体架构
系统由两套固件构成，通过 UART 交互（见 4.4）：
- **蓝牙主控固件（BlueHost）**：常驻运行，实现应用状态机、外设驱动、串口主机协议与电源调度。
- **Cat.1 从机固件（CatSlave）**：按需运行（仅 Cat.1 上电期间），实现 MQTT 客户端、VoIP 栈、HTTP OTA、串口从机协议、NTP 校时。

### 2.3 任务 / 线程划分（建议）

**蓝牙主控侧（常驻）**
| 任务 | 职责 | 优先级 |
|------|------|--------|
| 主业务任务 | 状态机调度、电源调度、报警编排 | 高 |
| 蓝牙扫描任务 | iBeacon 扫描、解析、上报计数 | 中 |
| 三轴中断任务 | 运动检测、唤醒（中断） | 高（中断） |
| 屏显任务 | 墨水屏刷新、IMEI 查询 | 低 |
| 外设任务 | 按键检测、充电管理 | 中 |

**Cat.1 从机侧（仅上电期间）**
| 任务 | 职责 | 优先级 |
|------|------|--------|
| 网络 / MQTT 任务 | 注册、连接、收发、重连、心跳 | 高 |
| VoIP 任务 | 通话建立、媒体、挂断 | 高 |
| OTA 任务 | HTTP 下载、Md5 校验、自升级 | 中 |
| NTP 任务 | 校时并回传蓝牙 | 低 |

### 2.4 资源与约束
- 整机尺寸底线 ≤ 105 × 60 × 7 mm；重量目标 45–48g（最终阈值待 8/19 会议）。
- 续航 ≥ 7 天（每日 8h 工作 + 16h 休眠），由双状态机实现。
- 防水 IP68，整机不可拆卸，不引入佩戴/离体检测。

## 3. 系统拓扑与状态机（核心）

### 3.1 双模组拓扑
设备由两颗可独立供电的模组构成，分工如下：
- **蓝牙 SoC（常驻主控）**：自带 MCU，始终带电（低功耗运行），承担全部应用逻辑与对外设的控制；是系统的"大脑"。
- **Cat.1（按需从机）**：仅负责 4G 数据通道（MQTT 上传）与 VoIP 通话（模组内置 VoIP 能力）；由蓝牙 SoC 通过 **GPIO 控制 MOSFET 供电**：静止态**硬断电**（0 电流），活动态**保持供电、运行于低功耗模式**（传输数据时自动切常规模式，见 3.2）。

**外设归属（均挂载蓝牙 SoC 侧）**：三轴加速度传感器、墨水屏、双按键、充电管理；无源 NFC 为例外——为被动元件，与 BLE/Cat.1 无事件关联，不触发设备软件逻辑（不联动状态机/上报）。
原因：若任一运动/唤醒相关外设挂在 Cat.1 侧，Cat.1 须常开，低功耗模型失效。

```
                ┌─────────────────────────────────────┐
                │       蓝牙 SoC（汇顶 GR5512）         │← 常驻低功耗·应用主控
                │   状态机 / 电源调度 / 外设驱动         │
                └───┬──────────┬──────────┬────────┬───┘
        ┌──────────┘          │          │        └──────────┐
     三轴传感器            墨水屏      双按键      无源 NFC(复旦微1208-10)
   (运动/唤醒)          (姓名/电量/       (报警/IMEI   (餐饮/门禁,
                        通话态显示)       查询/挂断)   无源不耗电)
                    │
                    │ GPIO→MOSFET 控制供电
                    │ (静止态硬断电 / 活动态低功耗模式)
                    ▼
            ┌──────────────────┐
            │   Cat.1 从机       │← 活动态供电·低功耗模式(传输时切常规模式)
            │  MQTT / VoIP /     │   喇叭(约70dB)在 Cat.1 侧
            │  OTA / NTP         │
            └──────────────────┘
```

### 3.2 工作模式与状态机
设备有两类顶层模式，报警为跨模式的紧急流程：

1) **正常模式（蓝牙主机 / Cat.1 从机）**
   - 蓝牙常驻低功耗，按三轴与扫描策略运行；
   - **Cat.1 供电与子模式**（关键修正）：进入活动态后 Cat.1 **保持供电**，先进入**低功耗模式**（已注册网络、具备收发能力，采用 eDRX/轻睡并保留下行监听，平台下行的『一键寻人』等指令可即时到达）；当蓝牙需要上传数据 / 发起 VoIP 时，Cat.1 **自动切到常规模式**完成收发，结束后**自动回低功耗模式**；进入静止态时蓝牙才切断 Cat.1 供电（硬断电）。
   - 即活动态内 Cat.1 **不随单次业务硬断电**，仅在"低功耗 ↔ 常规"之间切换。
   - **三轴与"是否在使用"的对应关系（关键）**：三轴**有数据（运动状态）**时设备**才可能被使用**（报警 / VoIP / 定位的关键期，绝不可中断）；三轴**无数据（静止休眠）**时设备按业务进入休眠、**此时无人使用**——这正是 OTA 提交（翻转重启）等维护操作的天然安全窗口，重启对用户完全无感。
2) **OTA 升级（蓝牙常驻主控编排，无角色翻转）**
   - 升级**不是独立顶层模式、不发生主从角色翻转**：蓝牙 SoC 始终为系统主机，升级作为"正常模式"内的子流程被蓝牙主控编排。平台在设备上线并上报版本后依据 **auto-OTA 参数** 决策推送 OTA 目标（见 4.3）；设备自调度完成"活动态后台预置 → 安全静止窗提交"的无感升级，全程不阻塞用户、平台零人工。Cat.1 在该子流程中仍是从机（仅充当 4G 下载通道与 UART 传输管道），蓝牙主控负责编排下载、写盘与提交。

状态迁移（聚焦 Cat.1 供电与子模式）：
```
        ┌── 三轴/按键唤醒(从静止) ──┐
        ▼                    │
   [静止态] ──无运动满5min──▶ [休眠前 offlineMsg] ─▶ [静止态: Cat.1硬断电(0电流), BLE低功耗]
        ▲                  │                       (三轴中断 → 给Cat.1上电注册 → 活动态)
        │ 三轴检测到运动     │
   [活动态: Cat.1上电→注册→低功耗模式] ◀─┘
        │
        │  需传数据/VoIP → 自动切【常规模式】→ 传完回【低功耗模式】(循环, 不硬断电)
        │
        └── 无运动满5min ──▶ (↑ 休眠流程)

   任意态 + 双键长按3s ─▶ [报警: 强制Cat.1切常规模式(静止态则先上电) → 优先sosMsg+VoIP+位置上报 → 报警后再走上线流程] ─▶ 恢复原态
```

### 3.3 进入 / 退出动作
| 迁移 | 触发 | 进入动作 | 退出动作 |
|------|------|----------|----------|
| 静止→活动 | 三轴检测到运动 **或 按键事件**（双键报警 / IMEI 查询等） | 蓝牙 GPIO 给 Cat.1 上电；Cat.1 注册网络+MQTT，随后进入**低功耗模式**（保持注册、可收发）；发布 `onlineMsg`（版本+电量+位置，**不携带 auto-OTA**）；**平台随即 `paraSetMsg(CmdType=0 查)` 查询参数，据结果决策是否下发 `paraSetMsg(设)` / `otaMsg`**（上线流程见 4.3.1） | — |
| 活动→静止 | 无运动满 5min | **先以 `periodicMsg` 清空缓存 beacon**（若累计 < 60 次）；再发布 `offlineMsg`（电量+位置）；蓝牙 GPIO 切断 Cat.1 供电（**硬断电**）；BLE 进入低功耗睡眠 | 保存失锁计数、扫描累计次数等状态变量（蓝牙 Flash） |
| 静止→报警（SOS 睡眠） | 双键长按 3s（静止态） | 蓝牙检测按键→**先给 Cat.1 上电联网**→**优先**上报 `sosMsg`+发起 VoIP（单次拨打，不重拨）+`sosLocationMsg`（均待平台确认）；报警处理完**再走上线流程**（onlineMsg + 平台参数查询）→ 进入活动态 | 报警取消（用户长按/平台）后恢复原态与 Cat.1 子模式 |
| 活动中→常规模式 | 蓝牙需上传数据 / 发起 VoIP | Cat.1 自动由低功耗模式切到**常规模式**完成收发 | 业务完成自动回低功耗模式 |
| 任意（活动态）→报警 | 双键长按 3s | 强制 Cat.1 切到**常规模式**联网；启动 VoIP（单次拨打，不重拨）；上报位置 | 报警取消（用户长按/平台）后恢复原态与 Cat.1 子模式（活动态回低功耗模式） |
| 正常态内 OTA 子流程 | 平台推送 `otaMsg`（目标版本）；**蓝牙主控全程编排，不发生主从角色翻转** | 见 4.3：活动态空闲后台预置（蓝牙写 A/B 非活跃分区、Cat.1 写常规分区）→ 安全静止窗"翻转重启"提交；全程不阻塞用户 | 升级完成重启回正常模式；清除 NV |

### 3.4 跨状态保持的变量（存于蓝牙 Flash）
- 蓝牙**失锁计数**（连续扫描不到 beacon 的次数，用于扫描间隔递增/恢复）。
- 蓝牙**扫描累计次数**（达 60 触发周期上报；休眠不清零，唤醒续计）。
- 当前 beacon 列表（最近 ≤5：Major/Minor/Rssi）。
- 电量、绑定电话参数、平台下发的 MQTT/OTA 地址等。

## 4. 功能模块设计（按模组职责划分）

> 系统采用**蓝牙常驻主控 + Cat.1 按需从机**的拓扑（见第 3 章）。本章按模组拆分职责，跨模组流程单列。

### 4.1 蓝牙主控模块（BlueHost，常驻）
蓝牙 SoC 为系统主控，始终低功耗运行，承担全部应用逻辑与对外设的控制：

| 子模块 | 说明 |
|--------|------|
| 应用状态机与电源调度 | 实现 3.2 状态机；决策 Cat.1 供电子模式：活动态保持供电并令其运行于**低功耗模式**、传输数据时切到**常规模式**、传完回低功耗模式；静止态切断供电（GPIO→MOSFET **硬断电**）；位置上报触发：蓝牙扫描累计 60 次上报一次（清零），**休眠前先以 `periodicMsg` 清空缓存 beacon、再发 `offlineMsg`（电量+位置）**，每次上报携带电量，电量 <10% 停止周期上报（保留报警/上线） |
| 三轴采集与静止判定 | 三轴中断唤醒（挂载蓝牙侧）；无运动满 5 min 触发休眠 |
| BLE 扫描与解析 | Seekcy iBeacon 扫描（默认 1 min/次，频率递增/恢复见 6.1），解析 Major/Minor/Rssi |
| 墨水屏显示 | 姓名/房号、电量、信号、欠费、通话态、IMEI 查询；事件驱动刷新（挂载蓝牙侧） |
| 无源 NFC（被动元件，非软件任务） | 复旦微 1208-10，餐饮/门禁；刷卡灵敏 ≥ 99%；无源、不耗设备电池，与 BLE/Cat.1 无事件关联（不纳入外设任务调度，见 1.2 外设归属） |
| 双键检测 | 双键同按 3s 报警；连续按查 IMEI；通话中长按挂断（挂载蓝牙侧） |
| 本地缓存与参数 | Flash 缓存待补报数据、平台下发参数（MQTT/OTA 地址、绑定电话等）、跨状态保持变量（失锁计数/扫描累计/beacon 列表） |
| 报警指示 | **屏幕显示**（BLE 侧墨水屏）+ **语音播报**（由蓝牙下发播放指令、Cat.1 侧喇叭播放，见 4.2）；无蜂鸣器/指示灯/马达震动（8/14 会议移除震动） |
| 低电量提醒 | 电量 **< 25%** 主动提醒（设备提示 + 发布 `lowBatteryMsg`） |

### 4.2 Cat.1 从机模块（CatSlave，活动态供电）
Cat.1 在活动态保持供电（运行于**低功耗模式**），由蓝牙指令驱动在**低功耗 ↔ 常规**模式间切换，作为数据 / 语音外设：

| 子模块 | 说明 |
|--------|------|
| 上电注册 | 进入活动态时上电注册 4G 网络 + MQTT（地址/账号见 5.1），就绪后回"已上线"给蓝牙；随后进入**低功耗模式**（保持注册、可收发、保留下行监听） |
| 数据上传 | 执行蓝牙指令，发 `periodicMsg` / `onlineMsg` / `offlineMsg` / `sosMsg` / `sosLocationMsg` / `lowBatteryMsg` 等（见 5.4） |
| VoIP | 由 **Cat.1 模组内置**的 VoIP 能力实现（底层信令 / RTP / codec 由模组完成，设备侧无需关注）；设备仅需向模组配置 **服务器地址、账号、密码**（由平台参数下发），并下发拨打号码（来自 `phoneBindMsg`，`CallOut` 为必须配置）；**单次拨打，不主动重拨（无论对端是否接听）**；双向挂断（用户/对端均可）；外放约 70dB；呼入白名单（`CallInList`，最多 5 个）**建议配置**以规避骚扰电话，**`CallInList` 缺配（为空）时接受所有来电**（不限制呼入） |
| 语音播报 | **报警/挂断等语音提示均由 Cat.1 侧喇叭播放**；蓝牙通过串口下发"播放指定提示音"指令；通话状态经串口异步回传蓝牙用于屏显 |
| HTTP OTA 下载 | 下载升级包（见 4.3）；下载期间保持**常规模式**（持续数据收发） |
| NTP 校时 | Cat.1 **每次上线**经 NTP 校时并将时间矫正**蓝牙侧 RTC**；全设备统一使用**蓝牙 RTC 时间**（见 8） |
| 串口从机协议 | **需回传**：通话状态（呼出中/接通/挂断/未接/无应答）、VoIP 挂断事件、校时结果、上传结果、OTA 进度，供蓝牙屏显与编排 |

> 说明：VoIP 为 Cat.1 模组内置能力，设备侧只负责把平台下发的 **服务器地址、账号、密码** 配置给模组、并下拨打号码；底层信令/RTP/codec 由模组实现，无需在本文档中展开。

> **VoIP 与 VoLTE（默认 VoIP）**：Cat.1 模组可同时具备 VoIP 与 VoLTE 两种语音能力，但二者**互斥**——同一时刻仅一种语音通道生效（不可并行）；**默认启用 VoIP**，VoLTE 作为保留能力并存，运行时仅启用其一；报警 / 通话统一经当前生效的语音通道（默认 VoIP，详见 PRD「语音通道（默认 VoIP，VoLTE 保留）」约束）。
>
> **呼入白名单**：`phoneBindMsg` 下发的 `CallInList`（≤5）为呼入白名单，仅允许白名单号码呼入以规避骚扰；**若 `CallInList` 为空（缺配），设备接受所有来电**（不限制呼入）。

### 4.3 OTA 升级（蓝牙常驻主控编排，无角色翻转）

OTA 采用"**平台决策目标 + 设备无感自调度执行**"模型：设备上线主动上报版本与参数，平台依据 **auto-OTA 参数** 决定是否检查版本并向设备推送升级目标；**设备侧不再区分"立即/自主"模式，而是按自身状态机自调度**——在活动态空闲时后台预置、在安全的静止窗口提交，全程不阻塞用户、平台零人工介入。**本过程由蓝牙 SoC 常驻主控全程编排，不发生主从角色翻转：蓝牙始终是系统主机，Cat.1 仅作为 4G 下载通道与串口传输管道。**

#### 4.3.1 触发与版本检查（平台侧决策）
- 设备上线（见 3.3 静止→活动）：蓝牙 GPIO 给 Cat.1 上电注册，随后发布 `onlineMsg` 主动上报 **当前版本号、电量、位置**（**不携带 auto-OTA 字段**——auto-OTA 为平台经 `paraSetMsg` 下发的设备参数，平台已存有，无需设备每次上线重复上报）。
- **平台每次上线都主动下发 `paraSetMsg(CmdType=0 查)`** 查询设备参数，设备回 `paraSetReplyMsg`；平台据此**确认是否需更新参数 / OTA**（详见 5.3 / 5.4）。
- 平台依据 auto-OTA 决策（auto-OTA 为 `paraSetMsg` 下发的设备参数，见 5.6，默认 1）：
  - `auto-OTA = 1`（默认）：平台 **主动做版本检查**——若存在"可基于当前版本升级"的新版本，则 **主动** 向设备推送 `otaMsg`（含当前版本、目标版本、下载地址、Md5）。
  - `auto-OTA = 0`：平台 **不主动推送** OTA 命令（设备仅上报版本，用于需人工 / 白名单管控升级节奏的场景）。
- 注：auto-OTA 语义为"是否开启平台主动推送"，**1 表示开启平台主动推送**（命名与取值方向一致，避免歧义）。

#### 4.3.2 OTA 命令（otaMsg）与无感自调度
`otaMsg`（下行）字段：`CurrentVersion`（设备当前版本）、`TargetVersion`（目标版本）、`Address`（整包 HTTP 地址）、`Md5`（整包校验）。升级触发时机与电量门槛**不**由平台指定，统一由设备自调度（见 4.3.3）；电量门槛阈值为端侧固定常量 `OtaBatteryThreshold` = 70%（非平台下发，见 5.6）。

设备收到后先回 `otaReplyMsg`（`otaReply=success`，指令完整），将 `TargetVersion` 持久化至 NV，随后由设备 **自调度** 完成"预置 → 提交"两段式升级：

```
设备侧                                  平台侧
  │── onlineMsg(版本,电量,位置) ───────▶│   上线主动上报(不含 auto-OTA 字段)
  │                                   │
  │              [auto-OTA=1] 检查版本并推送
  │              (平台依据 paraSetMsg 下发的参数)
  │                                   │   存在可升级新版本?
  │◀── otaMsg(CurrentVersion,        │   是 → 推送(只给目标,不指定时机)
  │         TargetVersion,           │
  │         Address,Md5) ────────────│
  │── otaReplyMsg(otaReply=success,  │   指令回执
  │         写NV)──────────────────▶│
  │                                   │
  │ 〔活动态·eDRX 空闲间隙〕            │
  │   后台下载整包 → 蓝牙写 A/B 非活跃分区; Cat.1 写常规分区  │   ← 设备全程可用,报警/VoIP 零影响
  │   (HTTP Range 断点续传;三轴中断即   │
  │    暂停,下次续传)                  │
  │                                   │
  │ 〔稳定静止态 且 充电中 且           │
  │    电量≥70%(端侧固定阈值) 且          │
  │    无报警进行中〕                  │
  │   仅"翻转重启"数秒 → 新固件生效    │
  │── otaResultMsg(Status,Version,   │   平台自动确认
  │         Time)──────────────────▶│
  │   失败 → 蓝牙 A/B 回滚 / Cat.1 重推 → 平台自动重推   │
```

#### 4.3.3 无感自调度升级流程
设计目标：**对用户功能使用零影响（无感） + 平台零人工介入（自动化）**。将"下载写盘"与"切换生效"彻底分离：

1. **指令接收与持久化**：设备收到 `otaMsg` 后将 `TargetVersion` **写入 BLE 侧 NV（Flash）** 持久化（跨 Cat.1 硬断电保留），并立即上报 `otaReplyMsg`（已收到并记录升级指令）。
2. **预置阶段（活动态空闲完成）**：Cat.1 处于活动态低功耗模式（eDRX 可达）且有空闲间隙时，经 HTTP 从 `Address` **后台下载整包**；**蓝牙镜像写入自身 A/B 非活跃分区**、**Cat.1 自身镜像写入常规升级分区（非 A/B）**（Cat.1 不采用 A/B 双分区）。此阶段活跃分区照常运行，**报警 / VoIP / 定位全程可用**；下载支持 **HTTP Range 断点续传**，若三轴检测到运动（用户可能要用设备）则暂停下载，下一个空闲间隙续传。
3. **提交阶段（安全静止窗触发）**：当设备进入 **稳定静止态** 且 **设备处于充电中** 且 **电量 ≥ `OtaBatteryThreshold`（端侧固定常量 = 70%，非平台下发）** 且 **无报警进行中** 时，才执行"翻转重启"数秒，切换到新分区使新固件生效。选静止态提交的深层原因：三轴无数据时设备已进入休眠、**无人使用**，重启对用户完全无感；叠加"充电中 + 高电量门槛"，进一步确保升级不消耗在用电池、不打扰用户（`充电中` 由蓝牙侧充电管理感知，静止态 Cat.1 硬断电但 BLE 充电管理仍在线）。`无报警进行中` 在静止态天然成立（Cat.1 已硬断电，不可能有进行中的报警），此处作为防御性校验保留。因预置已在活动态完成，静止态仅承担极短的重启窗口，随后即进入 0 电流深度休眠。
4. **无需升级 / 版本已是最新**：若 `TargetVersion ≤ 当前版本`（如已被其他途径升级），直接清除 NV 目标版本，不执行升级。

#### 4.3.4 升级执行（下载 / 写盘在 A/B 非活跃分区）
1. **下载与校验**：Cat.1 经 HTTP 从 `Address` 下载整包（含 Cat.1 自身镜像 + 蓝牙镜像），校验 **Md5 + 签名**；蓝牙镜像写入 **A/B 非活跃分区**，Cat.1 自身镜像写入常规升级分区（非 A/B）。
2. **Cat.1 自升级**：Cat.1 将自身镜像写入 **常规升级分区**（单分区，重启生效；失败重推，不采用 A/B）。
3. **蓝牙固件写入（蓝牙主控编排，Cat.1 仅作串口管道）**：预置阶段 Cat.1 经 HTTP 下载整包后，由 **蓝牙主控** 通过串口向 Cat.1 取流，将蓝牙镜像写入自身 **非活跃槽**（蓝牙对自身 Flash 拥有写入权，是自身升级的主导方；Cat.1 仅作为串口传输管道，不接管系统主控）；蓝牙固件 **A/B 双分区**，升级失败或过程中断电可回滚至旧分区，**拒绝成砖**。
4. **完成（仅重启生效）**：上述写盘全程不中断用户；仅在 4.3.3 提交阶段执行一次"翻转重启"使新分区生效 → 重启回正常模式；上报新版本（`otaResultMsg`）；清除 NV 目标版本。

#### 4.3.5 关键变量与可靠性
- **NV（BLE Flash）**：持久化升级的 `TargetVersion`，跨 Cat.1 硬断电保留；升级完成或判无需升级即清除。
- **分区与回滚**：蓝牙固件支持 A/B 双分区回滚；Cat.1 固件仅常规升级（单分区，重启生效，失败重推），不采用 A/B；写盘始终在非活跃分区（蓝牙）/ 常规分区（Cat.1），**活跃分区全程服务用户**；签名校验；`otaResultMsg` 回报结果。
- **失败重推**：下载 / 刷写失败回滚旧分区，`otaResultMsg` 回报 Status=fail，平台可自动重推 `otaMsg`（无需人工）。
- **无感保障**：仅"翻转重启"为短暂不可用窗口，且被约束在**静止态**（设备无人使用、天然安全，而非"小心翼翼避开用户"）；静止态不再为 OTA 引入周期性 RTC 唤醒，保持 0 电流纯三轴唤醒睡眠。

### 4.4 模块交互接口（蓝牙 ↔ Cat.1 串口）
- **物理层**：UART，建议波特率 115200，可选硬件流控。
- **帧格式**：【后续补充】命令 / 响应 / 异步事件帧的字节级定义留待协议章节细化；本章先**冻结接口语义（框架）**，确保两端开发可并行：
  - 蓝牙→Cat.1：上电完成确认、上传指令（消息类型+载荷）、发起/挂断通话、播放语音提示、校时请求；
  - Cat.1→蓝牙（**需回传**）：已上线、通话状态（呼出中/接通/挂断/未接/无应答）、VoIP 挂断事件、校时结果、上传结果、OTA 进度。
  - 说明：屏在蓝牙侧而语音/通话在 Cat.1 侧，故"通话状态回传"与"语音播放指令下发"是必选接口，缺一则屏幕无法显示通话态。
- **电源时序**：
  - 进入活动态（从静止态唤醒）：蓝牙 GPIO 拉高 → Cat.1 供电压稳 → Cat.1 自启 → 注册网络/MQTT（AT 握手）→ 进入**低功耗模式**。
  - **活动态内传输完成**：Cat.1 由常规模式**自动切回低功耗模式**（不硬断电）。
  - 进入静止态：断开 MQTT → 蓝牙 GPIO 拉低 → **硬断电（0 电流）**。
- **模式切换时序**：蓝牙通过串口向 Cat.1 下发"上传/通话"指令 → Cat.1 自动由低功耗切到**常规模式**完成收发 → 业务结束自动回低功耗。
- **唤醒时序**：三轴中断**或按键事件** → 蓝牙唤醒（BLE 退出低功耗）；若处于静止态则先给 Cat.1 上电注册进入活动态，活动态内则直接按需令 Cat.1 在低功耗↔常规间切换。

### 4.5 紧急报警端到端流程（跨模组）
- **触发**：双键同按 3s（蓝牙检测，防误报）。
- **静止态触发（SOS 睡眠）**：双键挂蓝牙侧，静止态按键时蓝牙**先给 Cat.1 上电联网**，再按下述流程**优先**上报 `sosMsg`+发起 VoIP+`sosLocationMsg`（均待平台确认）；报警处理完**再走上线流程**（`onlineMsg` + 平台参数查询），随后进入活动态常规行为。报警信息始终优先于常规上线消息。
- **蓝牙**：强制 Cat.1 上电联网；打包位置（**SOS 取位规则**：有蓝牙Beacon 即只报 Beacon；无 Beacon 则 LBS、WIFI、GPS **各自扫描各自，扫描完成一路就传输一路**；三路均无结果则只上报**空位置**）。
- **Cat.1**：发 `sosMsg`（等 `sosReplyMsg`，**60s 内未收到确认则重发，最多重发 3 次**）→ `sosLocationMsg`（等 `sosLocationReplyMsg`，同上 **60s / 最多 3 次**）；同时发起 VoIP 拨打 `phoneBindMsg` 主叫号。确认超时与重发策略统一见 5.8。
- **VoIP**：单次拨打不主动重拨（无论对端是否接听）；报警保持进行中至用户长按取消或平台取消；双向挂断（用户/对端均可）；通话中长按挂断 + 语音提示（语音由 Cat.1 侧喇叭播放）。
- **指示**：屏幕显示（BLE 侧墨水屏）+ 语音播报（蓝牙下发指令、Cat.1 侧喇叭播放）；无蜂鸣器/指示灯/震动。
- **时延**：按键到平台收到 `sosMsg`，**3~15s**（见 9.1）。

## 5. 通信协议与数据格式

### 5.1 连接与地址
- 传输：MQTT over TLS（`mqtts`），端口 **8883**。
- 地址：测试 `103.169.62.35:8883`；生产 `119.253.52.170:8883`。
- 卡端账号 / 密码：`warncard3_card / warncard3_cardTk123456!`
- 心跳：`MqttClientKeepAliveInterval`（默认 900s）。

### 5.2 Topic 定义
| 方向 | Topic |
|------|-------|
| 下行 | `/iotplat/render3/{product}/{deviceid}/down_raw` |
| 上行（报警类） | `/iotplat/datapush3/sos/{product}/{deviceid}` |
| 上行（非报警类） | `/iotplat/datapush3/notsos/{product}/{deviceid}` |

### 5.3 下行消息（平台 → 设备）
| MsgType | 说明 | 关键字段 |
|---------|------|----------|
| `sosReplyMsg` | 报警消息反馈 | Status(success)；设备侧 `sosMsg` 发出后 60s 内未收到本确认则重发（最多 3 次，见 5.8） |
| `sosLocationReplyMsg` | 报警位置反馈 | Status(success)；设备侧 `sosLocationMsg` 发出后 60s 内未收到本确认则重发（最多 3 次，见 5.8） |

| `personSearchMsg` | 一键寻人指令 | Cmd(1) |
| `otaMsg` | OTA 升级命令 | CurrentVersion、TargetVersion、Address(http)、Md5 |
| `logMsg` | 上传日志 | Cmd(1)、Address |
| `rebootMsg` | 远程重启 | Cmd(1) |

### 5.4 上行消息（设备 → 平台）
| MsgType | Topic | 说明 |
|---------|-------|------|
| `sosMsg` | sos | 报警触发（Data=1，RelatedValue=Time+300） |
| `sosLocationMsg` | sos | 报警位置（Position 对象） |
| `onlineMsg` | notsos | 上线（Version、Battery、Position；**不携带 auto-OTA 字段**） |
| `offlineMsg` | notsos | 下线/休眠前（Battery、Position） |
| `periodicMsg` | notsos | 周期上报（PeriodicPara、Battery、Beacon[]） |
| `personSearchReplyMsg` | notsos | 一键寻人位置（ReceiveCmdTime、Position） |
| `phoneBindReplyMsg` | notsos | 绑定结果（CmdType、Result、CallOut、CallInList） |
| `paraSetReplyMsg` | notsos | 参数设置结果（ParaData） |
| `otaReplyMsg` / `otaResultMsg` | notsos | OTA 命令回执（`otaReply=success/fail`，已写 NV）/ 升级结果（Status=success/fail、Version、Time） |
| `logReplyMsg` | notsos | 日志上传情况 |
| `rebootReplyMsg` | notsos | 重启结果 |
| `lowBatteryMsg` | notsos | 低电量预警（Battery、Status=lowBattery、Time） |

### 5.5 公共对象：Position
| 参数 | 类型 | 说明 |
|------|------|------|
| PositionType | string | `Bluetooth` / `LBS` / `GPS` |
| Beacon | array | Major(区域)、Minor(设备)、Rssi(信号)，≤5，Bluetooth 时必填 |
| Longitude / Latitude | string | WGS-84 十进制，非 Bluetooth 时必填 |

> 非 Bluetooth 定位：LBS 由模组联网后上报基站，平台三角/单基站估算经纬度返回；GPS 直接取经纬度。平台备注：**仅报警可能出现 GPS**；日常园区外不做 GPS 历史轨迹。

| CallType | **0（voip）** | 0（voip） | **协议 V1.3 新增**：语音通话类型，0=voip、1=volte，默认 0（与产品"默认 VoIP、VoLTE 保留"一致）；平台可经 `paraSetMsg` 下发切换 |

> **OtaBatteryThreshold 为端侧固定常量（70%），不作为平台可下发参数**：OTA 提交所需最低电量为设备固件固定值 70%，平台不可修改；升级提交仅在电量 ≥ 70% 时执行。

> 25% 低电量提醒为产品需求（非协议字段），由设备本地判定并发布 `lowBatteryMsg`。

> **与协议 V1.2 `paraSet` 默认值差异说明**（设备默认以 PRD / 本文档为准，协议默认仅作平台未下发参数时的兜底）：
> - `RestTime`：协议 `paraSetMsg` 默认 **10 min**，本文档设备默认 **5 min**（PRD F-009）；`BleScanInterval`：协议默认 **2 min**，本文档设备默认 **1 min**（PRD F-006）。平台可经 `paraSetMsg` 下发覆盖。
> - `BeaconUploadMethod` / `BeaconUploadAddr`：协议 `paraSetMsg` 仍列此二参数（默认 1），本代**暂时保留**（暂不启用）——维持产品决策，由 `periodicMsg` 内联 Beacon[] 取代历史 beacon 文件上传；协议中的参数与 HTTP 历史轨迹接口视为历史兼容占位。
> - `PeriodicPara`：协议 `paraSetMsg` 默认 60 min、`paraSetReplyMsg` 示例 120 min；本文档设备默认 60 min。`SleepTimeout`：协议 `paraSetMsg` 默认 120 min、`paraSetReplyMsg` 默认 720 min；本文档取 720 min（休眠超时上报兜底）。

### 5.7 HTTP 接口（历史轨迹）【保留】
> 本代 beacon 数据统一由 **`periodicMsg` 周期性上报（携带 Beacon[]）** 承载（见 5.4 / 5.6），不单独走 HTTP 文件上传；HTTP 历史轨迹接口作为协议历史兼容**保留**，本代未启用，后续版本可评估启用：
- `POST /device-msg-parse/api/device/uploadLocation`
- 表单：`data`（JSON：requestId、businessCode=`3ndcard_his_rail`、time、md5、fileName、deviceId）+ `file`（zipData：历史 beacon JSON）。
- 响应：`{code:200, message:"success", data:null}`。

### 5.8 消息确认与超时策略
设备与平台间消息的确认规则（详见 PRD F-033）：
- **需平台确认的消息**：仅 **报警类** 与 **找人类** 需平台应用层确认：
  - 报警类：`sosMsg` → `sosReplyMsg`、`sosLocationMsg` → `sosLocationReplyMsg`；
  - 找人类：平台经 `personSearchMsg` 触发设备上报位置，平台对该次上报予以确认。
  - 以上消息设备发出后 **60s 内未收到平台确认即重发，最多重发 3 次**（含首报共 4 次），仍失败则本地记录、下次上线补报。
  - 确认超时（60s）/ 重发上限（3 次）为端侧固定策略；协议 V1.3 `paraSet` 中 `SosReplyTimeout`(15s)/`SosLocationReplyTimeout`(30s) 为协议默认值（未同步 60s 策略），**平台未下发时以端侧 60s/3 次兜底；平台下发则以下发值为准**（2026-10-15 与用户确认：做联调时再实际确认，文档不再追踪此差异）。
- **无需平台确认的消息**：除上述外所有消息——下行指令（`paraSetMsg`/`phoneBindMsg`/`otaMsg`/`rebootMsg`）及其回执、纯上行通知（`onlineMsg`/`offlineMsg`/`periodicMsg`/`lowBatteryMsg`/`logReplyMsg`）等，**均不要求平台应用层确认**；纯上行通知依赖 **MQTT QoS1** 可靠投递，断连期间缓存、恢复后补报（见 7）。

## 6. 关键算法与策略

### 6.1 扫描频率递增/恢复算法
```
interval = 1min
missCount = 0
on each scan:
    if beacon found:
        missCount = 0
        if interval != 1min: interval = 1min   // 恢复：扫到即回 1min
    else:
        missCount += 1
        // 失锁升级：第1次失锁保持间隔1min(基线)，第2次起递增1min(2/3/4/5)，封顶5min
        // 与 PRD F-006 / 交互规格 F-006 一致
        if missCount >= 2 and interval < 5min:
            interval += 1min                    // 递增，封顶 5min
```

### 6.2 静止判定
无运动持续 **5 min** → 触发休眠流程（offlineMsg → 蓝牙 GPIO 切断 Cat.1 供电硬断电 → BLE 低功耗睡眠）。三轴中断立即唤醒并给 Cat.1 上电。

### 6.3 续航评估模型
- 占空比：每日 8h 工作（活动态）+ 16h 休眠（静止态）。
- 活动态功耗主因：Cat.1 在线 + BLE 扫描 + 偶发通话/报警；静止态 Cat.1 关机、BLE 低功耗。
- 目标 ≥ 7 天，由 500mAh 电池 + 双状态机约束。

### 6.4 定位取位策略（2026-10-15 调整，WiFi 正式启用进入定位链；位置数据格式以协议 V1.3 为准）
- **上线 / 下线 / 一键寻人**（依次尝试，取到即用）：
  `蓝牙Beacon → WIFI → LBS → GPS → 空位置`
  - 任一来源取到位置即采用并上报，不再尝试后续来源；全部失败则上报**空位置**。
- **SOS 报警**（不走顺序链，短路 + 逐路传输）：
  - 有蓝牙Beacon → **只报 Beacon**（短路，不触发其他来源）；
  - 无蓝牙Beacon → LBS、WIFI、GPS **各自扫描各自，扫描完成一路就传输一路**（不等待汇聚，抢时间；每路独立一条 `sosLocationMsg`，PositionType 分别为 0=LBS / 1=WIFI / 2=GPS，见协议 V1.3）；
  - 三路均无结果 → **只上报空位置**（PositionType=3）。
- **WiFi 扫描与传输时分**：联调时若确认 WiFi 扫描影响数据传输，扫描时可考虑暂停数据传输，避免数据上传丢失（以联调结论为准）。
- 与 PRD F-003 / F-007 / F-008、交互规格 1.4 / F-003 / F-010 / F-018 一致。

## 7. 异常与可靠性

| 项 | 策略 |
|----|------|
| MQTT 断连 | 自动重连；离线期间关键数据（报警/上线/休眠前位置）本地缓存，恢复后补报 |
| 关机前上报失败 | 重试有限次；仍失败则记录，下次上线 `onlineMsg` 补齐 |
| OTA | 平台依据 **auto-OTA 参数** 决策推送目标（4.3）；设备自调度完成"活动态后台预置 → 安全静止窗提交"，全程不阻塞用户、平台零人工；目标版本持久化至 **NV**；Cat.1 下载整包+校验 Md5+签名+写入 **A/B 非活跃分区**，并经串口 DFU 刷蓝牙非活跃槽；蓝牙 **A/B 双分区** 断电/失败可回滚拒绝成砖；仅"翻转重启"为短暂不可用窗口，且约束在**静止态**（设备无人使用、天然安全）；`otaResultMsg` 回报，失败平台自动重推 |
| 加密 | **仅使用 mqtts（MQTT over TLS）** 提供传输层加密（链路已加密，无需应用层加密） |
| 看门狗 | 关键任务异常自恢复 |
