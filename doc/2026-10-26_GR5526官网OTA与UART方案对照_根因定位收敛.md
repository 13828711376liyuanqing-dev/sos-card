# GR5526官网OTA/UART方案与本板实现对照

SAM | 2026-10-26 +08:00 | 本轮只做官网核对、活动SDK审查和无副作用寄存器读取；未修改设备固件、未编译/烧录、未启动新OTA。

## 结论与当前边界

1. 当前“应用接收至B区、验证后由独立Boot安装”的方向，与官方后台双区升级在结构上相符；没有证据说明整个架构必须推倒重做。
2. 当前确定故障在运行态UART接收服务：本次GR确认1536B，随后有效DATA offset1536无ACK；GR首错0x02为RX FIFO溢出。造成超时的具体代码点仍未锁定。
3. 官网Datasheet明确FIFO为128B；本板CPR也证实128B，SFE=1、SRT=2（半满64B触发）。460800/8N1下，触发后剩余空位64B，只能容纳约**1388.89µs**的数据。这是当前需要满足的具体时间预算。
4. 官方同时提供中断接收和DMA接收，官方DFU示例本身使用中断接收。因此“未用DMA就是根因”“改DMA一定成功”均不成立。
5. Flash写擦时XIP执行可能停顿是官方明确约束；但本次首错记录的受测OTA事务stage=2（已结束），不能据此直接归因“OTA写Flash期间仍发数据”。需要覆盖其他Flash调用和中断占用的实际时间。
6. 本轮不要求用户再次编译或试OTA。先把剩余证据补到具体执行地址/临界区，再交付单点修改。上一R6已SPENT，不自动再次恢复。

## 对当前方案的实际判定

### 后台双区方向成立，但当前并不是官方DFU协议

官方后台双区流程是：Bank0应用接收→写入Bank1→全部完成后更新DFU Info→复位→App bootloader校验/拷贝→启动应用。

当前项目保留独立Boot和A/B区域，CAT1预置、GR接收、Boot受控提交，方向符合此结构。但项目使用自定义OTA2协议、签名包/Boot描述符、双端owner/epoch及用户数据约束，不能将其称为“官方DFU已经移植完成”。

直接换成ROM DFU或官方示例Boot会改变协议、固件信息/签名验证、布局及数据保护契约。没有兼容证据，不作为本轮快捷替换方案。官网示例中GR551x的地址也不能套到当前GR5526布局。

本地SDK可核查路径：

- `SDK/projects/ble/ble_peripheral/ble_app_template_dfu/Src/platform/user_periph_setup.c`：1024B UART缓存、`app_uart_receive_async`接收、回调中重新挂接、DFU初始化、ACTIVE模式。
- `SDK/projects/ble/ble_peripheral/ble_app_template_dfu/Src/user/main.c`：主循环调用`dfu_schedule()`。
- 官方示例说明IRQ收包是合法路径，不证明其可不加分析地承受本项目所有业务中断和延迟。

### UART接收预算由硬件FIFO决定

官方原文：`Transmit and receive FIFO depth at 128 bytes`。FIFO段落还明确，半满阈值产生接收中断时已收到64字节。

本板无副作用读取：

| 项目 | 值 | 意义 |
|---|---:|---|
| UART4 SFE | 1 | FIFO使能 |
| UART4 SRT | 2 | 半满触发，64B |
| UART4 CPR | 0x00083D72 | FIFO模式字段8，按16B单位为128B，与Datasheet一致 |
| 波特率/格式 | 460800 / 8N1 | 每字节10bit，约21.701µs |
| FIFO从空到满 | 2777.78µs | 理想上限，不是可容忍无限阻塞 |
| 半满触发后的余量 | 1388.89µs | UART还未得到服务时的剩余接收容量时间 |

读取地址来自当前SDK寄存器定义：UART4_BASE=0x4000C900，SFE偏移0x98、SRT偏移0x9C、CPR偏移0xF4。未读取有清标志/弹出数据副作用的LSR/RBR，未写寄存器。原始值与脚本见`fifo_config.json`、`read_fifo.jlink/log`。

**字段纠正**：上一快照`rx_before=rx_after=16`是十进制16，即HAL_UART_STATE_READY=0x10；不是16字节缓冲，也不是BUSY_RX（0x12）。实际`UART4_BUFFER_SIZE=512`。软件环形队列空和dropped=0并不能防止硬件FIFO先溢出。

### Flash执行位置要核对完整调用链

官方Flash章节原文：

> If the CPU executes code from Flash while the on-chip QSPI controller is writing to Flash, the CPU execution will be stalled. In this case, the SRAM should be used for code execution.

当前实际AXF符号：UART4_IRQHandler=0x00206D19、hal_uart_irq_handler=0x0023EB35、uart4_evt_handler=0x00230D0D，均位于Flash映射区。

这说明Flash写擦与接收并发必须有明确约束；仅给顶层IRQ函数加RAM属性不能证明安全，还要审查HAL、回调、重挂、常量数据等传递依赖。DMA也要核查是否在CPU停顿期间仍能访问目标SRAM、缓存容量是否覆盖最长停顿，不能把“调用DMA API”当成“接收永不溢出”。

本次已有静默协议，且DWT记录首错stage=2，最后受测token8事务已结束。若仍怀疑Flash，下一证据必须指向未受测的其他Flash/NVDS操作或恢复期，不能重复指责已完成的受测写擦窗口。

### 中断与日志不能凭名称归因

当前实板UART4 IRQ54优先级63；BLE_SDK、BLE、UART0、I2C4也为63。QP临界区BASEPRI=0x3F，同阈值的UART4需关注其最长屏蔽时间及同抢占等级ISR占用。

SDK日志锁不是简单的“屏蔽BLE及同级”。其计算为：

```c
BASEPRI = NVIC_GetPriority(BLE_IRQn) + (1 << (NVIC_GetPriorityGrouping()+1));
```

当前BLE优先级63、分组0，得到65；UART4为63，所以该日志锁阈值本身不屏蔽UART4。不能据此直接删除日志或修改SDK锁。如果日志在同级ISR内同步输出，则占用该ISR的时间仍需另行核查；本次没有捕获到具体占用ISR地址，不把它写为已证实原因。

## DMA可以作为候选，但不能直接宣布为根因修复

官网APP UART文档和本地SDK均提供：

- `app_uart_dma_init`、`app_uart_dma_receive_async`；必须先UART初始化、再DMA初始化，传输过程中禁止初始化。
- SG/LLP收发API。当前本地`app_uart_dma_sg_llp`示例重点演示TX链表，不能把这份TX示例当成“RX循环链表已经验证”。
- 普通DMA示例为固定缓冲、完成后由循环再次启动；它不自动等于连续环形接收，也不证明无重挂空窗。

若选择DMA路径，必须先明确UART4 DMA请求映射、DMA实例/通道占用、RX超时和剩余计数语义、缓冲切换顺序、异常/休眠恢复，不能照搬UART1/DMA0 Channel0/1示例。当前未完成这些适配核对，因此本轮不直接改DMA。

## 接下来如何收敛，不再让用户试猜测

按一个明确故障关闭：**找到超过1.39ms的接收服务缺口来自哪里**。

1. 保留本次波形、首错和原AXF，已经通过的MQTT、ZIP、完整候选采用、旧任务退役不重复验证。
2. 核对运行态IRQ优先级与真实编译调用链，排除不成立的屏蔽解释。已完成HAL状态字段纠正、FIFO/阈值实读、日志锁阈值核对。
3. 目前剩余最小证据不是“再跑一遍OTA”，而是首错时的异常返回上下文：中断进入的堆栈PC/LR/xPSR、最长临界区的进入/退出地址及持续时间，或明确的RX完成→重新使能时间。已有首错只保存error/state/ring，无法还原该执行位置。需先形成可审查的最小跟踪设计；处理FPU扩展异常栈和MSP/PSP，不能随意读固定偏移伪造PC。
4. 只有执行地址或重挂时间证明具体缺陷后才改对应点。若证据证明业务确实允许超过接收预算的CPU停顿、又不能安全缩短，就选择并完整适配DMA连续接收；若证据是单个异常ISR/长临界区，则只修那个点。
5. 修后先按明确的纯UART接收验收设计验证长度/CRC、回调空窗、恢复和业务抢占，再考虑最终单次OTA；当前R6已SPENT，下一次实板OTA不在本轮授权内。

**当前不安排新的编译、下载或OTA试验**。本报告是官网/本板对照和定位范围收敛，不是“根因已定位到具体函数”的承诺。
