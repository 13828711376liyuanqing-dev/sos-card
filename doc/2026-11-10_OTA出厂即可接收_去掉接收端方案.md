# OTA 出厂即可接收：去掉"接收端"的方案

SAM | 2026-11-10 | 读者：项目负责人 | 状态：**方案，未改代码** | 依据：CAT1 源码（main.lua、ota_trial.lua、ota_native_fota.lua、ota_manager.lua、ota_device_options.lua、ota_runtime.lua、update.lua）和 3 次真实双端 OTA 的结果

## 一、基本线（用户 2026-11-10 定）

- 客人手里的机器**出厂时就具备 OTA 接收条件**。以后推送 = 打包一版更高的固件，直接在后台推送。
- 不能为每个升级包单独刷一个"接收端"，也不能逐台刷机。
- CAT1 要和 GR 一样：知道设备当前版本，就能收更高的版本。

## 二、现状为什么做不到（简单版）

CAT1 里现在是"**首次受控试装**"的设计，只允许一件事：把**写死在代码里的三个值**对上才放行。

| 写死的东西 | 在哪里 | 后果 |
|---|---|---|
| 源版本、目标版本（如 1.5.24 → 1.5.26） | main.lua、ota_trial.lua、ota_native_fota.lua 三处 | 每升一个版本，设备代码里的范围就得改，所以要刷新的接收端 |
| 升级包的 MD5（`OTA_TRIAL_MD5`） | main.lua，ota_manager.lua 的 `trial_job` 对比 | 只有这一个包能装；换包就要重刷 |
| 一次性票据（`SPENT`） | ota_manager.lua | OTA 用过一次，票就作废，设备不会再接受下一次 OTA，只有 Luatools 清 KV 和 FS 才恢复 |

另外 `native_contract_verified` 默认返回 false，只有这个"试装闸门"能把它改成放行。也就是说，**CAT1 现在没有"正式"的接收路径**。这是早期保守设计：当时 CAT1 原生升级没有真机证据。现在 3 次真机双端 OTA 都通过了，可以转正。

## 三、方案：把"写死的值"改成"规则"

| 现在 | 改成 |
|---|---|
| 源版本写死 | 源版本 = 设备自己当前的 `PRODUCT_VERSION`（运行时读） |
| 目标版本写死 | 目标版本 > 当前版本；目标版本来自平台消息，并被授权文件绑定 |
| 冻结 MD5 | 去掉；包的 MD5 用平台消息里的 MD5 + 包内签名清单 + 授权文件校验（这些现在就在校验） |
| 一次性票据 | 每次 OTA 一个新任务；完成或失败后清除，不再永久锁死 |

**保留不动的安全检查**：模块是 Air780EGH、内核 V2052、64 位、文件系统容量、内核哈希、`SCRIPT_ONLY_SAME_CORE`、包里不带用户数据、电量与保电、GR 授权、Boot 回滚、发令前清日志。

**控制权转移到哪里**：以前靠"这台设备只认这个 MD5"控制，以后靠**签名私钥和授权文件**控制（授权文件已经绑定 GR 正文哈希、CAT1 包哈希、评审摘要）。所以私钥保管成为唯一闸门，平台端只能推我们签名的包。

## 四、要改的文件

| 文件 | 改什么 |
|---|---|
| main.lua | 去掉 `OTA_TRIAL_MD5/SOURCE/TARGET` 和 `first_trial_profile` 的版本范围 |
| ota_trial.lua | `profile.source/target` 改成运行时判断（源 = 自己的版本，目标 > 源） |
| ota_native_fota.lua | 第 51 行写死的 `1.5.24/1.5.26` 改成同样的规则 |
| ota_manager.lua | `trial_job`、`n.trial`、`SPENT` 逻辑改成每次任务票据 |
| ota_device_options.lua、ota_runtime.lua | 放行条件改用规则 |
| update.lua | `cat_at OTA_TRIAL=` 台架命令：保留（改成同样规则）还是删除，待定 |

**工具侧随之简化**：4 号工具不再需要"设备当前版本"去改范围，只改版本；3 号工具"版本号必须等于 OTA_TRIAL_TARGET"的检查去掉；1 号工具的"接收端模式"不再需要（保留给旧固件）；一键工具里的"生成接收端"步骤去掉。流程变成：**改版本 → 编译 → 签名 → 打包 → 上传 → 推送**。

## 五、风险和代价

1. **改的是受保护的 OTA 代码**：要完整走评审、主机测试（`tools/ota/` 里已有大量测试，要同步更新）和真机双端 OTA。
2. **必须证明"不重刷、连续两次 OTA"**：例如 1.5.26 → 1.5.27 → 1.5.28，中间不碰设备。这是新的验收线。
3. **旧固件一次性重刷**：现在台架板和同事的设备都带写死的范围，要用 Luatools 刷一次新基线；之后不再需要。
4. **防误推的责任转移**：见第三节，平台只能推我们签名的包，私钥不能外泄。
5. **体积**：CAT1 脚本区现在 496617 / 524288，余 27671，去掉代码只会更小。

## 六、步骤

1. 确认本方案（第七节三个问题）。
2. 改 CAT1 代码，更新主机测试。
3. 评审清单、打包（版本 1.5.27，作为新基线）。
4. 台架板用 Luatools 刷一次新基线（GR 保持）。
5. 真机连续两次 OTA：1.5.27 → 1.5.28 → 1.5.29，**中间不刷任何东西**。
6. 简化工具和说明文档，更新技能。
7. 同步同事。

## 七、需要用户决定的三件事

1. **一次性票据**：改成"每次 OTA 一个新任务，完成后清除"，对吗？（我的建议：是。）
2. **版本限制**：只要求"比当前版本高"，还是限制同一个主版本、不能跨大版本？（我的建议：先只要求更高，跨大版本的限制放进平台侧规则。）
3. **台架命令** `cat_at OTA_TRIAL=<地址>`：保留，还是删除？（我的建议：保留，改成同样规则，台架调试要用。）
