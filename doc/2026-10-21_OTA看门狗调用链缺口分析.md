# OTA 看门狗调用链缺口分析

## 已确认的缺口

1. `tools/ota/boot/yp001_ota_sdk_handoff.c` 只有跳转前两次喂狗。`yp_boot_start` 在此之前调用选择器，选择器可能同步完成全部安装/回退，因此交接处喂狗无法覆盖恢复过程。
2. `ble_app_uart_c/Src/user/ota/yp001_ota_boot.c:yp_boot_resume` 在一个while中处理整个槽。候选槽0x75000/4096=117个扇区，每个扇区执行A→scratch、B→A、scratch→B三段复制，每段后还持久化日志。`tools/ota/boot/yp001_ota_flash.c` 的读、写、擦除、64字节读回检查及验签调用均没有看门狗服务入口。源码确认缺少服务点，但没有实测证据证明当前总耗时已超过窗口。
3. 隔离 `user_periph_setup.c` 设置Boot counter=20000；SDK `gr55xx_hal_aon_wdt.h`明确单位ms，即20秒。Boot初始化及刷新函数忽略HAL返回值；不能把“调用过喂狗”当作成功。
4. SDK `sign_verify.c` 一次性提交正文和尾部的hash计算，再执行RSA/ECC校验；可见调用链没有服务回调。仅在验签前后喂狗不能处理单次密码学调用本身超过窗口的问题。当前不能推定它一定超时或一定安全，需要具体算法/最大包/芯片时钟下的耗时上界。
5. 应用 `bsp.c:BSP_init` 在业务/OTA及部分外围初始化之后才调用 `app_aon_wdt_init`，counter=5000ms、alarm=2500ms。SDK `app_aon_wdt.c` 的init会先HAL deinit，再HAL init，最后注册中断并标记活动。调用方忽略返回值，可能无法发现接管失败。应用驱动也未初始化时直接调 `app_aon_wdt_refresh` 会返回 NOT_INIT，不能把它提前插入当作解决办法。

## 对已有结论的限制

上一轮“保留看门狗”只描述最小Boot跳转适配不主动关闭看门狗；不代表应用接管全过程没有停表窗口。主机交换测试未模拟真实看门狗时间，无法证明117扇区交换不会复位。

事务日志允许中断后恢复，但不能因此接受无界的看门狗复位循环。反复停在同一未完成阶段可能阻止启动，并增加Flash磨损。真实行为仍待故障注入和时序观测。

## 实施对策

1. 先在候选Flash后端加入由可信Boot提供的、能返回失败的服务回调。只在通过地址检查后及有界操作/读回块之间服务；失败停止后续擦写，将恢复交给持久日志。不要在无进展的中断定时器中无条件喂狗。
2. 对服务失败建立主机故障测试：拒绝地址不调用服务、不做Flash IO；读写擦除边界服务失败立即终止；交换重启仍能恢复且用户区保持。默认未绑定服务的生产候选必须拒绝启用，不能悄悄按“无看门狗”运行。
3. 验签接口需规定最大单次阻塞时间；先获得实际SDK算法耗时，再决定使用有服务点的可信分块验签适配。不得为喂狗自行改变被签名内容、跳过验签或只校验CRC。
4. 核对Boot初始化/刷新HAL状态并传递失败；真实硬件适配不再凭void返回臆测成功。应用接管失败需要明确受控恢复策略，随后再局部修改主工程及交付副本并分别编译。
5. 每个单次Flash HAL调用本身也需有耗时界限。调用前后服务只能覆盖多次操作的累计时间，无法救援一个无限阻塞的HAL调用。

验收要记录最长不喂狗间隔、交换总耗时、最大包验签耗时、SDK跳转到应用成功接管的耗时及初始化状态。只测“最后能开机”不足以确认安全余量。

### 服务接口的必要约束

- 回调必须返回真实状态，不能简单包装目前忽略HAL结果的 `bootloader_wdt_refresh(void)` 后固定返回0，否则只得到“调用成功”的假证据。
- 初始化时要求回调已绑定；完整检查地址与保护区之后才调用。初始化失败/未批准布局不得产生Flash写入。
- 每次有界读写擦除前、完成后以及读回分块之间服务。服务失败应锁住当前后端实例，禁止调用者在同一实例继续擦写；恢复需重新初始化并读持久日志。
- 若擦除/写入之后服务失败，数据可能已经改变，必须按已有事务阶段重新恢复，不能承诺原子失败。测试应覆盖“改变已发生、日志阶段未提交”的状态。
- 验签前后服务只能覆盖多次操作累计时间；单次ROM/密码学调用超时仍由看门狗复位。不能无条件在定时中断喂狗，否则挂死任务可能永远不复位。
- 不通过扩大20秒、关闭看门狗或删掉读回检查来掩盖缺口。具体服务频度与最坏执行时长应通过测量决定。

### 应用接管的准确表述

SDK的 `app_aon_wdt_init` 会先deinit后init，任一步失败就返回；生产 `BSP_init` 未检查其结果。因此可能出现旧看门狗已停、新看门狗未成功启动的状态。这是源码支持的失败路径，尚未在设备上复现。应先明确失败后的受控复位策略并检查返回值，再验证Boot到应用的接管时间，不能仅提前调用应用层refresh。

本次增补仍为只读分析，无新固件或实板操作。优先级保持：真实状态可返回的Boot服务接口 → Flash服务点与失败锁定 → 事务中断恢复测试 → 单次阻塞时序/应用接管验收。
