## 本轮结论

实现了 C/Lua 两端一致的 OTA2 帧编解码和有界流解析，并完成交叉测试。**还没有接入运行中的 UART 消费者，不能据此发起实板 OTA。** 本轮未烧写、未擦除设备，未生成新的上传 ZIP。

已查到的生产链路问题：

1. `Air780EGH/dfu_transfer.lua` 是旧 Goodix DG 协议，且 B 起点仍写为 0x002C0000；不能将它直接用于当前项目签名镜像和拟定 B 槽。
2. `user_periph_setup.c::cat_diag_poll()` 当前按文本处理，遇 NUL 丢弃整行；不能接收包含任意二进制的 OTA2 帧。
3. GR 的 `package_ready`、`completed` 仍返回 false，安全门仍保守关闭；独立记录页可用不表示安装可用。
4. 生产 Boot 入口、镜像接收写入授权、未知 B 内容处理，以及 CAT1 默认运行实例的生产绑定仍未闭环。

## 实际变更

- GR 主/交付 `Src/user/ota/yp001_ota_wire.c/.h`：24 字节头、512 字节最大载荷、CRC16-CCITT-FALSE 和 CRC32-IEEE、540 字节固定缓冲、逐字节输入、失步重同步；不操作 Flash。
- 两份 Keil 工程仅增加上述 C 文件的编译项，未改变编译器、宏、链接布局、调试或下载配置。
- `Air780EGH/ota_wire.lua`：相同格式的编码、解码和流解析；每次完整头通过后缓存期望长度，避免每个载荷字节重复计算头 CRC。
- `tools/ota/test_uart2.py`、`test_uart2_runner.c`：独立 Python struct/binascii 金标准，实际运行 C 和 Lua 实现。GCC 为 32 位而 Python 为 64 位，因此使用独立 EXE 测试进程，不通过 DLL 跨位数加载。

消息 Type 数值仍由后续会话合同定义；本层只验证信封，不将任何 Type 解释为擦写/激活授权。Session、Sequence 和 Offset 原样保留，后续接收状态机必须执行会话、重复帧与持久偏移校验，不能只凭 CRC 放行。

## 验证

`python tools/ota/test_uart2.py`：3 组通过。

- 0/1/255/512 字节载荷与 Python 金标准逐字节一致，覆盖 uint32 最大值。
- 对 284 字节帧的每一个字节翻转一位，C/Lua 均拒绝；超长、截断、附加字节拒绝。
- 540 字节帧全部 541 个分割位置、连续帧、前导噪声、损坏帧后恢复均通过；10 万字节噪声后 Lua 留存不超过 3 字节。
- C 编译 `-Wall -Wextra -Werror` 通过；厂商 `luac_64bit.exe -p` 通过。
- GR 生产记录页测试、编排故障注入通过；CAT1 文件适配 3 项、签名清单任务映射 3 项回归通过。

## 容量和部署边界

主工程 ReleaseCli 当前仍返回 payload 477536 字节，SHA256 `32ff7773f3312b50b882cc8158acfac73dfc8bfd86c2c924a19cac82ab406b29`。加 904 字节签名为 478440，拟定槽位 479232，余 792 字节。

**容量未增加是因为帧实现尚无生产调用，链接器去除了未引用函数，不表示接入后仍有足够空间。** 后续真正接入 UART 消费者和接收状态机时必须重新测量容量。不得扩大槽、侵占用户数据或关闭校验换取通过。

## 下一步接入顺序

1. 在现有单消费者内加入文本/OTA2 仲裁；字节丢失、超时与退出会话重置解析器，不能使二进制载荷变成业务命令。保留紧急业务让行。
2. 明确内部消息编号和 ACK 载荷，接停止等待、早到 ACK 缓存、序号/偏移幂等、accepted/durable 区分。
3. 接已验签任务、受限 B 写入和持久进度；先解决旧 B 内容归属/保留，不自动擦除未知内容。
4. 接 Boot、实际业务安全门与安装健康确认，再接 CAT1 串行自身升级。
5. 完整构建与容量检查通过后才生成下一阶段可部署镜像；不用当前未完成镜像要求用户再次烧录。
