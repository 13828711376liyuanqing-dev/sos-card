## 2. 本批次实际完成了什么

### 2.1 从 AXF、HAL、ROM 和时序找到 ADC 接收预算问题

此前现场已经取得 GR 硬件 RX FIFO 溢出证据；本批次进一步核对了部署 AXF、实际 ADC 参数、ROM 回调指针和官方转换时序。

旧 ADC 路径的关键问题：16kHz 时钟下，HAL 在 PRIMASK 屏蔽中断期间进入 ROM 等待，正常空 FIFO 条件下约需 4 个转换结果，每个结果15个时钟，转换部分约 **3.75ms**。460800/8N1 下，128B UART FIFO 从空到满约 **2.78ms**，半满后只剩约 **1.389ms**。

因此，这是一条确定违反接收服务预算的软件路径，不是仅凭函数名字猜测。

已落地：ADC 改为1MHz，保留原板级分压、标定、样本处理和业务规则，配套 GR/Boot 已部署。后续普通接收及两轮受控传输中，读取到的 UART 首错记录没有再次提交；已观察 ADC 整次调用最大约778µs。

边界：原始故障没有保存阻塞者执行历史，所以不能断言 ADC 是最早那次溢出的唯一历史触发者；整次调用耗时也不等于所有情况下关中断最坏值证明。

### 2.2 修复恢复 hello 被隔离态吞掉的问题

原恢复 hello 没有前导换行，在 GR“丢弃到换行”的隔离态中可能整条被丢弃。已按原捕获顺序，在真实 C 解析器上复现并修复为原子 CRLF + hello。

这解决了一个真实恢复缺陷，但不能替代原始接收错误的修复，也不能证明整段 OTA 已稳定。

### 2.3 补上外层安全门拒绝的观察缺口

原外层 `safe(false)` 拒绝可绕过内层接收快照，造成反复只能看到 `UART_QUIET_DENIED`、无法解释具体拒绝条件。已增加独立 RAM 首次拒绝记录。

两轮最新读取均未提交外层拒绝记录，所以本次不能继续归因为“已知外层 peer 拒绝”。也不能拿内层全零去解释外层没有发生过拒绝。

### 2.4 修复主机只读观察器的分段漏判

旧观察器用短窗口、局部字符串寻找完整 JSON，合法回应跨窗口时可能漏判。已增加累计分帧、TX ACK 与时间记录，针对性用例通过。

实板普通通信证据包括：5次版本查询得到5次回应；另外约846B连续 HELP 流未出现 GR 首错。HELP 主机白名单漏掉了4个含 `+`/`?` 的命令名，这是观察器过滤行为，不能写成设备丢了4行，也不能声称主机完成了846B全字节相等核对。

### 2.5 找到并修复第一处静默释放期限错误

原 CAT1 已收到正确242释放帧后，仍继续使用旧3秒期限，等到243 ACK发送完成才删除hold。若释放及时到达、发送协程或sent回调稍晚执行，原代码仍可误报 `UART_QUIET_TIMEOUT`。

已由原代码确定复现：2999ms收到242，3001ms运行发送任务，原代码报错；修复后该情况通过，真实迟到/错身份/缺释放/缺sent仍停止。

这项修复已经进入最后部署的 CAT1 集合。**实板仍失败，说明这项修复不充分；不能写成“静默问题已解决”。**

## 4. 目前真正确定的问题与未确定项

### 4.1 已确定：新的静默计时起点缺口

最后一轮结束后，继续检查发现：3秒静默期限从 CAT 收到240请求就开始，**许可241 ACK等待发送的时间也被计入了Flash执行预算**。但 GR 是收到许可后才进入操作，释放重发还使用其自身约2秒预算，两端计时起点没有对齐。

已经增加并跑出失败用例：

```text
t=0ms     CAT收到240请求
t=1200ms  CAT才发出241许可ACK，仍在GR原2秒握手期限内
t=1215ms  GR完成约15ms操作，第一份242丢失
t=3001ms  CAT按“收到请求”开始的3秒期限提前报错
t=3216ms  GR按既有2秒规则重发242，本应属于可恢复的释放交互
```

部署源码实际失败断言：

`FLASH_DEADLINE_STARTED_BEFORE_GRANT_WRITE`

- [负例记录](/D:/CODEX/sos-card/logs/r6_release_deadline_20261026/grant_deadline_reproduction.json)

**截止本总结：这项计时起点修复尚未实施、尚未打包、更未部署。** 不要把前一项“及时释放误判”的修复，当成已包含这个新修复。

### 4.2 未确定：最后实板故障的第一条异常消息

最终 GR 静默状态：

```text
phase=0，kind=0，token=628
granted=1，allowed=0
```

操作测量只覆盖获准执行的操作本体，不覆盖许可前、释放前后的全部调度等待。**不能用14ms操作耗时推导全过程不可能超过3秒，也不能排除GR前台调度延迟。**

## 6. 今天做错或做得不够的地方

### 6.1 把“真实缺陷存在”推进成了“足以解决本次实板故障”

及时释放误判确实存在，测试也确实通过，但并没有证明最后实板故障就是这个边界。之后又发现许可ACK排队时间被算入Flash期限，说明静默协议的整条时间预算没有一次检查完整。

**责任：分析和联测范围不充分。** 不能拿“这是个真实bug”来回避“它没有解释并关闭这次故障”。

后续要求：同一静默会话必须把请求、许可提交、许可实际完成、操作、释放接收、释放ACK完成和各自超时放在同一张时间线上；不能继续按看到的末端错误逐项修补。

### 6.2 主机全长联测仍与实板时序存在差距

新的主机联测确实覆盖845块，比原来只到512B的模型更有价值。但对端是模拟，原场景没有同时覆盖“许可排队延迟 + 首次释放丢失 + GR重发 + CAT本地期限”的组合。

**错误不在于运行了主机测试，而在于过早把其覆盖范围当成了再次上板的充分依据。** 后续应先补这个组合的负例，再证明修改没有放宽实际3秒Flash许可和真实发送失败保护。
