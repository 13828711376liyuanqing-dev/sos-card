# YP001 现场空间策略（CAT1 文件区）

SAM | 2026-10-30 18:42 +08:00 | 来自 10-30 第三轮 OTA（1.5.2→1.5.3）的 COMPONENT_SPACE 事故和对 CAT1 代码的只读梳理。**结论是设计与代码阅读得出的，现场设备上的实际积累量还没有测过**，所以标了“待验证”。

## 1. 事实（实测）

- CAT1 文件区：128 块 × 4096 = **524288 字节**。干净状态已用 15 块（运营商 `*.nvm` 等 15 个小文件），可用最多 **462848**。
- GR 组件要先整包存进 CAT1 文件区再经 UART 送给 GR。设备的放得下条件：`可用 ≥ 已签名 GR 镜像 − 已下载暂存部分 + 904（签名预算）+ 16384（预留）`。1.5.3 的镜像 438472 字节 → **需要 455760**。
- OTA 一发起，设备多写约 4 块状态文件（`yp001_ota_state_0/1` 各约 4 KB、`yp001_cat_fota_0` 8456 B 等）：可用 462848 → 446464，**差 9296**，停在 `COMPONENT_SPACE`。`OTA_PRUNE`×2 后 450560，靠已暂存的下载部分才继续。
- 所以：**这套 OTA 在最理想的出厂状态下，余量也只有约 7 KB**；任何多出 2 块（8 KB）以上的数据，现场的整机就升不了级。GR 镜像槽最大 442368 时门槛是 459656，已经超过“清空 + 有状态文件”的可用空间（约 446464–450560）。

## 2. CAT1 会往文件区写什么（代码梳理，待现场验证增长量）

| 数据 | 来源 | 大小/风险 |
|---|---|---|
| `yp001_ota_state_0/1`、`yp001_cat_fota_0/1` | OTA 状态、原生 FOTA 记录 | 固定，约 17 KB，发起 OTA 后才出现；历史键会累积（`OTA_PRUNE` 清理） |
| `yp001_business_0/1` | 业务存储 | 很小（约 120 B），两份副本 |
| `/hxxtloc`、`/hxxt_tm` | GNSS 定位缓存 | 很小，覆盖写 |
| **`/record.pcm`** | `audio_drv.lua` 录音：16 kHz/16 bit 约 **32 KB/秒** | **风险最大**：录几秒就占满剩余空间；只在下次录音前删旧文件，异常断电或中途失败会残留 |
| **`/gr5526_fw.bin`** | `dfu_transfer.lua`/`uart_app.lua` 旧的 UART DFU 暂存 GR 固件 | **438 KB 级**；残留一份就 OTA 不下去 |
| 运营商 `*.nvm`、`plat_config` 等 | 模组自己 | 随网络注册略有变化，不受控 |

## 3. 结论（按优先级）

1. **OTA 前自检 + 自动清理（设备端，必做）**：接单（`OTA_TRIAL`/平台下发）时若 `可用 < 需要`，先自动做 `OTA_PRUNE` 一类的“自己的历史”清理；仍不够，再删“可再生数据”（`/record.pcm` 残留、`/gr5526_fw.bin` 残留、定位缓存），**绝不删业务数据（`yp001_business_*`）和 NVDS**；仍不够就明确拒绝并上报“需要 N、可用 M”，不要无限重试。现在只有人工 `OTA_PRUNE`，现场不可行。**待实现 + 实板验证**。
2. **所有写文件的模块要有上限（数据预算）**：录音、日志、缓存各自限长/限量，文件区总预算 = 524288 − 15 块（运营商）− OTA 状态（约 17 KB）− GR 暂存（镜像 + 904 + 16384）。预算表写进代码评审清单，新增写文件要先登记。录音写完/失败/启动时都要清理残留，启动时清一次。
3. **平台侧按设备上报的空间决定推不推**：心跳/状态里带 `fs_free`（可用字节）和 `fs_need`（本包需要），平台只对 `fs_free ≥ fs_need + 余量` 的设备下发；不够的设备不推，记录原因。需要新增上报字段 + 平台配置。
4. **GR 镜像大小有硬预算**：上面的结构性问题决定了 GR 不能再变大（当前 438472，已超出“有状态文件时”的安全线）。下一版要么**缩小 GR**（目标：≤ 约 430 KB，使 需要 ≤ 约 447 KB），要么**改暂存方式**（例如 CAT1 边下边送、只暂存压缩包、或让 GR 自己暂存），这是需要决策的架构问题，不是调参能解决的。
5. **人工处理只作兜底**：现场卡 `COMPONENT_SPACE` 时，运维用 4 号工具“清理 OTA 历史”（需要串口），所以不能作为常规路径。

## 4. 每次发版前的检查清单

1. 4 号工具“检查空间”：GR 余量、CAT1 脚本余量（见 `yp001-space-budget`）。
2. 用一台**用过一段时间的设备**读 `cat_at OTA_FS`，对比出厂基线（15 块），记录已用块数与文件列表；超过基线的文件逐一说明来源。
3. 确认 `/record.pcm`、`/gr5526_fw.bin` 不存在或有清理；GR 镜像大小是否比上一版变大。
4. 发起 OTA 前先清理再读数；读数与 `需要 = 镜像 + 904 + 16384` 比，**并再留 ≥ 16 KB（OTA 状态文件）**。
5. 把读数写入当轮记录，别抄上一轮的。

## 6. 官方资料核查（10-30 18:50，只读到搜索摘要，两个官方 wiki 页面抓取失败 "Socket is closed"，**未读到原文**）

- 官方 `fota.init`：参数是字符串则 FOTA 数据存进**文件系统**；整数或不传由底层决定；**Air780EXXX 系列用固定的内部地址，一般不传参数**（wiki.luatos.com/api/fota.html，摘要）。→ 我们的 CAT1 自身升级（原生 FOTA，写 62 块、249981 字节）走专用区的可能性大，**不占文件系统**（我们没有专门量过，待验证）。
- EC618 系列底层差分包 ≤ 480K，新旧脚本区大小要一致（wiki.luatos.com/chips/air780e/fota.html，摘要）。
- 文件系统用量：`io.fsstat("/")`/`fs.fsstat` 返回总块数、已用块数、块大小（新代码建议用 io 库）。
- 外挂 SPI Flash 可用 SFUD 挂成 LFS 文件系统，并可设偏移和大小，官方示例注明适用于 Air780EGH（cnblogs luatos/p/19010610，摘要）。需要硬件上有 SPI Flash。
- **没有找到**：官方对临时文件清理的说明、`libfota2` 空间不足的处理、Air780EGH 文件系统分区能否扩大的明确说明。
- 结论：**空间问题是我们“GR 镜像先整包暂存到 CAT1 文件系统”这个设计造成的，官方 FOTA 本身不需要这块空间**，所以没有现成的官方办法替我们清理；要从设计上解决（见 §3 与下面的候选方案），FAE 只能回答平台能力问题。
