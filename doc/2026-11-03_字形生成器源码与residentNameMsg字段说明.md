# 字形生成器源码位置与 residentNameMsg 文件字段说明

SAM | 2026-11-03 | 读者：后台/平台开发、GR/CAT1 开发 | 例子文件：`firmware_releases/name_glyphs/平台下发包_20261102/residentNameMsg_欧阳䶮𠮷.json`

## 一、开发源码在哪里

`tools/glyph_maker/` 里有两套工具，**源码就是文件本身，没有另外的工程或编译步骤**。

| 文件 | 是什么 | 给谁 |
|---|---|---|
| `backend/姓名字形生成器_后台版.html` | **后台版的全部源码**：一个 HTML 文件，界面、渲染、打包、CRC 都写在里面的 `<script>` 中。核心算法在 `// CORE-BEGIN` 到 `// CORE-END` 之间（`crc16`、`pack`、`b64`、`trim`、`glyphJson`、`buildMsg`、`emboldenX`），是纯函数，可以直接搬进 Node 后台服务 | 后台 |
| `backend/使用说明.md` | 后台版使用说明 | 后台 |
| `glyphlib.py` | 台架版核心库（Python）：点阵打包/解包、CRC、读取板上字库 `font_cn_*.c`、调用 `lv_font_conv` 渲染、生成消息/串口行 | 我们 |
| `glyph_maker.py` + `glyph_maker.bat` | 台架版界面和命令行（生成、经 COM26 推送、T0 自检） | 我们 |
| `fontconv/` | 本地安装的 `lv_font_conv@1.5.2`（Node），和板上字库同一个生成工具 | 台架版用 |

两套的打包和 CRC 算法已逐项比对一致。设备端对应代码：GR `ble_app_uart_c/Src/user/business/yp_name_glyphs.c`、`yp001_business.c`、`gui/epaper_ui.c`；CAT1 `Air780EGH/resident_name.lua`。

## 二、文件整体结构

一个姓名 = 一个 JSON 文件，UTF-8，一行。顶层字段描述"给谁、显示什么"，`Glyphs` 数组装每个字的点阵。

```json
{"MsgType":"residentNameMsg","Seq":1793618795,"Name":"欧阳䶮𠮷","Room":"1#1-102","Campus":"泰康之家·燕园",
 "FontId":"simhei","FontVer":1,"Glyphs":[ {字形}, {字形}, ... ]}
```

## 三、顶层字段

| 字段 | 例子 | 含义 | 怎么来的 |
|---|---|---|---|
| `MsgType` | `residentNameMsg` | 消息类型，CAT1 靠它识别这是姓名下发 | 固定值 |
| `Seq` | `1793618795` | 版本序号，同一终端必须越来越大；设备拒收比上一次小的 | 工具默认取生成时的 Unix 时间（秒），可手改 |
| `Name` | `欧阳䶮𠮷` | 要显示的姓名，1~8 个字，UTF-8 不超过 63 字节 | 输入法输入或码点插入 |
| `Room` | `1#1-102` | 房号，用设备自带字库显示 | 手填 |
| `Campus` | `泰康之家·燕园` | 园区名，用设备自带字库显示 | 手填 |
| `FontId` | `simhei` | 字形来源字体标识（记录用，设备不校验） | 固定值 |
| `FontVer` | `1` | 字形格式版本（记录用） | 固定值 |
| `Glyphs` | 数组 | 姓名里每个字的点阵，每个字 32px、16px 各一个，最多 16 个 | 渲染生成，见下 |

## 四、`Glyphs` 每一项的字段

以"䶮"的 16px 字形为例：`{"U":"4DAE","S":16,"W":14,"H":14,"X":1,"Y":-1,"A":256,"D":"BEAEYP/4CSAZwDMIxPgAAD/wAQB//AOADMBwPA==","C":"2152"}`

| 字段 | 例子 | 含义 | 怎么来的 |
|---|---|---|---|
| `U` | `4DAE` | 这个字的 Unicode 码点（十六进制），"䶮"= U+4DAE；"𠮷"= `20BB7`（扩展 B 区，5 位） | 从姓名逐字取码点 |
| `S` | `16` | 字号（像素），只能 16 或 32。32 用于主页姓名，16 用于低电页 | 每个字各生成一份 |
| `W` | `14` | 点阵宽（像素），即字形墨迹的实际宽度 | 渲染后裁掉四周空白得到 |
| `H` | `14` | 点阵高（像素） | 同上 |
| `X` | `1` | 点阵左边离"笔位"多少像素（左边距） | 裁边时记录 |
| `Y` | `-1` | 点阵**底边**在基线上方多少行；负数表示底边在基线下方（"䶮"底边比基线低 1 行） | 裁边时按基线计算 |
| `A` | `256` | 写完这个字后笔位前进多少，单位 1/16 像素：16px 字 = 256，32px 字 = 512 | 字号 × 16（汉字等宽） |
| `D` | base64 | 点阵数据，见第五节 | 打包后 base64 编码 |
| `C` | `2152` | 校验码，见第六节 | CRC-16 计算 |

`W/H/X/Y/A` 与板上 LVGL 字库的 `box_w/box_h/ofs_x/ofs_y/adv_w` 一一对应，所以推送的字和设备自带字的排版规则一样。

## 五、`D` 点阵数据怎么来的

1. **渲染**：用黑体（缺字时用 SimSun-ExtB 等扩展字体）在 16 或 32 像素下把这个字画出来。
2. **二值化**：灰度 ≥ 阈值（默认 128）记为 1（黑点），否则 0。黑体里没有、借用细宋体的字，阈值降到 64 并横向加粗 1 像素（防止发淡）。
3. **裁边**：去掉四周全白的行列，得到 `W×H` 和偏移 `X/Y`。
4. **打包**：1 位/像素，**每行补齐到整字节**，高位在前。每行字节数 = ⌈W/8⌉，总字节数 = ⌈W/8⌉ × H。
5. **base64 编码**写进 `D`。

例："䶮" 16px，W=14 → 每行 2 字节，14 行共 28 字节。解码后前几行（左为字节，右为像素）：

```
00000100 01000000   .....#...#....
00000100 01100000   .....#...##...
11111111 11111000   #############.
00001001 00100000   ....#..#..#...
...
01110000 00111100   .###......####
```

每行 16 位只用前 14 位，最后 2 位是补齐用的 0。

## 六、`C` 校验码怎么来的

- 算法：**CRC-16/CCITT-FALSE**（多项式 0x1021，初值 0xFFFF，不反转，不异或输出）。
- 输入：10 字节"头" + `D` 解码后的点阵字节。头 = `U`（3 字节，大端）、`S`、`W`、`H`、`X`、`Y`（各 1 字节，负数按补码）、`A`（2 字节，大端）。
- 例："䶮" 16px 的头是 `00 4D AE 10 0E 0E 01 FF 01 00`，加上 28 字节点阵，CRC = `2152`。
- 头也算进校验，是为了防止"点阵对、尺寸或位置被改"的情况。GR 收到后重算，不一致整批拒收，屏幕保持原来的姓名。

## 七、设备收到后怎么用

1. CAT1 检查字段范围（字数、字号、宽高 ≤ 40、`D` 长度、`C` 格式），逐字形转成串口行发给 GR，不写文件系统。
2. GR 逐个解 base64、核对长度 = ⌈W/8⌉×H、重算 CRC；收齐全部字形才整批生效，并把 `Name/Room/Campus` 存为当前居民信息。
3. 显示姓名时，每个字先找推送的字形（按 `U`+`S`），找不到再用设备自带字库，都没有画方框。
4. 推送的字形只在 GR 内存里，重启后自动向 CAT1/平台要回。

## 八、只用 JSON

平台存储和下发都只用这个 JSON 文件（2026-11-03 用户决定）。终端（CAT1）已去掉 zip 支持，收到 zip 会报 `NOT_RESIDENT_NAME_JSON` 拒收。
