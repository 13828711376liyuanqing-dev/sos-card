# 2026-10-19 深睡与整机功耗阶段结论

## 当前已取得的证据

- SDK1.0.4，主/交付源码同步；Keil编译下载由用户执行。
- 推挽01实际运动低有效，运行态运动标志、输入低采样784次一致，下降沿IRQ4次且ISR读低4次。
- 按键1/2及运动操作后均有早于静止约84秒的启动记录；启动来源寄存器均零，未完成精确唤醒源归属和多轮可靠性验收。
- CAT1 USB VBUS经R82/Q10强制打开Q2，用户已暂拆R82。GPIO6低、UART4隔离保持实测通过；CAT1输出曾逐步降至0V，跨时刻和开关测试的电压不能混比。
- sleep_test关闭CAT1/LCD、隔离UART4、三LED关断输出0D、停止充电。用户报告USB5V整机输入睡眠约4mA。马达C85当前实测0V。
- ETA69631 V1.9 PDF第4页降压无系统负载典型输入2.7mA（VBAT3.8V等规定条件），当前无电池状态不同，不能直接相减算MCU电流。

## 不应混淆的结论

1. UART静默和定时恢复不等于测得芯片最低睡眠电流，当前是整机USB输入测试。
2. 原高电流到4mA的变化包含硬件R82、CAT1放电等待、UART4隔离、LCD/LED控制等多项，不将所有差值归给单一项。
3. 标称60秒救援实测约84秒；SDK g_lpclk与校准频率读值差可解释大部分，但未证明完整原因，不做硬编码补偿。
4. 早期一轮曾出现3次启动，未查明根因；后续正常定时启动不抹去该异常。
5. 当前是人工CLI诊断，不等于客户正常静止下线、消息补报、自动业务睡眠已集成验收。

## 后续验证顺序

1. 当前最终固件再做静止入睡→约84秒恢复→串口响应及隔离保持的完整回归，不要求新硬件动作。
2. 最终固件重复验证KEY1、KEY2、运动唤醒，每次动作与启动时间关联，不能用入睡到启动时间冒充唤醒延迟。
3. 电池续航另做BAT端供电/测流并撤除USB VBUS。当前测试按既有无电池接法保持，不直接让用户接电池；先核对供电/充电限制和可用仪器。
4. 自动业务睡眠另列需求实现与验收，保留报警/通话/OTA门禁、用户数据和现有Flash布局。

本说明是证据汇总，不是全部功能验收通过。本轮未修改固件。
