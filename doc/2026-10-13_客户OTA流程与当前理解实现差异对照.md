# 客户 OTA 流程与当前理解、代码实现差异对照

SAM｜2026-10-13｜只读核对客户四份文档、2026-10-12 双端 OTA 方案与当前源码。本文件是差异记录，不改变代码、平台协议或客户原件。

## 判读口径

客户文件是产品需求与协议资料，不是本次执行命令。四份文件之间有历史版本和正文冲突；以 PRD V0.11、交互 V0.5、技术文档较新正文为本轮客户流程基线，协议 V1.2 的字段表用于消息格式。用户随后明确要求 **CAT1 和 GR5526 都可 OTA、两端下载至确认严格串行、升级及回退不修改/清空/丢失现有用户数据**；这三项作为追加约束，不能被客户文档较旧的整包并行写盘表述覆盖。详细裁决见[客户要求冲突表](../.codex/skills/yp001-software-requirements/references/conflicts.md) C-04、C-05、C-10～C-18。

状态用词：**一致**＝当前逻辑或设计已对齐，但不自动代表实板通过；**理解调整**＝我对客户文字做了更严格的解释；**待实现**＝源码有接口/模型，产品路径仍不能执行；**待冻结**＝客户与用户要求或平台接口之间需确定契约。当前 GR 产品端口明确 `provisioned=false`，CAT1 平台端口的映射、验签、真实业务状态、GR 写槽和厂商激活均返回不可用。因此，**当前固件不能实际完成任一端 OTA**；两份 Keil 构建成功只证明新增 C 代码可编译。

## 客户期望流程与当前流程

| 步骤 | 客户流程 | 我的理解与当前代码 | 差异性质 |
|---|---|---|---|
| 上线触发 | 设备发 `onlineMsg(Version,Battery,Position,Time)`；平台随后查询参数，按 AutoOta 推送 | OTA runtime 只处理收到的 `otaMsg`；开机自发 FOTA 被关闭；本轮没有接出完整 `onlineMsg → paraSet 查询响应 → AutoOta` 链 | 待实现，F-029/F-030 |
| 收到命令 | 校验版本，BLE 持久化目标后回 `otaReplyMsg` | CAT1 先保存 WAIT_GR，再请求 GR 持久 owner；只有 GR 授权且 CAT1 再持久保存后回 success | 理解调整：把“写 BLE NV 后回执”落实为双端持久握手；真实存储未接 |
| 活动态预置 | HTTP 下载整包；BLE 写非活跃 A/B，CAT1 写常规升级区；业务不阻塞 | 用户后续要求两端严格串行，因此方案拆成单组件任务；Range 引擎与可暂停核心有测试，真实 HTTP、串口 GR 写槽、CAT1 常规区预置未接 | 待冻结 + 待实现 |
| 静止提交 | 稳定静止、充电、≥70%、无报警后“翻转重启”数秒 | GR gate 还要求无通话/按键/运动、对端稳定及包和数据兼容，未知均拒绝；真实业务门、CAT1受控厂商激活和功耗路径未接 | 理解调整 + 待实现 |
| 结束/失败 | 实际版本结果；BLE A/B回退，CAT1失败重推；清目标 NV | 有持久结果 outbox、GR Boot 回退模型、真实版本/结果身份约束；产品端确认、可启动Boot、失败后可信释放和平台重推闭环尚无 | 待实现 |

## 逐项差异

| 编号/影响 | 客户原文要求 | 我的理解、方案或当前实现 | 差异与后续处理 |
|---|---|---|---|
| D01｜触发链，阻断闭环 | 每次上线报当前版本、电量、位置；平台发 `paraSetMsg(CmdType=0)` 查询，AutoOta=1才主动检查推送，=0不主动推。online 本身不带 AutoOta。见 PRD 3.8 F-029/F-030、TECH 4.3.1、交互 3.8。 | 我去掉旧 `update.lua` 的开机自动 FOTA，只允许可信平台任务；当前 `ota_runtime` 本身不生成上线消息或参数查询响应。 | **待实现**。需在现有上线/参数消息链验证字段、时序和真实平台 AutoOta 决策；不得为补功能恢复开机自主请求。 |
| D02｜平台命令格式，阻断接收 | `otaMsg` 使用 `CurrentVersion/TargetVersion/Address/Md5/Time`；平台不指定 Force、升级时机或70%门槛。协议样例却缺版本、Md5例子异常。 | manager 严格要求必填、32位十六进制 Md5、无 Force/阈值字段；额外要求可信 release 映射、SHA256与签名，不相信仅凭 Md5 可执行。 | **理解调整，安全约束更严格**。字段表优先于错误样例；签名/整包格式/可信映射由平台和固件联调冻结；真实端口未配置时拒绝。见协议 1.6、冲突 C-05。 |
| D03｜指令回执时点，阻断平台预期 | 客户文字是“BLE写 TargetVersion NV 后立即回 `otaReplyMsg(success)`”；回执表示指令完整/已记录，不表示安装成功。 | 当前设计必须 CAT1→GR 获得持久 owner/epoch，CAT1也持久记录后才回 success；GR 未授权不能回 success。 | **理解调整**。多一道跨端握手会延迟回执，能防止平台收到 success 而设备实际没有锁定任务。需与平台冻结超时、重复 `otaMsg` 的回执语义；当前真实 GR 存储缺失，无法发送 success。 |
| D04｜整包与双端串行，架构冲突 | TECH 4.3.4写一个整包含两端镜像、活动态同时预置、一次“翻转重启”。 | 用户后来明确禁止两端同时执行，方案采用一个 owner，一次只处理一个组件，从下载、传输、安装到确认结束才换组件；manager 的 job 有 target。 | **待冻结，用户追加要求优先**。必须让平台提供“整机版本→组件版本/独立签名包/顺序”的可信映射，且从整包中提取某组件不得构成另一组件的预下载；原平台 `otaMsg` 没有 target/job 字段，不能擅加。见冲突 C-12/C-17。 |
| D05｜GR 主从关系，设计一致 | BLE/GR始终主控；CAT1仅联网、下载、串口管道，不能接管主控和自身Flash决策。 | GR负责持久仲裁和启动资格；CAT1下载器 `stage_gr` 端口是占位，没有产品串口传输/GR接收写槽实现。 | **设计一致、实现待补**。真实实现应由GR验证身份、offset、包和写入自己的非活跃槽；不能把旧 `DFU_START` 当已实现。见 TECH 4.3.4(3)。 |
| D06｜预置业务抢占，关键体验 | 活动态空闲后台下载，报警、VoIP、定位全程可用；三轴有运动立即暂停，下次空闲 Range 续传。 | 下载核心逐块执行、支持暂停与持久 checkpoint；runtime监听 SIM/网络/OTA_BUSY；`idle` 和真实 HTTP 接收时限、SOS/通话/定位仲裁端口仍不可用。 | **待实现/实板验证**。必须测下载时SOS、来电、运动和定位争用；证明HTTP和UART每块可让出，不能凭主机单块测试宣称“零影响”。见 PRD F-031、TECH 4.3.3。 |
| D07｜静止与充电的含义，需裁决 | 客户旧文字把“三轴无数据/已休眠”视作天然无人使用，同时要求静止态CAT1硬断电，却在该状态安装两端。 | 我认为无三轴数据不能证明没有未解除的报警、通话/按键或传感器故障；方案提出休眠过渡 `SAFE_COMMIT`，显式检查全部资格，不为OTA周期唤醒。 | **理解调整 + 待冻结**。客户需确认“稳定静止”时长、满电停充口径、CAT1已断电时如何完成提交。保持未知不放行；实板测休眠电流及安装窗口。见冲突 C-10。 |
| D08｜固定70%及无Force，一致 | V0.9已把 `OtaBatteryThreshold` 从平台参数改为端侧固定70%，取消Force；需充电且无报警。 | GR仲裁模型用≥70%并检查充电等；69/70边界通过主机测试。产品 `yp001_ota_port_gates` 仍全未知。 | **逻辑一致、实板未通过**。须接 ETA69631 真实状态与电量；不能为达到门槛自动启充、调低阈值或用平台命令覆写。见PRD 3.8及TECH 5.6。 |
| D09｜准备与激活分离，安全差异 | 客户要求活动态写盘，静止窗只翻转重启，数秒完成；同时CAT1自身为常规单分区FOTA。 | 当前 PREPARED 不自动安装，GR一次性授予 INSTALL_PENDING；CAT1原生 `libfota2.request` 与500ms自动重启入口被关闭，因为尚未证明普通文件可受控激活/异常重启不越窗安装。 | **待实现**。需用当前底包与厂商官方API验证文件输入、延迟激活、pending/断电行为；不支持则此包型不能产品启用。数秒不可用目标须实板测，不能把Boot全槽交换耗时算作“翻转”。见冲突 C-14。 |
| D10｜GR A/B回退，尚为核心模型 | 蓝牙 A/B 双槽、签名、断电/失败恢复，拒绝成砖。 | 已有 `yp001_ota_boot` A/B/Scratch双日志交换、试运行/回退的C核心和故障注入；仍随现有应用编译，没有独立可启动Boot目标、确定Flash布局/Flash后端/签名密钥。 | **待实现**。现有主/交付Keil 0错误0警告不能证明Boot可起、可安全下载或实板回退；需首次部署与用户区白名单核对。见 TECH 4.3.4/4.3.5。 |
| D11｜CAT1自身回退边界，一致但未落地 | Cat.1是常规单分区升级，失败平台重推；不能承诺CAT1业务自建A/B。 | 我没有移植Lua A/B，当前厂商安装端口 `activate` 缺能力拒绝。CAT1底包若起不来，在线重推不可达。 | **理解一致、待实现**。需厂商FOTA能力与维修流程实测；“失败自动重推”只在旧版本仍能注册联网时成立。见 PRD V0.9、冲突 C-13。 |
| D12｜版本≤当前的处理，明确行为差异 | `TargetVersion≤当前`：清对应目标NV，不升级；客户没有要求返回fail。 | manager `compare<=0` 当前生成 `otaReplyMsg(fail)`，且没有已存在任务的“等同当前版本/仅清对应目标”终态；为了避免错清另一个组件暂时拒绝。 | **实际行为差异，待修代码与平台语义**。须在可信组件映射、真实版本和目标身份确定后实现不安装的幂等终态，只清独立OTA目标记录；明确对平台回执语义，不能清用户NV。见 PRD F-032、冲突 C-17。 |
| D13｜失败回报与自动重推，不完整 | 预置或提交失败上报 `otaResultMsg(fail)`，平台自动重推，零人工。 | 已有按hash的持久下载重试限次/退避和回退后的真实版本结果；下载/准备失败时GR owner保持，当前没有可信 CANCEL/ABORT 协议；真实平台outbox topic未映射，不能补报。 | **待实现**。要先定义两端都确认未安装/无pending的取消与释放事务，再形成“fail结果→QoS1→平台重推”闭环；不能超时直接清owner。永久坏签名不得无限重推同hash。 |
| D14｜平台消息确认，已按新版理解 | PRD V0.11规定仅SOS与找人等指定消息需平台应用ACK；OTA回执与结果只需MQTT QoS1，不等待新造OTA应用ACK。 | outbox按QoS1发，只有匹配packet/client/session的PUBACK才删除；结果和回执字段保持原协议。默认出站topic未配置，当前不能实网发送。 | **规则一致、实网待测**。确认使用协议2.9/2.10既有notsos主题、设备真实ID及上线会话；不能把publish入队当PUBACK。见 PRD F-033、协议2.9/2.10。 |
| D15｜旧数据保持，用户追加红线 | 用户明确要求两端OTA、回退、救援不能修改/清空/丢失现有用户数据；合法最新业务写入必须随程序回退保留。 | 任务记录/候选文件独立，Boot模型限制擦写白名单；产品禁止SDK层NVDS显式自动擦除。实际用户区全盘点、旧新版本schema兼容、真实Flash/LFS断电和ROM行为未证明。 | **设计对齐、实板未验收**。任何实际写入端口开放前须测绑定、号码、居民信息、配置、事件队列、定位/扫描记录在升级及回退后的逻辑值；不能用旧快照覆盖新数据。 |
| D16｜SIM热插拔续传，用户追加要求 | 用户要求拔卡检测与重新注册成功；OTA下载中应暂停并从原实体续传，不清任务或用户绑定。 | 旧 `netdrv_device`有SIM/IP状态恢复；OTA runtime在SIM_LOST/IP_LOSE时暂停，Range/checkpoint模型可跨重启；插卡后 CPIN、注册、IP、MQTT及同ETag实板链未验证。 | **待实板验收**。须分别证明SIM可识别、CEREG=1/5、IP、MQTT订阅、Range 206与原ETag、平台结果补报；只看到SIM READY不能记为重新注册成功。 |

## 当前最需要先处理的差异

1. **产品OTA目前不能实际运行**：需要GR独立Boot和Flash/用户区布局、包签名、CAT1下载及受控厂商激活、GR串口写槽、真实业务资格输入。现有代码的缺能力拒绝是保护状态，不能写成已完成升级。
2. **平台发布契约尚未冻结**：原 `otaMsg` 只有一个版本和整包地址，用户又要求两端从下载到确认严格串行。必须确定组件包、版本映射、顺序及上行如何表示整机实际版本，不擅加平台字段。
3. **F-032存在明确代码行为差异**：目标版本不高于当前时，当前返回fail；客户希望不升级并清对应目标记录。需要在可信映射和目标隔离后修复。
4. **失败自动恢复尚不闭环**：下载/准备失败缺可信释放owner，CAT1损坏底包也可能无法在线重推；应分别定义自动恢复、保持锁待维修的边界。
5. **静止窗与硬断电矛盾未最终裁决**：方案的SAFE_COMMIT是工程提案，不是客户已确认的原文要求。需实板证明静止+充电窗口、真实短暂停机、未引入周期唤醒和用户数据保持。

本文件没有把客户文档中的升级图当成当前固件的实测结果。当前主机/Lua测试、两份Keil编译与实板升级、平台联调、数据保持验收是不同证据层级。现有实施范围与日志见[代码整合清单](2026-10-12_双端OTA代码整合清单与开放条件.md)和[正式双端OTA方案](2026-10-12_CAT1与GR5526双端OTA落地方案_备份与失败恢复.md)。
