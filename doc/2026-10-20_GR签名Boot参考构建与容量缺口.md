## 体积核算

| 项目 | 字节 |
|---|---:|
| Code | 78172 |
| RO data | 3128 |
| RW data，解压前运行大小 | 3940 |
| Map Total ROM，含压缩后的 RW 初值 | 82552 |
| Load Region 未压缩大小 0x14CF8 | 85240 |
| 两种口径按 4096 对齐后的 Boot 预算 | 86016 |
| 当前应用单槽，477536 字节对齐 | 479232 |

不能直接把 Keil 输出 Code+RO+RW 与实际存储初值混为一谈。Map 的 Load Region 标注压缩大小 0x14278；本次两种口径均需 21 个扇区。

容量式：`1048576 - 2×479232 - 86016 - 8192(SCA) - 8192(NVDS) - 4096(交换) - 8192(Boot双日志) - 8192(仲裁双记录) = -32768`。

其中 SCA/NVDS 位置和容量来自此前官方资料及实机只读结果；日志/仲裁/交换仍是方案预算，尚未形成批准地址表。若维持两个当前槽及上述保留项，留给 Boot 的上限为 **53248 字节（52KiB）**，且没有应用增长余量。正式 Boot 还需加入本项目交换事务和保护校验，不能把参考体积当最终上限。

参考 AXF SHA256：`7962F014A9EF446CDE78082729F35337920001E3F5E9E52902F381D63B2216E1`。机器记录：隔离目录 `size_result.json`。

## 不能直接套用的原因

1. 示例 Boot 加载地址 0x00204000，与现有应用范围重叠；示例 DFU_INFO 为 0x00203000，也在现有应用范围内。直接启用其擦写会破坏当前程序。
2. 示例按名称找应用，默认名称和 0x00240000 地址不属于本机已批准布局。
3. 启用签名后，默认 `BOOTLOADER_SIGN_VERIFY_AFTER_DFU=1`，存在持久跳过验签标记；这不等于每次启动都独立验签，正式策略需单独设计。
4. 示例普通复制安装不是本项目已经主机测试的掉电可恢复双槽交换；没有本机试运行确认、失败回退及用户区白名单后端。
5. 参考板 BLE DFU、按键/日志和外围初始化不等于 YP001 板级适配。

## 后续实施顺序

1. 在隔离目标裁出最小 Boot，优先排除 BLE DFU 和参考板无关外围；由 CAT1 经应用串口预置，Boot 负责验签、交换、启动和恢复。保留可信验签，不能靠关闭安全功能满足容量。
2. 接入已有交换事务核心后重新独立链接，量出最终 Boot、RAM、栈及恢复时间，再确定是否还需继续减少应用体积。52KiB 仅当前数学上限。
3. 盘点所有持久用户区和代码写擦地址，建立默认拒绝的分区白名单；设计旧应用入口与 Boot 的首次迁移、断电恢复路径。不能通过搬动 NVDS 或恢复旧用户快照腾空间。
4. 完成签名包、保护区、扇区交换/反向恢复的主机故障注入，再做经授权的实机升级、掉电和回退验收。

CAT1 自身 OTA 仍需证明厂商接口的安全窗内受控激活和同布局用户数据保持；本次 Boot 构建不消除该项缺口。两端严格串行、70%+充电+稳定静止+无报警门槛不变。
