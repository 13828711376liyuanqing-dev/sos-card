# YP001 BLE 手机发现与 FPB 异常修正

修改人：SAM；时间：2026-10-08 22:08–22:44（北京时间，+08:00）。

## 目标与结论

目标：苹果 LightBlue 能发现并连接 YP001；蓝牙定位扫描暂不验收。

已完成两份工程编译和主工程下载复位。原先广播启动后可重复出现的 INVSTATE HardFault，在本次修正后观测窗口内未再出现；串口持续回应 `ble_status`。**最新结果：用户确认 LightBlue 发现并再次连接成功，随后串口实测 advertising=0、conn=0，验证当前连接已建立。完整断开重连流程及长时间稳定性仍需验收。** 后文按时间顺序保留早期失败及待验状态，以本段和末尾补充为最新结论。

当前 BLE 名称 `YP001`，本板启动日志地址 `EA:CB:3E:CF:01:06`。使用 LightBlue / nRF Connect 扫描，不以 iPhone 系统设置中的蓝牙列表作为普通自定义 BLE 的发现判据。

## 原因及证据链

1. 原工程是中心设备/扫描器流程，`Goodix_UART` 是扫描目标名，不是本板广播名称；没有手机可连接广播。
2. 加入可连接广播后，协议栈回报 ADV_START 成功，但随后陷入 HardFault：`LR=0008DF9F PC=200126E0 CFSR=00020000 HFSR=40000000`。PC 落在消息堆数据区，不能持续正常运行。
3. `patch_value` 曾被放入普通 RW 区 `0x2000BCB8`，FP_REMAP 读回 `0x2000BCA0`。仅将其独立并按 32 字节对齐到 `0x20023E40`，仍然出现同类异常。因此“只需 32 字节对齐即可解决”已被实测否定。
4. ROM `0x8DF9A` 的调用目标是 `stack_raw_log_output`，但原始日志开关区读回全零。仅凭 LR 不能判定是日志回调问题；未修改 ROM 或屏蔽异常。
5. 在 `phone_advertising_init` 入口停下后，临时将补丁表及补丁/调试寄存器影子中的重映射地址改到预留 RAM `0x2000AF80`，恢复运行：主循环继续执行，CFSR/HFSR 为零，串口 `ble_status` 能正常回应。
6. 将这一已实测位置固定到 scatter，再重新生成固件、下载、复位。无需临时 RAM 写入，仍能正常启动广播和响应 CLI。

已定位的工程级问题是 **FPB 补丁表链接放置不合适**。最终使用预留 RAM 内、128 字节对齐的已验证位置。尚未单独证明硬件限制究竟由地址范围还是更高对齐要求造成，不把猜测写成芯片规格结论。

- `20261008_ble_connect_swd.log` 显示 NoException，CFSR/HFSR 均为零，FP_REMAP=0x2000AF80。没有发现上一轮同样的 HardFault。
- `20261008_ble_connect_attempt.log` 和 `20261008_ble_connect_public_uart.log` 的观测窗口内，`ble_status` 持续 advertising=1、conn=255，未捕获 CONNECTED、DISCONNECTED 或连接失败事件。未取得用户点击时间，不能据此声称板子已经拒绝连接或没有收到空中请求。
